# Ротация JWT-секрета (без разлогина пользователей)

Зачем: `JWT_SECRET_KEY` — единственный ключ, которым подписаны и короткие
access-токены (30 минут), и долгие refresh-токены (30 дней). Если ключ утёк
(попал в переписку, в чужой ноутбук, в лог), надо просто сменить его. Раньше
смена ключа означала «все пользователи мгновенно разлогинены» — поэтому её
откладывали. Теперь это плановая операция.

## Как это устроено

- Токены **подписываются только текущим** секретом (`JWT_SECRET_KEY`).
- Проверяются **текущим и предыдущим** (`JWT_SECRET_KEY_PREVIOUS`):
  наш `decode_jwt` (кастомные эндпоинты), стратегия fastapi-users (`/jwt/*`),
  заявка на подтверждение нового устройства (`device_guard`).
- Access-токены живут 30 минут — они «переживают» смену ключа просто по времени.
  Refresh-токены живут 30 дней, поэтому предыдущий секрет нужно держать
  **не меньше 30 дней** (`AUTH_JWT.refresh_token_expire_days`).

## Процедура

```bash
# 1) Сгенерировать новый секрет (64 hex-символа — достаточно)
python3 -c "import secrets; print(secrets.token_hex(32))"
```

2. В продовом `~/microshop/.env`:

```dotenv
JWT_SECRET_KEY=<НОВЫЙ секрет>
JWT_SECRET_KEY_PREVIOUS=<СТАРЫЙ секрет>
```

3. Применить (перезапуск web/worker/beat — пересборка не нужна):

```bash
ssh user1@176.108.249.9 "cd ~/microshop && docker compose -p microshop-test \
  -f docker-compose.test.yaml up -d --no-deps $(sh scripts/lib/web_slot.sh) worker beat"
```

Имя слота бэкенда (`web-blue` или `web-green`) печатает `scripts/lib/web_slot.sh`:
в работе всегда один из двух слотов. Оба варианта подхватывают новый `.env`,
потому что переменные передаются в оба слота.

4. Проверить, что всё живо: `./scripts/ci/smoke_prod.sh` — вход и API отвечают;
   дополнительно можно войти в приложение на телефоне, не перелогиниваясь
   (refresh-токен пользователя подписан старым ключом и должен приниматься).

5. **Через 30+ дней** удалить `JWT_SECRET_KEY_PREVIOUS` из `.env` и повторить
   перезапуск бэкенда. После этого токены, подписанные старым
   ключом, перестают приниматься: кто не открывал приложение больше 30 дней —
   просто войдёт заново по коду/паролю.

## Проверки

Тесты `backend/tests/test_messenger_api.py`:

- `test_previous_secret_still_accepted_after_rotation` — токен, подписанный старым
  секретом, принимается и на `/jwt/users/me/` (стратегия fastapi-users), и на
  кастомных эндпоинтах; токен с посторонним ключом — 401;
- `test_new_tokens_signed_with_current_secret_only` — новые токены подписаны
  текущим секретом и НЕ проверяются предыдущим;
- `test_accepted_secrets_deduplicates` — если предыдущий совпадает с текущим или
  пуст, он не дублируется.

## Если ключ утёк (срочная ротация)

Порядок тот же, но после шага 3 стоит дополнительно попросить всех выйти на всех
устройствах (`POST /auth/sessions/revoke-all/` в профиле): это отзовёт
refresh-сессии и заставит войти заново, а не просто продлит старые. Ускоренный
вариант: не задавать `JWT_SECRET_KEY_PREVIOUS` вовсе — тогда все токены станут
недействительными сразу (пользователи войдут заново по коду/паролю).
