репозитория в **Public**. Документ намеренно не содержит реальных адресов,
ключей и персональных данных.

## Осталось намеренно

- **ФИО оператора в политике конфиденциальности и соглашении**
  (`docs/privacy-policy.md`, `docs/terms-of-service.md`,
  `frontend/public/*.html`): это обязательный реквизит работающего сервиса, и он
  уже опубликован на `pismo.space`. Заменить можно только вместе с переходом на
  ИП/юрлицо.
- **Адрес поддержки** в интерфейсе и юридических страницах: это публичный
  контакт сервиса, а не секрет. Если нужен отдельный ящик — заведите
  `support@…` и обновите тексты.
- **Скриншоты RuStore** (`docs/rustore-assets/screenshots/`) — данные
  синтетические, реальных людей и номеров нет.

## 1. История: оставляем как есть

Решено **не переписывать историю и не создавать новый репозиторий.** Причины:

- боевых секретов в истории нет: gitleaks по всем коммитам — 0 находок;
- остались только dev-заглушки: `.env.dev` раннего (Django) этапа
  (`SECRET_KEY=django-insecure-…` — стандартное значение Django для разработки,
  плюс пароль локальной БД) и `frontend/certs_from_backend/server.key` —
  self-signed сертификат для localhost, который ни один клиент не принимает и
  который больше не используется;
- сервер, где мог применяться старый `.env`, выводится из эксплуатации.

Если когда-нибудь понадобится почистить историю (например, перед передачей
проекта), это делается так — уже осознанно и с переклоном всех копий:

```bash
# нужен git-filter-repo (pip install git-filter-repo)
git filter-repo --path .env.dev \
                --path frontend/certs_from_backend \
                --invert-paths
git push --force-with-lease origin main
```

⚠️ После перезаписи все клоны нужно переклонировать (SHA изменятся), а на
сервере деплой подтянет новую историю через `git fetch` + `reset --hard`.

## 2. Проверить перед переключением

```bash
# секреты по всей истории (правила проекта)
docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest \
  detect --source=/repo --config=/repo/.gitleaks.toml --redact

# остатки личных данных и инфраструктуры
git grep -nE 'prod\.example\.com|alerts@example\.com' | head   # это заглушки — ок
git grep -nE '176\.108|id_rsa1|/home/user1|79109744376'        # должно быть пусто

node scripts/check-docs-links.mjs
```

ВАЖНО: мы осознанно публикуем историю как есть. Если в будущем в ней найдётся
настоящий секрет, переключение обратно не поможет: объекты останутся доступны
по SHA и попадут в кэш/форки. Тогда — переписать историю, сменить секреты и
только потом решать вопрос с публикацией.

## 3. Настройки GitHub

- Settings → General → **Change visibility → Public**.
- Settings → Code security:
  - **Secret scanning** и **Push protection** — включить;
  - **Dependabot alerts** — включить (`.github/dependabot.yml` уже есть);
  - **Private vulnerability reporting** — включить (на него ссылается
    `SECURITY.md`).
- Settings → Branches: защитить `main` (PR + зелёный CI, запрет force-push).
- Settings → Actions → General: разрешить только нужные actions, «Read
  repository contents» по умолчанию; deploy-job уже ограничен этим
  репозиторием.
- Помнить: **логи Actions в публичном репозитории видны всем**. Секреты
  маскируются, но пути, имена контейнеров и вывод git — нет; перед публикацией
  стоит посмотреть один прогон deploy/smoke глазами.

## 4. После публикации

- Добавить бейджи CI в README (по желанию).
- Проверить, что в форках не запускается deploy (в workflow стоит условие на
  репозиторий).
- При первом внешнем PR — прогнать `make check` и убедиться, что gitleaks не
  пропускает секреты из форка (push protection уже включён).
