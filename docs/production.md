# Продакшен-развёртывание

> Боевой прод (pismo.space) выкатывается автоматически: пуш в `main` → GitHub Actions
> → `scripts/ci/deploy_remote.sh` на сервере. Вручную поднимать ничего не нужно.
> Ниже — что где лежит и как устроена выкатка; отдельно — как поднять свой сервер
> «с нуля» по шаблону (`docker-compose.prod-template.yaml`).

## Файлы

| Файл | Назначение |
|---|---|
| `docker-compose.prod.yaml` | боевой прод-стек: слоты `web-blue`/`web-green`, одноразовый `migrate`, `db`, `rabbitmq`, `worker` (Celery), `beat`, `frontend` (nginx), `certbot`, `coturn`. Имя проекта внутри — `microshop-test` (историческое): от него зависят имена томов, менять нельзя |
| `docker-compose.prod-template.yaml` | шаблон одиночного прод-стека (`db`, `migrate`, `web`, `rabbitmq`, `worker`, `beat`, `frontend`) — «starting point» для своего сервера; в CI не используется |
| `frontend/Dockerfile.dist` | сборка статики (`vite build`) — «поставщик» файлов для тома |
| `frontend/Dockerfile.nginx` | nginx-раздача (конфиг без статики: она в томе) |
| `frontend/nginx-prod/default.conf` | SPA + прокси `/api` (включая WebSocket) и `/media` на слоты `web-blue`/`web-green`; монтируется в контейнер, поэтому правки применяются `reload`'ом |
| `scripts/stt/` | ассеты распознавания речи на устройстве: сборка движка, загрузка моделей, выкладка в `/stt/` (см. `docs/on-device-transcription.md`) |
| `scripts/ci/deploy_remote.sh` | деплой на сервере по шагам, без простоя |
| `scripts/lib/web_slot.sh` | печатает активный слот бэкенда (`web-blue`/`web-green`) — нужен скриптам, которые заходят в контейнер приложения |

Архитектура прод-версии: **nginx терминирует внешний трафик** (статик + прокси на
`web`), поэтому бэкенд поднимается на внутреннем HTTP (без self-signed TLS из dev).

## Деплой без простоя (боевой сервер)

Деплой запускается сам: GitHub Actions при пуше в `main` (job `deploy`) делает на
сервере `git reset --hard origin/main` и запускает `scripts/ci/deploy_remote.sh`.
Скрипт намеренно НЕ делает `up --force-recreate` (это пересоздавало всё, включая
базу, и сайт пропадал на 1–2 минуты), а обновляет по шагам:

1. уборка контейнеров, оставшихся от прерванного деплоя (иначе конфликт имён);
2. `docker compose build` — сборка образов без трогания работающих контейнеров;
3. **статика фронтенда**: одноразовый сервис `frontend-dist` копирует свежий
   `dist` в том `frontend_html`, из которого читает рабочий nginx. Контейнер
   nginx НЕ пересоздаётся — интерфейс не пропадает;
4. инфраструктура (`db`, `rabbitmq`, `coturn`, `certbot`) — только если изменилась;
5. `migrate` (одноразовый контейнер);
6. **бэкенд** (синий/зелёный): свободный слот `web-*` поднимается на новом
   образе, `worker` и `beat` перезапускаются рядом; в работу слот входит только
   после `healthy`, и лишь затем гасится прежний. Подробно — в разделе ниже;
7. nginx: конфиг проверяется (`nginx -t`) и применяется `nginx -s reload`. Так можно
   потому, что каталог `frontend/nginx-prod` смонтирован в контейнер: правки
   конфига видны сразу и не требуют пересоздания (оно случается только если
   менялось описание сервиса — тома, порты);
8. проверки: ревизия alembic совпадает с ожидаемой и `https://127.0.0.1/api/v1/health`
   отвечает 200. Снаружи затем проверяет job `smoke`.

## Скорость сборки и деплоя (2026-09-21)

Деплой длинный не из-за объёма правок, а из-за пересборки того, что могло бы
взяться из кеша. Замеры на прод-VM (2 vCPU): правка кода в бэкенде — 140 с
(`poetry install` 70 с, `chown -R` по венву 24 с, экспорт/распаковка образа 35 с),
статика фронтенда — 52 с (`pnpm install` + `vite build`).

- **`docker system prune -f` из шага деплоя убран.** Он сносил вместе с висячими
  образами и КЕШ СБОРКИ, поэтому на каждом деплое `poetry install` и `pnpm
  install` шли с нуля и заново распаковывались сотни мегабайт слоёв. Теперь
  убираются только остановленные контейнеры и висячие образы, а кеш сборки живёт
  и ограничен по объёму (`docker builder prune --keep-storage 3GB`; полный кеш —
  около 2.5 ГБ, диск прода 19 ГБ).
- **Из образа бэкенда убраны два лишних слоя.** `chown -R /home/microshop` (326 МБ
  и ~24 с) стоял ПОСЛЕ `COPY ./backend`, то есть переписывался при каждой правке
  кода; теперь poetry и венв ставятся сразу от рабочего пользователя (`USER
  microshop` + `pip install --user`), а chown остался на пустом `/app/media`.
  Кеш скачанных пакетов poetry (~114 МБ) в образе не нужен — удаляется в том же
  слое. Итог: образ 1.38 ГБ → 632 МБ (−54%), а правка кода пересобирает только
  копию кода (2.9 МБ) и запускает контейнер от того же пользователя, что и раньше.
- Дальше по желанию: статику фронтенда уже собирает job `frontend` в CI — если
  привозить её на сервер артефактом, шаг 3 станет распаковкой вместо
  `pnpm install` + `vite build` (выигрыш ~50 с на холодном кеше и ~25 с на
  тёплом). Сборка слотов и сервисов идёт параллельно и на 2 vCPU конкурирует сама
  с собой (`COMPOSE_PARALLEL_LIMIT`), поэтому выигрыш от неё ограничен.

Почему так можно: `index.html` отдаётся с `expires -1` (без кэша), а файлы в
`/assets/` имеют в имени хэш содержимого — поэтому подмена файлов в томе
подхватывается браузером сразу и не ломает открытые вкладки.

Тот же шаг (3) убирает прошлые сборки: имена файлов хешированные, копирование
ничего не удаляет — том рос бесконечно (к 21.09.2026 в `assets/` накопилось 3094
файла и ~97 МБ, диск сервера подошёл к 48%). `frontend/copy-static.sh` удаляет из
`assets/` файлы старше `KEEP_DAYS` суток (по умолчанию 1) — при нескольких выкатках
в день в томе остаётся 2–4 поколения, чего хватает открытым вкладкам. Порог
переопределяется переменной окружения сервиса `frontend-dist`.

Возраст сравнивается в минутах (`find -mmin +1440`), а не через `-mtime`: у
`-mtime` дробная часть суток отбрасывается, и порог молча сдвигается на сутки
вверх (`-mtime +1` — это уже двое суток).

Отдельно от тома `frontend_html` живут ассеты распознавания речи: каталог
`~/pismo-stt` на сервере (путь можно переопределить переменной `PISMO_STT_DIR`)
монтируется в контейнер nginx как `/stt/` — статика интерфейса деплогом не
трогается, а 140 МБ моделей не копируются каждый раз. Обновляются они командой
`scripts/stt/publish.sh`, перезапуск не нужен.

Две вещи, которые надо помнить:

- **не пушить, пока предыдущий деплой не завершился.** В workflow стоит
  `concurrency`, поэтому второй прогон подождёт, но лучше не полагаться на это;
- `worker` и `beat` при деплое перезапускаются, поэтому фоновая обработка (OTP,
  GIF, push) на несколько секунд замирает. На ответы API и на сайт это не влияет.

## Синий/зелёный бэкенд (почему API не пропадает)

Бэкенд представлен двумя сервисами, `web-blue` и `web-green`, из которых в
работе ровно один. Слот — это просто контейнер, образ у обоих один
(`microshop-test-backend:latest`).

Деплой обновляет бэкенд так:

1. определяет, какой слот в работе (по файлу состояния
   `~/.microshop-deploy/active-web-slot`, а если его нет — по запущенному
   контейнеру);
2. поднимает **свободный** слот на свежем образе и ждёт у него `healthy`;
   если слот не поднялся — он удаляется, а прод остаётся на прежнем (пользователи
   ничего не замечают, следующий деплой попробует снова);
3. записывает новый активный слот в файл состояния;
4. гасит прежний слот (сразу же: окно, когда работают оба слота, по умолчанию
   нулевое — почему именно так, ниже).

Обновление 17.09.2026 (этап B6 — доставка между процессами): события мессенджера
и сигналинг звонков теперь идут через мост RabbitMQ, а не только по локальным
сокетам (`api_v1/events/service.dispatch_realtime`, `api_v1/calls/views._deliver_signal`).
Каждый процесс получает событие из fanout и раздаёт его своим сокетам, поэтому
пользователь, попавший на другой слот, звонок получает и сообщения видит. Для
сигналинга есть подтверждение доставки (`ack`): зовущий знает, доставили ли сигнал
хоть в один сокет, и паркует вызов только когда абонент действительно офлайн.

Обновление 17.09.2026 (этап 2 B6): состояние звонков и присутствие тоже больше
не привязаны к процессу. Парковка офлайн-вызова и недоставленный сигналинг живут
в БД (миграция `f9a0b1c2d3e4`, `api_v1/calls/store.py`), а присутствие
собирается из своих сокетов и пульса других процессов (`presence-heartbeat`,
TTL 45 с).

Что это значит для деплоя: оба слота можно держать живыми дольше — звонки между
людьми на разных слотах соединяются, сообщения и статусы доходят. `DRAIN_SECONDS`
по умолчанию 0 (окно ~2 с), но увеличивать его уже безопасно: перед изменением
стоит один раз проверить вызов и статус «в сети» между двумя слотами вживую.

nginx знает оба слота сразу:

```nginx
resolver 127.0.0.11 valid=2s ipv6=off;
upstream backend {
    zone backend 64k;
    server web-blue:8000  resolve max_fails=2 fail_timeout=5s;
    server web-green:8000 resolve max_fails=2 fail_timeout=5s;
}
```

`resolve` (нужен nginx ≥ 1.27.3, на проде 1.27.5) заставляет nginx брать адреса
слотов из DNS в рантайме. Поэтому:

- конфиг не ломается, когда один из слотов не запущен (без `resolve` nginx бы
  просто не стартовал: «host not found in upstream»);
- остановленный слот перестаёт получать запросы через пару секунд, а не до
  перезапуска nginx;
- ошибка соединения со слотом, который только что погасили, повторяется на живом
  (`proxy_next_upstream error timeout`) — запрос до приложения не дошёл, поэтому
  повтор безопасен даже для POST;
- `proxy_connect_timeout 5s` нужен обязательно: остановленный контейнер не
  отвечает вообще (пакеты просто теряются), и без короткого таймаута nginx ждал
  бы минуту — ровно это дало замеренный секундный провал `api=000`.

Побочный эффект: пока слот остановлен, nginx раз в ~3 с пишет в лог
`web-blue could not be resolved (3: Host not found)` — это шум (перепроверка DNS),
запросы при этом обслуживает живой слот. Логи ротируются (5 МБ × 2), так что
место не кончается.

Проверено локально на отдельной docker-сети: nginx стартует с отсутствующим
слотом; пока живы оба — запросы обслуживаются; после остановки слота все запросы
идут на оставшийся (ни одного 502), включая случай, когда слот пересоздан с новым
IP.

## Запуск (свой сервер по шаблону)

```bash
# 1. Секреты (корневой .env): POSTGRES_PASSWORD, JWT_SECRET_KEY,
#    RABBITMQ_USER, RABBITMQ_PASSWORD
#    Плюс по желанию AT_REST_KEY (шифрование текстов сообщений в БД и файлов
#    media, openssl rand -hex 32) — без него данные пишутся как раньше.
# 2. Публичный origin фронтенда (тот же, что отдаёт nginx)
export VITE_API_ORIGIN=http://localhost   # или https://chat.example.com после TLS

docker compose -f docker-compose.prod-template.yaml up -d --build
```

Проверки: `curl http://localhost/api/v1/health` → `{"status":"ok"}`;
`curl http://localhost/` → index.html приложения.

## Пост в «Новости приложения» при выкатке

Правило проекта: заметная для человека правка описывается ещё и постом в канале
новостей (id 16), простым языком и без внутренних деталей — из `docs/changelog.md`
пост не берётся дословно: там числа, эндпоинты и причины, а подписчику нужен
смысл. Серверные и инфраструктурные изменения (рефакторинг, метрики, ротации
секретов) в канал не публикуются.

Публикуется штатным путём — сообщением от владельца канала, чтобы работали
уведомления и вложения. Из приложения это делает владелец руками, а при выкатке —
скриптом (в контейнере активного слота, там есть доступ к БД):

```bash
SLOT=$(cat ~/.microshop-deploy/active-web-slot)   # web-blue или web-green
cat /tmp/post.md | docker exec -i microshop-test-$SLOT-1 \
  poetry run python -m scripts.post_news --stdin
# Опубликовано: пост #441 в канале id=16
```

Токены для этого не нужны: скрипт отправляет пост той же функцией, что и обычное
сообщение из API (`messages.crud.send_text_message`), — значит работают права
канала, шифрование «в покое» и push подписчикам. Автор — аккаунт владельца
(`is_superuser`); можно указать конкретный номер через `--phone`, а другой канал —
через `--channel-id`. Id опубликованного поста вписываем в `docs/changelog.md`
(«опубликован пост #NNN»).

## Что важно для боевого прода

- **TLS**: добавьте в `frontend/nginx-prod/default.conf` server на 443 с
  сертификатами (Let's Encrypt) и редирект 80 → 443; тогда
  `VITE_API_ORIGIN=https://<host>`.
- **Медиа**: том `media_data` шарится между слотом бэкенда и `worker` (worker
  пишет GIF-файлы, бэкенд отдаёт через `/media` и раздаёт realtime). Не забывайте
  про бэкапы; очистка сирот теперь автоматическая (celery beat, ежедневно), но
  доступен и ручной запуск (`poetry run python -m scripts.cleanup_orphan_media
  --delete`).
- **RabbitMQ/Celery**: воркер исполняет фоновые задачи (SMS/OTP, GIF, уведомления);
  `beat` — периодику. Том `rabbitmq_data` хранит состояние брокера. Порт наружу
  не публикуется (внутренние подключения по compose-сети).
- **Секреты**: никогда не хранить в git; ротация через `.env`.
- **Шифрование «в покое»**: `AT_REST_KEY` шифрует тексты сообщений в БД и файлы
  media на диске (`docs/backend.md`, раздел «Шифрование данных в покое»).
  Переменную нужно добавить и в `environment:` используемого compose-файла —
  просто положить её в `.env` недостаточно, compose передаёт в контейнер только
  перечисленные переменные (в `docker-compose.prod.yaml` строки уже есть, нужен
  `web` и `worker`: воркер тоже пишет файлы и собирает текст push).
  Порядок включения на живом проде:
  1. добавить `AT_REST_KEY=$(openssl rand -hex 32)` в `~/microshop/.env`;
  2. выкатить деплой (пересоздаст слоты и воркер с новой переменной);
  3. перешифровать историю — сначала посмотреть объём, потом закрыть:
     `docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web \
      poetry run python -m scripts.encrypt_texts --dry-run` (весь текст: сообщения,
     черновики, комментарии, подписи, имена, профиль) и
     `... python -m scripts.encrypt_media --dry-run` (файлы), затем без `--dry-run`.
  Миграция `b7c8d9e0f1a2` расширяет короткие колонки до `text` — она накатывается
  деплоем автоматически и мгновенная (в PostgreSQL varchar → text не переписывает
  таблицу), отдельного окна обслуживания не нужно.
  Ключ хранить в менеджере паролей: потеря ключа = потеря текстов и файлов.
  Если ключ утёк — он ротируется без потери истории: новый в `AT_REST_KEY`,
  старый в `AT_REST_KEY_PREVIOUS`, затем скрипты с `--rotate`
  (`docs/at-rest-rotation.md`).
  Бэкапы при этом остаются валидными (в дампе шифротекст), но **ключ нельзя
  хранить на том же диске, что дампы** — иначе шифрование не защищает.
- **Режим технических работ** (плановое окно, миграция на живых данных, разбор
  инцидента): включается из приложения — настройки профиля → «Администрирование»
  → «Технические работы», либо скриптом в контейнере web при недоступном интерфейсе:
  `docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web-blue
  poetry run python -m scripts.maintenance on --message "Обновляем сервис"`.
  Раздел виден только владельцу (`is_superuser`): администраторы (`is_admin`)
  пользуются жалобами и приглашениями и не видят экран техработ, но рубильник им
  недоступен — включить его значит остановить сервис всем (см. ниже «Роли»).
  Пока режим включён, `/api/v1/*` отвечает 503 (кроме проверок живости, входа и
  запросов администраторов и владельца), а приложение показывает экран «Идут
  технические работы»; `/media/` и статика продолжают отдаваться. Состояние лежит
  в таблице `app_settings`, поэтому переживает деплой, а выключение не требует ни
  правки `.env`, ни перезапуска контейнеров (см. `docs/backend.md`, раздел «Режим
  технических работ»).  Клиентские дефекты режима исправлены 22.09.2026 (`docs/changelog.md`): запрос с
  протухшим access-токеном получает `401` и обновляет сессию, заглушка не закрывает
  экран входа, повтор refresh-токена в пределах минуты не выкидывает из всех вкладок.
  Срез по логам в окно техработ: `docker logs --since 3h microshop-test-frontend-1
  2>&1 | grep " 503 " | awk '{print $1}' | sort | uniq -c` — 503 по IP,
  `| awk '{print $6, $7}'` — по путям.- **Роли: администратор и владелец.** Роли в интерфейсе не выдают — только
  скриптом в контейнере web (он читает контакты владельца через ORM, поэтому
  зашифрованные псевдонимы вроде «Мама» расшифровываются):

  ```bash
  # кто уже админ и какие есть контакты
  docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web-blue \
    poetry run python -m scripts.set_admin --owner-phone +7… --list

  # выдать админские права контактам по именам (жалобы, приглашения, обход техработ)
  docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web-blue \
    poetry run python -m scripts.set_admin --owner-phone +7… --name Мама --name Вася

  # выдать по номеру телефона и, если нужно, роль владельца (с рубильником)
  docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web-blue \
    poetry run python -m scripts.set_admin --phone +7… --owner
  ```

  Перед выдачей полезен `--dry-run` (только показать) и `--revoke` (снять роль).
  Скрипт печатает таблицу «имя → телефон/логин → id → роль» и пишет изменение в
  лог сервиса.
- **Осторожно с именем compose-файла**: скрипты деплоя и бэкапов берут
  `COMPOSE_FILE` (по умолчанию `docker-compose.prod.yaml`) — это и есть боевой
  файл. Слово «test» в именах контейнеров/томов (`microshop-test-web-1`) — от
  `name: microshop-test` внутри него: переименовывать проект нельзя, иначе
  создадутся новые пустые тома. Исторический `docker-compose.test.yaml` удалён из
  репозитория; если он найдётся на сервере (untracked), он не используется —
  деплой правит `prod.yaml`.
- **WebSocket**: nginx уже проксирует с Upgrade — звонки и события работают.
- **Масштабирование**: in-memory rate limiter и WebSocket-менеджеры рассчитаны на
  1 процесс бэкенда; при горизонтальном масштабе нужен Redis/общий стор (а
  realtime-мост RabbitMQ уже рассчитан на несколько реплик web). Важное следствие:
  во время деплоя оба слота работают одновременно (~`DRAIN_SECONDS`), и лимиты на
  эти секунды считаются по каждому процессу отдельно.

## Почему статика обновляется без перезапуска

В образе nginx лежит только заглушка `index.html` (129 байт), а рабочие файлы
приходят из тома `frontend_html`. Проверено: `index.html` внутри контейнера и в
томе — это один и тот же файл (совпадает inode), то есть nginx читает файлы
напрямую из тома, и подмена файлов на лету не требует перезапуска nginx.

## Что ещё можно улучшить

Остались мелочи: пересоздание контейнера nginx (только когда меняется описание
сервиса в compose) и перезапуск `worker`/`beat` (фоновая обработка замирает на
несколько секунд). На ответы API и на выдачу сайта это уже не влияет.
