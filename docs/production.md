# Продакшен-развёртывание (starting point)

> Это отправная точка: реальный прод потребует домен, TLS-сертификаты, правильные
> секреты и (желательно) off-site бэкапы (см. docs/offsite-backup.md).

## Файлы

| Файл | Назначение |
|---|---|
| `docker-compose.prod.yaml` | прод-стек: `db`, одноразовый `migrate`, `web` (без reload/bind), `rabbitmq`, `worker` (Celery), `beat` (периодика), `frontend` (nginx) |
| `frontend/Dockerfile.dist` | сборка статики (`vite build`) — «поставщик» файлов для тома |
| `frontend/Dockerfile.nginx` | nginx-раздача (конфиг без статики: она в томе) |
| `frontend/nginx-prod/default.conf` | SPA + прокси `/api` (включая WebSocket) и `/media` на слоты `web-blue`/`web-green`; монтируется в контейнер, поэтому правки применяются `reload`'ом |
| `scripts/ci/deploy_remote.sh` | деплой на сервере по шагам, без простоя |
| `scripts/lib/web_slot.sh` | печатает активный слот бэкенда (`web-blue`/`web-green`) — нужен скриптам, которые заходят в контейнер приложения |

Архитектура прод-версии: **nginx терминирует внешний трафик** (статик + прокси на
`web`), поэтому бэкенд поднимается на внутреннем HTTP (без self-signed TLS из dev).

## Деплой без простоя (боевой сервер)

Деплой запускается сам: GitHub Actions при пуше в `main` (job `deploy`) делает на
сервере `git reset --hard origin/main` и запускает `scripts/ci/deploy_remote.sh`.
Скрипт намеренно НЕ делает `up --force-recreate` (это пересоздавало всё, включая
базу, и сайт пропадал на 1–2 минуты), а обновляет по шагам:

1. уборка контейнеров, оставшихся от прерванного деплоя (иначе конфликт имён);
2. `docker compose build` — сборка образов без трогания работающих контейнеров;
3. **статика фронтенда**: одноразовый сервис `frontend-dist` копирует свежий
   `dist` в том `frontend_html`, из которого читает рабочий nginx. Контейнер
   nginx НЕ пересоздаётся — интерфейс не пропадает;
4. инфраструктура (`db`, `rabbitmq`, `coturn`, `certbot`) — только если изменилась;
5. `migrate` (одноразовый контейнер);
6. **бэкенд** (синий/зелёный): свободный слот `web-*` поднимается на новом
   образе, `worker` и `beat` перезапускаются рядом; в работу слот входит только
   после `healthy`, и лишь затем гасится прежний. Подробно — в разделе ниже;
7. nginx: конфиг проверяется (`nginx -t`) и применяется `nginx -s reload`. Так можно
   потому, что каталог `frontend/nginx-prod` смонтирован в контейнер: правки
   конфига видны сразу и не требуют пересоздания (оно случается только если
   менялось описание сервиса — тома, порты);
8. проверки: ревизия alembic совпадает с ожидаемой и `https://127.0.0.1/api/v1/health`
   отвечает 200. Снаружи затем проверяет job `smoke`.

Почему так можно: `index.html` отдаётся с `expires -1` (без кэша), а файлы в
`/assets/` имеют в имени хэш содержимого — поэтому подмена файлов в томе
подхватывается браузером сразу и не ломает открытые вкладки.

Две вещи, которые надо помнить:

- **не пушить, пока предыдущий деплой не завершился.** В workflow стоит
  `concurrency`, поэтому второй прогон подождёт, но лучше не полагаться на это;
- `worker` и `beat` при деплое перезапускаются, поэтому фоновая обработка (OTP,
  GIF, push) на несколько секунд замирает. На ответы API и на сайт это не влияет.

## Синий/зелёный бэкенд (почему API не пропадает)

Бэкенд представлен двумя сервисами, `web-blue` и `web-green`, из которых в
работе ровно один. Слот — это просто контейнер, образ у обоих один
(`microshop-test-backend:latest`).

Деплой обновляет бэкенд так:

1. определяет, какой слот в работе (по файлу состояния
   `~/.microshop-deploy/active-web-slot`, а если его нет — по запущенному
   контейнеру);
2. поднимает **свободный** слот на свежем образе и ждёт у него `healthy`;
   если слот не поднялся — он удаляется, а прод остаётся на прежнем (пользователи
   ничего не замечают, следующий деплой попробует снова);
3. записывает новый активный слот в файл состояния;
4. гасит прежний слот (сразу же: окно, когда работают оба слота, по умолчанию
   нулевое — почему именно так, ниже).

Ограничение, которое важно знать: сигналинг звонков и presence/«печатает» живут
**в памяти процесса** (`backend/api_v1/calls/manager.py`), а не в мосте RabbitMQ
(через мост ходят только события от воркера). Поэтому пока работают оба слота,
часть пользователей попадает на другой процесс и их звонки друг друга не видят.
Именно поэтому `DRAIN_SECONDS` по умолчанию 0, а не 20 с: окно перекрытия длится
~2 с (столько nginx держит старый адрес в DNS). Настоящее перекрытие — а вместе
с ним и горизонтальное масштабирование — требует сначала перенести сигналинг и
presence в мост (см. `docs/feature-proposals.md`, B6).

nginx знает оба слота сразу:

```nginx
resolver 127.0.0.11 valid=2s ipv6=off;
upstream backend {
    zone backend 64k;
    server web-blue:8000  resolve max_fails=2 fail_timeout=5s;
    server web-green:8000 resolve max_fails=2 fail_timeout=5s;
}
```

`resolve` (нужен nginx ≥ 1.27.3, на проде 1.27.5) заставляет nginx брать адреса
слотов из DNS в рантайме. Поэтому:

- конфиг не ломается, когда один из слотов не запущен (без `resolve` nginx бы
  просто не стартовал: «host not found in upstream»);
- остановленный слот перестаёт получать запросы через пару секунд, а не до
  перезапуска nginx;
- ошибка соединения со слотом, который только что погасили, повторяется на живом
  (`proxy_next_upstream error timeout`) — запрос до приложения не дошёл, поэтому
  повтор безопасен даже для POST;
- `proxy_connect_timeout 5s` нужен обязательно: остановленный контейнер не
  отвечает вообще (пакеты просто теряются), и без короткого таймаута nginx ждал
  бы минуту — ровно это дало замеренный секундный провал `api=000`.

Побочный эффект: пока слот остановлен, nginx раз в ~3 с пишет в лог
`web-blue could not be resolved (3: Host not found)` — это шум (перепроверка DNS),
запросы при этом обслуживает живой слот. Логи ротируются (5 МБ × 2), так что
место не кончается.

Проверено локально на отдельной docker-сети: nginx стартует с отсутствующим
слотом; пока живы оба — запросы обслуживаются; после остановки слота все запросы
идут на оставшийся (ни одного 502), включая случай, когда слот пересоздан с новым
IP.

## Запуск

```bash
# 1. Секреты (корневой .env): POSTGRES_PASSWORD, JWT_SECRET_KEY,
#    RABBITMQ_USER, RABBITMQ_PASSWORD
# 2. Публичный origin фронтенда (тот же, что отдаёт nginx)
export VITE_API_ORIGIN=http://localhost   # или https://chat.example.com после TLS

docker compose -f docker-compose.prod.yaml up -d --build
```

Проверки: `curl http://localhost/api/v1/health` → `{"status":"ok"}`;
`curl http://localhost/` → index.html приложения.

## Что важно для боевого прода

- **TLS**: добавьте в `frontend/nginx-prod/default.conf` server на 443 с
  сертификатами (Let's Encrypt) и редирект 80 → 443; тогда
  `VITE_API_ORIGIN=https://<host>`.
- **Медиа**: том `media_data` шарится между слотом бэкенда и `worker` (worker
  пишет GIF-файлы, бэкенд отдаёт через `/media` и раздаёт realtime). Не забывайте
  про бэкапы; очистка сирот теперь автоматическая (celery beat, ежедневно), но
  доступен и ручной запуск (`poetry run python -m scripts.cleanup_orphan_media
  --delete`).
- **RabbitMQ/Celery**: воркер исполняет фоновые задачи (SMS/OTP, GIF, уведомления);
  `beat` — периодику. Том `rabbitmq_data` хранит состояние брокера. Порт наружу
  не публикуется (внутренние подключения по compose-сети).
- **Секреты**: никогда не хранить в git; ротация через `.env`.
- **WebSocket**: nginx уже проксирует с Upgrade — звонки и события работают.
- **Масштабирование**: in-memory rate limiter и WebSocket-менеджеры рассчитаны на
  1 процесс бэкенда; при горизонтальном масштабе нужен Redis/общий стор (а
  realtime-мост RabbitMQ уже рассчитан на несколько реплик web). Важное следствие:
  во время деплоя оба слота работают одновременно (~`DRAIN_SECONDS`), и лимиты на
  эти секунды считаются по каждому процессу отдельно.

## Почему статика обновляется без перезапуска

В образе nginx лежит только заглушка `index.html` (129 байт), а рабочие файлы
приходят из тома `frontend_html`. Проверено: `index.html` внутри контейнера и в
томе — это один и тот же файл (совпадает inode), то есть nginx читает файлы
напрямую из тома, и подмена файлов на лету не требует перезапуска nginx.

## Что ещё можно улучшить

Остались мелочи: пересоздание контейнера nginx (только когда меняется описание
сервиса в compose) и перезапуск `worker`/`beat` (фоновая обработка замирает на
несколько секунд). На ответы API и на выдачу сайта это уже не влияет.
