### Аутентификация (важно)

Порядок шагов на экране входа (он же — бэкенд-контракт):

1. `POST /api/v1/auth/password/status/` с `{phone_number}` →
   `{registered, has_password, otp_available}`:
   - `has_password=true` → шаг «введите пароль» (`/auth/password/login/`);
   - `has_password=false` и `otp_available=true` → сначала код на номер
     (`/auth/request-otp/` → `/auth/verify-otp/`), затем `POST /auth/password/set/` —
     чтобы дальше входить по паролю и не платить за SMS каждый раз;
   - `otp_available=false` (не настроен ни один канал доставки) → сразу создание
     пароля (`/auth/password/register/`), иначе регистрация была бы невозможна.
     В этом режиме номер при регистрации НЕ подтверждается (§ ограничения).
2. `otp_available` считается true, если заданы `SMS_AERO_*` (шлюз шлёт код на
   номер) или `TELEGRAM_GATEWAY_TOKEN`; обычный Telegram-бот учитывается только
   для аккаунтов с уже привязанным чатом (`tg_chat_id`).
3. Аккаунт, созданный кодом, помечается `password_set=false` (внутри — случайный
   пароль), поэтому `/auth/password/set/` для него не требует `current_password`,
   а для аккаунта с паролем — требует (несовпадение → 400).
4. Телефон — логин аккаунта: `PATCH /jwt/users/me/` с `phone_number` → 422
   (`UserUpdateWithProfileSchema._reject_phone_number_change`), в профиле поле
   только для чтения.
5. Также работает OAuth2 form `username`/`password` (`POST /auth/token/`).

### Периодические задачи (celery beat)

Расписание собирает `build_beat_schedule()` в `core/celery_app.py` — часть задач
зависит от настроек, поэтому оно не литерал, а функция (её проверяет
`tests/test_celery_schedule.py`):

| Задача | Когда | Что делает |
|---|---|---|
| `cleanup-orphan-media-daily` | ежедневно, 04:00 | убирает файлы media без ссылок в БД |
| `delete-expired-stories-hourly` | каждый час (:07) | удаляет истории старше 24 часов |
| `prune-call-signals` | каждые 5 минут | страховка от «зависших» парковки вызова и очереди сигналинга |
| `prune-security-events-weekly` | воскресенье, 04:30 | чистит журнал безопасности (записи старше 180 дней) |
| `send-due-scheduled-messages` | каждую минуту | отправляет отложенные сообщения (`scheduled_messages`), чьё время пришло |
| `telegram-poll-updates` | каждые `TELEGRAM_POLL_INTERVAL_SECONDS` (5 с) | long polling обычного Telegram-бота: ловит `/start bind_<код>` и привязывает чат к аккаунту (резервный канал OTP) |

**Про `telegram-poll-updates`:** задача нужна только там, где есть маршрут до
`api.telegram.org`. На хостингах без него (в т.ч. у нас на проде — сетевая
блокировка) поллинг бессмыслен: бот ничего не получает, а в логе воркера каждые
5 секунд появляется `succeeded in 0.0001s: None`. Поэтому задача попадает в
расписание только если заданы и токен бота, и разрешение на опрос:

```dotenv
TELEGRAM_POLL_ENABLED=false   # опроса нет вовсе — задачи не в расписании
```

Токен при этом лучше не стирать: он ещё нужен доставке кода в уже привязанный
чат (`tasks/otp_tasks.py`, шаг «обычный бот»). После смены переменной достаточно
перезапустить `beat` (`docker compose up -d beat`) — воркеру правки не нужны.
Проверить, что задачи больше нет: `docker compose logs beat | grep telegram` —
после перезапуска строк быть не должно.

**Политика паролей и защита входа:**

- Правила пароля — `core/passwords.py` (зеркало на фронте — `utils/passwordPolicy.ts`):
  минимум **10** символов, чёрный список частых паролей, запрет пароля из данных
  аккаунта (номер, e-mail, логин), 4+ одинаковых символа подряд и простых
  последовательностей. Композиционные требования («заглавная+цифра») сознательно
  не используются — NIST SP 800-63B их не рекомендует.
- **Перебор пароля** ограничен на уровне аккаунта: `password_login_attempts`
  (`auth/login_guard.py`) считает неудачи по номеру/логину; после
  `auth_login_max_failures=5` вход блокируется на 1 мин, затем задержка удваивается
  до `auth_login_lockout_max_seconds=1800`. Лимиты «по IP» обходятся сменой адреса.
- **Смена пароля отзывает все refresh-сессии** и возвращает новую пару токенов
  (текущее устройство остаётся, остальные вылетают); есть отдельный
  `POST /auth/sessions/revoke-all/`. Повторное использование уже отозванного
  refresh-токена тоже отзывает все сессии — семейный отзыв (защита от кражи).
  Исключение — гонка в пределах `REUSE_GRACE_SECONDS` (60 с) при ЖИВОМ потомке
  ротации (`replaced_by`, `refresh_sessions.py`): две вкладки или потерянный ответ
  получают ещё одну сессию вместо выброса из приложения. Если потомок уже отозван
  («выйти на всех», смена пароля), окно не действует.
- Флаги `password_set` и `password_weak` отдаются в `GET /jwt/users/me/`.
  `password_weak` ставится при входе (только там пароль виден в открытом виде),
  поэтому профиль показывает предложение сменить старый слабый пароль.
**E-mail-канал (второй после номера):** включён, когда заданы `SMTP_*` (см. `.env.example`).
Пока SMTP не задан — канал выключен: профиль пишет «отправка писем на сервере выключена»,
а на экране входа нет входа по e-mail. Как включить (пароль приложения у Gmail/Яндекса
и разовая настройка продового `.env` скриптом) — `docs/email-smtp.md`;
быстрая проверка состояния: `curl -s https://pismo.space/api/v1/auth/channels/`.

- Адрес подтверждается кодом из письма (`POST /auth/email/request-verification/` →
  `.../confirm-verification/`) — только после этого он годится для входа без пароля и
  восстановления доступа; при смене адреса через профиль `email_verified` сбрасывается.
- Вход по коду из письма (`/auth/email/login/request|confirm/`) и сброс пароля
  (`/auth/password/reset/request|confirm/`). Ответ на «запрос кода» одинаковый
  независимо от того, есть ли такой адрес (защита от перебора базы), а код живёт
  `auth_otp_expire_seconds`, одноразовый, с лимитом попыток и cooldown отправки.
- Сброс пароля отзывает все refresh-сессии и сразу выдаёт токены этому устройству.
- Ошибки валидации пароля проверяются ДО расхода кода, чтобы неудачная попытка не
  сжигала код из письма.
- Коды писем хранятся в `email_codes` (хеш, попытки, срок), письма отправляет воркер
  (задача `tasks.otp_tasks.send_email_code`), при незаданном SMTP код пишется в лог.
- `GET /auth/channels/` сообщает клиенту, включён ли e-mail-канал, чтобы экран входа
  не показывал недоступные кнопки.

### Регистрация по приглашениям (публичной регистрации нет)

Аккаунт заводится только по одноразовой ссылке `/invite/<token>`; выключенный
`REGISTRATION_ENABLED` рубильник сами приглашения не блокирует — они и есть контроль
доступа.

- Публичное: `GET /auth/invites/{token}/` — валидна ли ссылка (и за каким номером
  закреплена), `POST /auth/invites/{token}/register/` — регистрация (номер, пароль,
  `accept_terms`). Инвайт сгорает только при УСПЕШНОЙ регистрации (`used_at`).
- Только для `is_admin` или `is_superuser`: `GET /auth/invites/` (список + сколько действует),
  `POST /auth/invites/` (номер/заметка/срок), `DELETE /auth/invites/{id}/` — отзыв
  (`revoked_at`; отозвать использованную или уже отозванную → 400).
- Согласие с документами: `accept_terms=true` при регистрации пишет в журнал
  безопасности событие `terms_accepted` с перечнем документов (`audit.TERMS_DETAIL`).
  Поле необязательное — старые клиенты его не присылают.
- Выдать ссылку можно и без приложения: `make invite` (и `make invites`,
  `invite-revoke`, `admin` — см. шапку Makefile), вручную —
  `poetry run python -m scripts.create_invite`.


**Уведомления о критичных действиях (`api_v1/auth/security_notifications.py`):**
письмо уходит на **подтверждённый** e-mail аккаунта при смене пароля, сбросе пароля,
выходе на всех устройствах, смене адреса (письмо идёт на **прежний** адрес — так
владелец узнаёт о подмене) и при **входе с нового устройства**.

- Канал — только e-mail: Telegram недоступен из РФ-сетей, SMS Aero без договора
  отклоняет SMS, а у владельца нет других рабочих каналов.
- Если подтверждённого адреса нет, письмо не отправляется (чужой/ошибочный ящик не
  должен получать сведения об аккаунте) — в лог идёт запись; поэтому в профиле
  («Безопасность») и есть просьба подтвердить адрес.
- «Вход с нового устройства»: отпечаток браузера/приложения (`login_devices`,
  sha256 от User-Agent) + последний IP и время; **первый** вход аккаунта молчит
  (это регистрация), повторный вход с того же устройства — тоже.
- Суточный лимит: не более 20 писем на пользователя (защита от рассылки-спама).
- Задача `tasks.notifications.send_email`; при незаданном SMTP текст пишется в лог
  воркера (dev).

**2FA на новом устройстве + список активных входов
(`api_v1/auth/device_guard.py`, `device.py`, `refresh_sessions.py`):**

- Вход с устройства, которого у аккаунта не было, **не выдаёт токены**: сервер
  отправляет код на подтверждённый e-mail и отвечает `428` с телом
  `{detail, code_sent_to, challenge_token, expires_in}`. Клиент показывает шаг
  «Новое устройство» и зовёт `POST /auth/login/verify-device/` с challenge и кодом.
- `challenge_token` — короткоживущий JWT (отдельные `aud`/`type`, по умолчанию 10 мин),
  привязанный к подписи устройства: подтвердить вход можно только с того же браузера или
  приложения. Как access/refresh он непригоден.
- Первое устройство аккаунта (регистрация) и повторный вход с известного устройства —
  без кода. Если подтвердить нечем (нет подтверждённого e-mail или выключен SMTP),
  вход не блокируется: устройство запоминается, а владельцу уходит письмо-предупреждение
  (запирать человека вне собственного аккаунта нельзя).
- Вход по коду из письма (`/auth/email/login/confirm/`) и сброс пароля кодом
  (`/auth/password/reset/confirm/`) 2FA не требуют — владелец ящика уже доказал доступ;
  устройство при этом запоминается без лишнего письма.
- `GET /auth/sessions/` — активные входы (устройство, IP, время, «текущий» по подписи
  User-Agent); `DELETE /auth/sessions/{id}/` — завершить один вход (чужая сессия → 404).
  В профиле это блок «Безопасность» → «Активные входы», рядом «Выйти на всех устройствах».
- Данные устройства живут в `refresh_sessions` (подпись, User-Agent, IP) и переносятся
  при ротации refresh-токена, поэтому список показывает и «старые» входы.

**Журнал безопасности аккаунта (`api_v1/auth/audit.py`, таблица `security_events`):**
входы (успешные и неудачные — с привязкой к аккаунту, если номер зарегистрирован),
блокировка перебора, запросы кодов, запрос/подтверждение кода для нового устройства,
смена и сброс пароля, смена и подтверждение e-mail, отзыв сессий, удаление аккаунта.

- `GET /auth/security-log/` — история владельцу (только свои записи), профиль
  показывает блок «Безопасность» → «Последние действия»;
- хранится 180 дней (`audit.RETENTION_DAYS`), старые записи подчищает еженедельная
  задача `tasks.security_tasks.prune_security_events`;
- запись события никогда не ломает вход/смену пароля: ошибки логируются и гасятся
  (журнал важнее для разбора, а не для доступа);
- при удалении аккаунта записи остаются (`user_id` → NULL): сам факт «входили»
  полезен при разборе инцидентов.

- Все «личные» эндпоинты требуют заголовок `Authorization: Bearer <access_token>`.
- `/jwt/*` — fastapi-users: `POST /jwt/auth/login|logout`, `GET/PATCH /jwt/users/me/`.
- Custom-эндпоинты (`chats`, `messages`, `users/…`) используют `get_current_user` (`api_v1/auth/utils.py`), который принимает **те же** JWT от fastapi-users (в `decode_jwt` отключена проверка `aud`, субъект сверяется с БД). Защищённые от собственных токенов.

### Профиль и аватар

- `GET/PATCH /api/v1/jwt/users/me/` — профиль (схема `UserWithDetailsSchema`, включает `id`, `username`, `avatar_url`, `avatar_thumb_url`, `profile`, `chats`).
- `PUT /api/v1/users/me/avatar/?ext=png` — загрузка фото аватара. Тело запроса = **сырые байты** файла (без multipart), `ext` из белого списка `png/jpg/jpeg/gif/webp`, лимит 8 МБ. Возвращает `{avatar_url, avatar_thumb_url}` (оба — `/media/avatars/…`).
- `DELETE /api/v1/users/me/avatar/` — удаление аватара (и файлов). Возвращает `{avatar_url: null, avatar_thumb_url: null}`.
- `avatar_url` — оригинал того, что загрузили; `avatar_thumb_url` — миниатюра
  128px (Pillow), которую клиент показывает в списках, шапках, историях и
  пушах: оригинал с телефона может весить мегабайты, а на экране это кружок
  40–56px. Миниатюра сохраняет прозрачность (PNG), иначе — JPEG q85;
  если файл не читается как изображение, `avatar_thumb_url = null` и клиент
  показывает оригинал (`avatar_url`).
- `avatar_url`/`avatar_thumb_url` отдаются в профиле, поиске/контактах,
  участниках чатов, аватаре группы и авторе истории (см. `core/avatar_store.py`).
- Для уже загруженных аватаров миниатюры досоздаёт скрипт:
  `poetry run python -m scripts.make_avatar_thumbs --apply` (без `--apply` — dry-run).

### Тихие часы (не беспокоить)

Push рисует система (в Android — SDK RuStore, в PWA — служба push браузера),
поэтому «сейчас тихо» решает **сервер** — при закрытом приложении клиент такую
проверку просто не выполняет.

- Настройка живёт в `profile`: `quiet_hours_enabled`, границы `quiet_hours_start` /
  `quiet_hours_end` (минуты от полуночи, 0…1439) и `quiet_hours_offset` — сдвиг
  местного времени от UTC. Сдвиг присылает клиент при сохранении: у устройства он
  всегда актуален, а серверу не нужна база часовых поясов (`zoneinfo` есть не во
  всех образах). Значения по умолчанию — окно 23:00–08:00, звонки разрешены.
- Правила — `core/quiet_hours.py` (`local_minutes`, `in_quiet_window`,
  `skips_push`): окно может идти через полночь, а совпавшие границы считаются
  «окна нет» (иначе вышло бы 24 часа тишины).
- Фильтр — `tasks/notifications.py::_awake_ids` перед отправкой: сообщения в тихие
  часы не уходят (`is_call=False`), звонок пропускается только если человек снял
  галочку «Разрешить звонки» (`is_call=True`). Само событие живым сокетам и
  непрочитанное в приложении остаются — мы не будим, а не теряем сообщение.
- Уведомления безопасности (`send_security_push`) эту проверку НЕ проходят
  намеренно: вход с нового устройства и заморозка аккаунта важнее тишины.
- Тесты: `backend/tests/test_quiet_hours.py` (20 — границы, переход через
  полночь, разные пояса, звонки).

### Шифрование данных «в покое» (at-rest)

Переписка хранилась открытой в БД: диск, снапшот, дамп или скопированный
`db_dump/*.sql` — и содержимое чатов читается без доступа к серверу. Теперь текст
сообщений лежит зашифрованным ключом сервера.

- Ключ — `AT_REST_KEY` (32 байта в hex или base64, `openssl rand -hex 32`). Пока
  не задан — шифрование выключено, данные пишутся и читаются как раньше, поэтому
  переменную можно добавить в любой момент и ничего не сломается.
- Шифрование — `core/at_rest.py` (AES-256-GCM, формат
  `enc:v2:<номер ключа>:<base64 nonce|ct>`; старый `enc:v1:` без номера
  читается), в колонку встроено типом `core/db_types.py::EncryptedText`: код
  продолжает работать со строкой как обычно.
- Существующую историю перешифровывает скрипт `scripts/encrypt_texts.py`
  (`--dry-run` — объём, `--batch` — размер порции, `--only` — одна колонка или
  таблица). Идемпотентен. Старое имя `scripts/encrypt_messages.py` оставлено для
  случая «только сообщения».
- Поиск по сообщениям: SQL по зашифрованному полю ничего не найдёт, поэтому имя
  файла ищется в SQL (метаданные не шифруем), а текст — перебором истории
  страницами по 500 с расшифровкой и подстрокой без учёта регистра; предел —
  `SEARCH_SCAN_LIMIT = 20_000` сообщений на запрос. Поведение для пользователя не
  изменилось (подстрока, все чаты или один, 403 не-участнику).
- Шифруется не только текст сообщений, но и остальной пользовательский текст:
  черновики (`message_drafts.text`), комментарии и предложенные посты каналов,
  подписи историй (`stories.caption`), личные имена контактов
  (`contacts.custom_name`), комментарий и заметка по жалобе, заметка журнала
  модерации, заметка к приглашению, «о себе» (`profile.bio`), имя/фамилия/статус
  пользователя и заголовок/описание/имя сайта в карточке ссылки. Полный список —
  в `scripts/encrypt_texts.py::TARGETS`, он же сверяется с моделями тестом
  `tests/test_at_rest_texts.py` (забытая колонка = падающий тест).
- Короткие колонки (`varchar(120)`, `varchar(255)` и т.п.) расширены до `text`
  миграцией `b7c8d9e0f1a2`: шифротекст длиннее открытого текста (base64 + nonce +
  тег), иначе запись упала бы на переполнении. В PostgreSQL смена varchar → text
  не переписывает таблицу, миграция мгновенная; ограничение длины осталось в
  схемах Pydantic.
- Что остаётся открытым осознанно: идентификаторы и то, по чему идёт поиск или
  уникальность — `username`, `phone_number`, `email`, `chats.name`,
  `chats.channel_username`, `messages.file_name`, `link_previews.url`; плюс
  служебные коды (`reason`, `status`, `action`, `kind`, `mime_type`) и метаданные
  (кто, когда, в каком чате, размер файла).
- Чего это НЕ делает: не защищает от администратора сервера (у него есть ключ) и
  не заменяет E2EE.
- Файлы media (вложения, аватары и их миниатюры, истории, картинки предпросмотра)
  шифруются тем же ключом: `core/media_crypto.py`, формат `encf:v1:` — заголовок
  (magic + размер содержимого + базовый nonce) и куски по 1 МиБ, каждый своим
  AES-256-GCM (`AES-256-GCM(ciphertext||tag)`). Размеры кусков фиксированы, поэтому
  позиция любого байта считается арифметикой, а не поиском по файлу.
- Отдаёт медиа теперь приложение, а не `StaticFiles`: расшифровать файл умеет
  только код (`api_v1/media/views.py`). nginx лишь проксирует `/media/`. Роут
  поддерживает Range (`206`/`416`), `HEAD`, `ETag`/`304` и `If-Range`, расшифровывая
  только нужные куски — без этого не работала бы перемотка видео. Ответ идёт
  потоком, в памяти держится один кусок.
- Почему не «шифруем файл целиком»: видео на сотни мегабайт не влезло бы в память,
  а Range-запрос требует читать середину файла.
- `Content-Type` по расширению, но html/svg/xml всегда отдаются как
  `application/octet-stream`; имя из URL проверяется (`..`, абсолютный путь, симлинк
  наружу → 404).
- Существующие файлы перешифровывает `scripts/encrypt_media.py` (`--dry-run`,
  `--limit`, идемпотентен, каждый файл пишется атомарно через временный + `rename`).
- Запись идёт через `core/media_crypto.write_file` (используют `media_store` и
  `avatar_store`), поэтому воркер (GIF) тоже пишет зашифрованным — ключ нужен и ему.
- Файлы, загруженные до включения ключа, читаются как есть; если ключ потерян, а
  файлы зашифрованы, `/media/...` отвечает `503` (а не отдаёт шифротекст).
- ВАЖНО: ключ не попадает ни в дампы БД, ни в бэкап медиа — потеря ключа означает
  потерю текстов и файлов. Хранить в менеджере паролей; в проде переменную нужно
  добавить и в `environment:` используемого compose-файла (`.env` сам в контейнер
  не попадает).
- Ротация ключа: пишем только `AT_REST_KEY`, читаем его и `AT_REST_KEY_PREVIOUS`
  (список через запятую). В шифротексте есть номер ключа, а история переводится на
  новый ключ скриптами с `--rotate` (текст — `encrypt_texts`, файлы —
  `encrypt_media`); значения, не читаемые известными ключами, не перезаписываются.
  Процедура — `docs/at-rest-rotation.md`.

### Текст сообщения в уведомлении (`profile.notification_preview`)

Push показывает текст прямо на экране блокировки — его видит любой, кто взял
телефон, и текст оседает в галерее уведомлений. Настройка выключает превью:
остаётся имя отправителя (понятно, открывать ли чат), тело — «Новое сообщение».
По умолчанию `true` — как было до появления настройки.

- Решает сервер (`tasks/notifications.py::_body_for_user`) по тому же принципу,
  что и тихие часы: push рисует система, а не наша страница.
- Тело уведомления теперь персональное, поэтому push группируется по паре
  «заголовок + тело» (`_group_by_push`): иначе одному уведомлению с текстом ушли
  бы и те, кто превью выключил.
- E2EE-чаты текст и так не отдают (там своё нейтральное тело) — два правила не
  конфликтуют.

### Роли: администратор (`is_admin`) и владелец (`is_superuser`)

Раньше флаг был один, и «дать админку» означало «дать всё»: разбор жалоб,
приглашения, обход экрана техработ и сам рубильник техработ. Рубильник — это
остановка сервиса для всех, поэтому он остался у владельца, а помощникам
выдаётся роль администратора:

| Возможность | `is_admin` | `is_superuser` |
|---|---|---|
| Разбор жалоб (`/moderation/reports/`) | ✅ | ✅ |
| Приглашения (`/auth/invites/`) | ✅ | ✅ |
| Обход экрана техработ (и в приложении, и по API) | ✅ | ✅ |
| Рубильник техработ (`PUT /system/maintenance/`) | — | ✅ |

- Проверки на сервере: `get_current_admin` (любая из ролей) для модерации и
  приглашений, `get_current_superuser` (только владелец) для рубильника;
  в `main.py` заглушка техработ пропускает обе роли (`_request_from_admin`).
- Роль отдаётся клиенту в `CurrentUser` (`is_admin`, `is_superuser`) — фронт по
  ней показывает админский раздел, а раздел «Технические работы» — только
  владельцу.
- Выдаётся скриптом (в интерфейсе ролей не выдают):
  `poetry run python -m scripts.set_admin --owner-phone +7… --name Мама` —
  роль администратора, `--owner` — роль владельца, `--list` — показать контакты
  владельца и их роли, `--search` — найти пользователя по имени/логину.

### Режим технических работ (рубильник)

Сервис можно «закрыть» на время обновления или разбора инцидента: обычные
запросы к API начинают получать `503` с `{"detail": {"code": "maintenance",
"message": …}}`, а приложение показывает полноэкранный `503` («Идут технические
работы») — вместо ошибок и полупустых списков.

- Состояние живёт в таблице `app_settings` (ключ `maintenance`, значение JSON:
  `{enabled, message, since, by}`), а не в `.env`: переключается на живом сервере
  без перезапуска контейнеров и переживает деплой. Логика — `core/maintenance.py`,
  модель — `core/models/app_setting.py`, слой API — `api_v1/system/views.py`
  (миграция `c5d6e7f8a9b0`).
- Статус публичный (приложение опрашивает его при запуске, при возвращении на
  вкладку и раз в 30 с), переключение — только у владельца (`is_superuser`;
  администратору рубильник недоступен, см. раздел «Роли»). Включение пишется
  в лог (`logger.warning` с id администратора), автор и время — в самой записи.
- Список исключений — `MAINTENANCE_EXEMPT_PREFIXES` в `main.py`: проверки
  живости (`/health*`), сам рубильник (`/system/maintenance`), маяк связи
  (`/system/ping`, по нему приложение отличает «нет сети» от техработ) и вход
  (`/auth/`, `/jwt/`). Без этого владелец не смог бы ни войти, ни выключить
  режим, а мониторинг принял бы плановые работы за упавший сервис. Запросы
  администратора проходят всегда (проверка токена + роль), а в
  приложении ему не показывают заглушку — иначе он не смог бы вернуться в
  админскую панель.
- Результат проверки кэшируется в памяти процесса на `CACHE_TTL_SECONDS` (2 с):
  режим проверяется на каждом запросе, и лишний `SELECT` там ни к чему. Цена —
  до двух секунд задержки переключения на других процессах.
- Если БД недоступна, режим считается **выключенным**: техработы — осознанное
  действие человека, а не следствие аварии (иначе недоступная БД выглядела бы
  как плановые работы и прятала бы настоящую причину).
- Перехватываются только пути `settings.api_v1_prefix` (то есть `/api/v1/`),
  поэтому `/media/` и статика продолжают отдаваться (их файлы и так открыты по
  ссылке, а клиент видит заглушку). WebSocket-middleware не перехватывает —
  открытые соединения доживают до переподключения.
- Аварийный путь (в приложение не зайти — сломана сборка, потерян пароль):
  `poetry run python -m scripts.maintenance on|off|status [--message "…"]` внутри
  контейнера `web-*`. Нужен он редко: вход (`/auth/`, `/jwt/`) из заглушки
  исключён, а приложение больше не закрывает экран входа (см. `docs/frontend.md`).
- **Негодный access-токен получает `401`, а не заглушку** (правка 22.09.2026).
  `admin_viewer_of` в `api_v1/auth/utils.py` различает четыре исхода: `admin`,
  `user`, `anonymous` (токена нет — отвечаем 503) и `invalid` (токен передан, но
  истёк/подделан/это refresh-токен — отвечаем `401` с кодом `token_invalid` через
  `token_invalid_error`). Иначе клиент с протухшим access-токеном не догадался бы
  обновить сессию: авто-refresh во фронте срабатывает только на `401`, и
  приложение жило «полуживым» (пустые чаты, логины вместо личных имён) до
  перезагрузки страницы. См. `docs/changelog.md`, раздел от 22.09.2026.

### Realtime между процессами web (мост RabbitMQ)

- Живые WebSocket-соединения живут в памяти конкретного процесса `web`. Чтобы
  событие доходило до абонента на другом процессе (деплой «синий/зелёный»,
  масштабирование), любой процесс публикует событие в fanout-обмен
  `settings.events_exchange`, а каждый процесс читает свою очередь и раздаёт
  событие своим сокетам (`core/amqp.py`, `api_v1/events/bridge.py`).
- Единая точка отправки — `api_v1/events/service.dispatch_realtime` (локальная
  раздача + мост). Через неё идут сообщения, прочтение, presence, «печатает…»,
  события каналов и реакций на истории. Сигналинг звонков идёт тем же обменом,
  но раздаётся в `call_manager` (по префиксу типа `call-`), а отправляет его
  `api_v1/calls/views._deliver_signal`.
- Дублей нет: в теле есть метка процесса (`origin`) — своё же событие из fanout
  процесс отбрасывает, а повторную доставку отсекает по `event_id`.
- Для сигналинга есть подтверждение доставки (`ack`, `wait_for_delivery`):
  зовущий знает, доставлен ли сигнал хоть в один сокет, и паркует вызов только
  когда абонент действительно офлайн. Без ack при нескольких процессах вызов
  парковался бы зря.
- Публикация не должна задерживать HTTP: канал переиспользуется, есть таймауты
  (0,5 с) и предохранитель (5 с тишины после двойной неудачи) — недоступный
  брокер оставляет работу хотя бы локальным сокетам.
- Присутствие («человек у экрана») собирается из двух источников: свои активные
  сокеты и пульс других процессов. Каждый процесс раз в 15 с публикует список
  своих активных пользователей (`presence-heartbeat`, `api_v1/events/bridge.py`),
  остальные держат его до TTL 45 с (`events_manager.mark_remote_present`). В БД
  это состояние положить нельзя: «у экрана» — свойство живого сокета, а сокеты
  есть только у своего процесса. Мёртвый процесс просто перестаёт пульсировать,
  и его пользователи через TTL становятся «не в сети».
- Что остаётся в памяти процесса: только сами сокеты и кэш чужого пульса — по
  TTL он и так самовосстанавливается.

### Хранилище сигналинга звонков (парковка и очередь)

- Парковка офлайн-вызова и недоставленный сигналинг живут в **БД**
  (`pending_call_offers`, `queued_call_signals`; миграция `f9a0b1c2d3e4`, код —
  `api_v1/calls/store.py`). Раньше это было состояние процесса
  (`api_v1/calls/manager.py`): при двух процессах web абонент, открывший
  приложение на другом слоте, не получал припаркованный вызов, а зовущий —
  придержанный ответ.
- Строки технические и почти всегда пустые: срок жизни минуты (`expires_at`,
  naive UTC), удаляются при чтении и лениво при записи; плюс страховочная
  задача `tasks.call_tasks.prune_call_signals` раз в 5 минут.
- Пределы прежние: парковка одна на абонента (новый вызов вытесняет старый),
  очередь до `MAX_QUEUED_MESSAGES` = 64 (лишнее отбрасываем с начала).
- Следствие: перекрытие слотов `web` больше не теряет вызовы — второй слот
  можно поднимать с окном (см. `docs/production.md`).

### Звонки и история звонков

- Сигналинг — WebSocket `/api/v1/ws/calls?token=` (`api_v1/calls/views.py`;
  доставка между процессами web — через мост, см. раздел выше). ICE-серверы
  с временными TURN-кредами — `GET /api/v1/calls/ice-servers/`.
- Публичный статус техработ (`GET /system/maintenance/`) учитывает зрителя:
  запрос с токеном администратора (или владельца) получает `enabled=false`, а
  настоящее состояние — в `actual_enabled`. Так администратор не упирается в
  заглушку даже в старом клиенте (кэш PWA, не обновлённое приложение), который
  про роли ничего не знает и решает «показывать ли экран» по этому же ответу;
  админская панель читает `actual_enabled`. Проверка «запрос от администратора»
  живёт в `api_v1/auth/utils.py::request_from_admin` — её используют и заглушка
  (`main.py`), и статус.
- Групповой звонок: сообщение `call-drop` убирает из состава того, кого
  сбрасывают (не отправителя) — оно адресовано неответившему, поэтому обычная
  обработка «завершение от отправителя» выкидывала бы из звонка инициатора.
- **Групповой звонок «mesh» (до четырёх человек)** идёт по тому же каналу:
  клиент адресует SDP/ICE конкретному участнику (`to_user_id`), а признак `group`
  вместе с `chat_id` говорит серверу, что вызов общий. Сервер проверяет, что чат
  групповой и оба участника в нём, ведёт состав звонка (`_group_calls`) и
  рассылает его всем сообщением `call-peers` — без списка участников полносвязную
  схему не собрать. Пятый получает `call-unavailable` с `reason=full`.
- Исход звонка пишется **системным сообщением** в личный чат участников
  (`_persist_call_record`: `kind='call'`, `call_kind` — audio/video, `call_state`
  — completed/missed/declined, `call_duration`, `call_caller_id`). Отдельной
  таблицы звонков сознательно нет: своя таблица разъезжалась бы с лентой чата
  (звонок есть в истории, а в чате его нет), а миграции на записи о звонках уже
  были (`2026_09_09_1400-d0e1f2a3b4c5`).
- `GET /api/v1/calls/history/?limit=&offset=` (`api_v1/calls/crud.py`) собирает эти
  записи по всем чатам человека, свежие первыми, и добавляет то, что нужно
  экрану: собеседника (`peer`), тип, исход, длительность и `outgoing`
  (инициатор — `call_caller_id`, с фоллбэком на автора записи для старых строк).
  Скрытые модерацией записи не отдаём. Направление считает сервер, а не клиент:
  правило одно и то же и в истории чата, и на экране звонков.

### Стикеры и эмодзи-паки

- **Стикер — это библиотека, а не сообщение.** Паки и картинки лежат в своих таблицах (`sticker_packs`, `stickers`), поэтому один и тот же файл на диске переиспользуется: отправили стикер десять раз — файл один. Файлы идут через `media/` и считаются в общей квоте (у стикера владельца нет, поэтому квота считает через `JOIN` с паком).
- **Что приходит с клиента:** картинка уже обрезана, но сервер всё равно приводит её к виду (`core/sticker_store.py`): PNG/WebP с прозрачностью пересобираются в WebP (сначала lossless, если не влезает — lossy), сторона обрезается до 512 px, лимит 512 КБ; **GIF отдаётся как есть** — пересборка сломала бы анимацию, поэтому слишком большой GIF честно отклоняется.
- **Отправка стикера** — обычное вложение с `sticker=true` в `POST /messages/attachment/`: сообщение получает `kind='sticker'`, и клиент рисует его без пузыря. В E2EE-чате сервер файл не читает, поэтому «в стикеры» из сообщения там делает клиент (загружает расшифрованные байты обычной загрузкой), а `POST /stickers/from-message/` отвечает `400` с пояснением.
- **Настройки эмодзи живут на сервере** (`emoji_pack_choices`, `emoji_favorites`): каталог паков — это наборы Unicode-эмодзи в клиенте (`frontend/src/utils/emojiPacks.ts`), а `GET/PUT /users/me/emoji/` держит только ключи включённых паков и избранное. `PUT` заменяет выбор целиком — так не нужны отдельные ручки на добавление/удаление/перестановку, а состояние на сервере всегда ровно то, что человек видит. Смысл в том, что выбор переезжает между устройствами (отметил паки на телефоне — видно и на ноутбуке).

### Медиафайлы

- Каталог `backend/media/`, раздаётся приложением: `/media/...` (роут `api_v1/media/views.py`, см. `main.py`). Не `StaticFiles`: файлы на диске зашифрованы (`AT_REST_KEY`), и расшифровать их может только код; он же обслуживает Range-запросы (перемотка видео).
- Файлы сообщений кладутся в `backend/media/` корень, аватары — в `backend/media/avatars/`.
- **Список «используемых» файлов — один**: `core/media_usage.collect_used_media_names` (сообщения вместе со снимками пересылки и ответа на историю, `stickers.file_url`, аватары людей и групп с миниатюрами и иконками уведомлений, медиа историй, `link_previews.image_url`). Им пользуются и периодическая задача `tasks/media_tasks.cleanup_orphan_media`, и скрипт `scripts/cleanup_orphan_media.py`. > Публичные «читающие» эндпоинты `users` (`GET /users/`, `GET /users/{user_id}/`,
> `GET /users/{user_id}/chats/`) и legacy `products`/`posts`/`telegram` **удалены**
> (не использовались мессенджером и открывали чужие данные).
>
> На «дорогие»/«писательские» эндпоинты действует **per-user rate limit**
> (в минуту, ключ — `user.id`): отправка/пересылка/загрузка/GIF и поиск по
> сообщениям и людям; лимиты задаются в `core/config.py` (`*_limit_per_minute`).
>
> **Модерация (требование RuStore к UGC):** жалоба, блокировка и удаление
> аккаунта есть в интерфейсе приложения («Пожаловаться»/«Заблокировать» —
> в шапке чата и в меню сообщения, «Заблокированные» — в «⋯» списка чатов,
> «Удалить аккаунт» — в профиле). Разбор жалоб — служебный экран «Жалобы»
> в меню «⋯», видимый только пользователю с ролью администратора или владельца
> (назначение и инструкция для модератора — `docs/rustore.md`, §9.1).
> Жалобы лежат в `user_reports` (статусы `new → in_review → resolved/rejected`),
> автоблокировки по жалобе нет — решение принимает модератор вручную.
>
> **Блокировка бывает двух видов** (`user_blocks.messages_allowed`): полная
> (по умолчанию: переписка и звонки запрещены в обе стороны, чат скрыт из списка)
> и мягкая — «только звонки»: переписка и чат остаются, запрещён дозвон.
> Второй вид нужен чаще, чем полная: «не звони мне, но писать можно». Разница
> видна на уровне проверок: сообщения и скрытие чата смотрят только полную
> блокировку (`is_blocked_between`, `get_blocked_ids`), а звонки — любую
> (`is_call_blocked_between` в `api_v1/calls/views._is_call_blocked`).
> Истории фильтруются как переписка — по полной блокировке.

### Модель данных (основное)

- `user` — `id`, `username` (уник.), `phone_number` (уник., null), `first_name`, `last_name`, `email` (nullable), `hashed_password`, `avatar_url`, `avatar_thumb_url` (миниатюра 128px), `status` (текст-статус), `last_seen` (присутствие); профиль (1:1), чаты (m2m), сообщения.
- `profile` — 1:1 к `user`: `bio`, `birth_date`, `language`, `country`, `notifications_enabled`, `privacy_mode`, `notification_preview` (показывать текст сообщения в push), поля тихих часов (`quiet_hours_*`).
- `chats` — `id`, `name`; участники через m2m `chat_user_association`. **Личный чат = ровно 2 участника**.
- `messages` — `id`, `text`, `timestamp` (default now()), `user_id`, `chat_id`, `reply_to_id` (self FK), `is_read`, `is_pinned`, `edited_at`, `file_name/file_url/mime_type/file_size`, поля пересылки `forwarded_from_id`/`forwarded_sender_id`/`forwarded_sender_name`/`forwarded_chat_id` (снимок «от кого»). Индекс `(chat_id, timestamp)`.
- `message_reactions` — PK `(message_id, user_id)`, `emoji` (по одной реакции на пользователя).
- `otp_codes` — OTP-коды телефонов (хеш кода, попытки, срок); `refresh_sessions` — refresh-токены с отзывом/ротацией.
- `chat_invites` — ссылки-приглашения в группы (токен, срок годности, лимит
  входов, отзыв);
- `device_keys` — публичный ключ E2EE устройства; строка идентифицируется парой `(user_id, device_id)` (несколько устройств на аккаунт, миграция `c4d5e6f7a8b9`); `chat_group_keys` — обёртки ключа группы (по строке на участника: ключ группы, зашифрованный на общем секрете с `wrapped_by`); `chat_device_keys` — обёртки ключа ЧАТА по устройствам (PK `chat_id+user_id+device_id`, миграция `f1a2b3c4d5e6`, эндпоинты `GET/PUT /keys/chat/{chat_id}/`): одно и то же устройство-раздатчик (`wrapped_by_user_id` + `wrapped_by_device_id`) и получатель знают общий секрет ECDH, поэтому телефон и компьютер читают общие сообщения; `push_subscriptions` — Web Push-подписки; `rustore_push_tokens` — токены RuStore Push; `chat_mutes` — «без уведомлений» (PK `user_id+chat_id`); `telegram_bind_links` — коды привязки Telegram; `message_drafts` — черновики сообщений (PK `user_id+chat_id`, текст в том же виде, что в сообщении: в E2EE-чате это шифротекст).
- `sticker_packs` — свои наборы стикеров (`owner_id` → `user`, `title` до 60 символов, `position` — место вкладки в панели); `stickers` — картинки пака (`pack_id` с `ON DELETE CASCADE`, `file_url`/`mime_type`/`file_size`, `position`). Владелец — у пака, у стикера его нет: удалили пак — ушли и стикеры, а файлы с диска уберёт ночная уборка сирот.
- `emoji_pack_choices` (PK `user_id+pack_key`, `position`) и `emoji_favorites` (PK `user_id+emoji`, `position`) — какие паки эмодзи человек включил себе и что положил в «Мои»; порядок задаёт клиент, сервер хранит как есть.
- `user_blocks` — блокировки 1-1 (уникальная пара `blocker_id+blocked_id`, `messages_allowed` — вид блокировки); `user_reports` — жалобы (`reporter_id`, `reported_id`, `reason`, `comment`, контекст `chat_id`/`message_id`, `status`, `note`, `created_at`, `reviewed_at`).
- `pending_call_offers` — припаркованный входящий вызов (PK `user_id`, `call_id`, `payload` JSONB, `expires_at`); `queued_call_signals` — недоставленный сигналинг (`user_id`, `payload` JSONB, `expires_at`). Обе — технические, живут минуты; зачем в БД — в разделе про realtime.
- Legacy-таблицы `post`/`product`/`order`/`group` — **удалены** (миграция `f6a7b8c9d0e1`); моделей нет.

### Язык серверных текстов (русский / английский)

Тексты, которые человек видит в ответах API, письмах, push и SMS, переводятся
на его язык — иначе английский интерфейс обрывался бы русской ошибкой.

- Каталог: `backend/core/i18n.py` + `core/i18n_en.py`. Ключ перевода — **сам
  русский текст** (`t("Чат не найден")`), перевод — английский, в словаре `EN`.
  Так же сделано во фронтенде (`src/i18n/index.ts`) — один принцип на весь проект.
- Чего нет в каталоге, **остаётся русским**: перевод делается по частям, ничего не
  ломая. `detail=f"…"` писать нельзя (f-строку не перевести) — страж-тест
  `tests/test_i18n.py` это проверяет.
- Язык берётся **только из профиля** (`Profile.language`):
  - в HTTP-запросах — из заголовка `X-Locale` (его ставит приложение из профиля,
    middleware `request_locale` в `main.py`); если заголовка нет, `get_current_user`
    один раз читает язык из профиля;
  - в письмах, push, SMS и фоновых задачах — `lang=получателя`
    (`locale_of_user(session, user_id)`): уведомление читает получатель, а действие
    мог совершить кто-то другой.
- Если язык неизвестен (запрос без входа, профиль пуст) — русский, как раньше.
- Push: у каждого получателя может быть свой язык, поэтому заголовок и тело
  собираются **на каждого человека** и группируются по готовому тексту (личное имя
  контакта, настройка «показывать текст», язык).
- Журнал безопасности (`SecurityEvent.detail`) и тексты писем тоже переведены:
  их человек читает в профиле и в почте.

### Проверки backend (должны проходить)

```bash
cd backend
poetry run flake8 . --exclude=.mypy_cache,__pycache__
poetry run isort .
poetry run black .
poetry run mypy main.py core api_v1 tasks
```

Замечания:

- Poetry env живёт в `~/.cache/pypoetry/virtualenvs/backend-*` (можно использовать и на хосте, и в контейнере).
- `mypy` лучше запускать с `--cache-dir=/tmp/<xxx>`, чтобы не плодить `root`-овые `.mypy_cache` в репозитории.
- `api_v1/users/schemas.py` **исключён из Black** (`tool.black.exclude`) — форматируйте вручную.
- В alembic-версиях допустимы строки длиннее 88 (per-file-ignore E501).
- Тесты: `poetry run pytest -q` (unit-тесты идут всегда; БД/API-интеграция — только при заданном `TEST_DATABASE_URL`, см. `backend/tests/`; для HTTP-тестов нужен `httpx` из dev-зависимостей). mypy по тестам не гоняется (`main.py core api_v1`).
