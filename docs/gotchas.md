# Общие правила и «грабли»

То, что легко забыть и на чём уже спотыкались. По темам правила разложены в
соседних документах ([frontend.md](frontend.md), [backend.md](backend.md),
[checks.md](checks.md)), а здесь — короткий список на все случаи.



- Приватный чат — это `Chat` ровно с 2 участниками в `chat_user_association`; поиск/создание — через `chats/crud.get_or_create_private_chat`.
- В модели `Message` поле `timestamp` уже было в БД (default `now()`) — оно отображается в модели, **без** отдельной миграции.
- Маска телефона обязана содержать `+7` (маска `+7 (999) 999-99-99`), иначе валидация «11 цифр, начинается с 7» не сработает.
- `ApiUser.username` обязателен (не `null`) — при сохранении профиля нельзя слать `username: null`.
- Загрузка файлов/аватара — **без** `python-multipart` (сырое тело запроса). Не добавляйте `UploadFile`/`File`, иначе понадобится эта зависимость.
- Сериализация сообщений — dict-хелперы в `messages/crud.py` (`message_to_dict`, `message_basic_to_dict`); реакции агрегируются `{emoji, count, reacted_by_me}`.
- Не регенерируйте `.mypy_cache`/`__pycache__` в репо (часть файлов `root`-овые, не удалить без sudo). Mypy — с `--cache-dir=/tmp/...`.
- Тестовая авторизация «по коду»: код попадает в лог ТОЛЬКО когда доставка не настроена (dev) — `docker compose logs -f worker` (задача Celery `tasks.otp_tasks.send_sms_otp`, строка «SMS-заглушка») или `logs -f web` (`enqueue_sms_otp` пишет код, если не задан ни один канал). При настроенном SMS Aero код в лог НЕ пишется (виден только id сообщения шлюза; код можно взять в кабинете SMS Aero → Отчёты).
- SMS Aero: базовый адрес API — `https://gate.smsaero.ru` (старый `gateway.smsaero.ru` не резолвится — проверено `getent hosts`); подпись (`sign`) в `/v2/sms/send` обязательна, бесплатная — `SMS Aero`.
- Стоимость (аккаунт от 10.09.2026, `/v2/tariffs` и страница цен): «Код в Telegram» — **1,99–2,49 ₽**, авторизац. SMS — 8,30–12,59 ₽ (МТС 8,49), сервисные SMS — 8,49–32,19 ₽, бесплатная подпись дороже всего (Билайн до 46,90 ₽). Поэтому воркер сначала отправляет код в Telegram (`/v2/telegram/send` с `text` + `sign` = автооткат на SMS), а обычное SMS — только если сам вызов упал. Для входа пароль остаётся основным способом: SMS тратится лишь один раз — при регистрации.
- Перед e2e-проверкой API удобно создать временных пользователей через `POST /users/` + `POST /auth/token/`, а после удалить их по `username`-префиксу.
- **Воркер Celery не перезагружается сам.** Правки в `tasks/` (в том числе новые
  аргументы задач) подхватывает только `web` (uvicorn reload); воркер продолжает
  жить со старым кодом. Если `web` уже шлёт новый аргумент, задача падает с
  `TypeError: <task>() got an unexpected keyword argument …`, а следствие
  выглядит как «функция не работает»: эндпоинт отвечает 202, сообщения нет.
  После правок задач — `docker compose restart worker beat` (20.09.2026: так
  «перестали отправляться» гифки — новой подписи `caption` старый воркер не знал).
- **Альбом — это метка, а не отдельная сущность.** `messages.album_id` ставит клиент;
  группировку в сетку делает тоже клиент (`utils/albums.ts`), а сервер только
  считает лимиты (частота загрузок и анти-флуд) ОДИН раз на альбом — по первому
  вложению, и push отправляет только на первое (`album_first` в
  `send_attachment_message`). Иначе пачка из 10 фото упиралась бы в лимит
  «10 загрузок в минуту», а получателю прилетало бы 10 уведомлений.
- **Подпись забирает ПЕРВОЕ ушедшее вложение** (у альбома — первая картинка), а не
  «последнее». Текст для подписи берётся в окне отправки (`MediaSendDialog`), а не
  из поля ввода: поле может быть занято следующим сообщением.
- **Перевод есть только в Chrome 138+ на компьютере.** Где нет `Translator`
  (мобильные браузеры, WebView Android-приложения, Safari/Firefox) — пункта меню и
  кнопки нет вовсе (`canOfferTranslation()`, `utils/translation.ts`): «починить»
  его можно только отправкой текста на сторонний сервис, а это ломает обещание
  E2EE. Состояние устройства объясняет раздел «Устройство» в профиле.
- **Распознавание речи в браузере умеет только Chrome на КОМПЬЮТЕРЕ.** Расширение
  `SpeechRecognition.start(MediaStreamTrack)` (звук ЗАПИСИ в распознаватель, а не
  микрофон) есть только там: Chrome на Android и Safari слушают микрофон, а
  переданный трек молча игнорируют — нажатие «В текст» заканчивалось
  «Распознавание не получило звук», хотя звук в записи есть. Наличием API это не
  проверяется, поэтому смотрим платформу (`fileSpeechCapable` в
  `utils/voiceRecognition.ts`); на телефоне кнопки нет — путь один, приложение
  Pismo, где запись распознаёт само устройство (`services/nativeSpeech.ts`).

- **Эффекты видео выключаются при показе экрана — и это не поломка.** Пока идёт
  показ, камера не отправляется: обработка (canvas) и «сырая» камера гасятся
  (`_releaseCameraForScreenShare`), а после остановки `_restoreCamera` собирает
  эффекты заново из настроек стора. Если добавить в этот путь подмену дорожки «как
  для камеры», эффект прилипнет к дорожке ЭКРАНА.
- **«Сырая» камера (`runtime.rawCameraTrack`) обязана обновляться при каждом
  захвате.** У собеседников лежит обработанная дорожка, поэтому по `localMedia` её
  уже не найти: не обновишь — не сможешь ни выключить эффекты, ни сменить камеру,
  а старая камера останется включённой (индикатор горит, хотя видео нет).
- **`canvas.captureStream` — обязательное условие эффектов.** Нет его (старые
  WebView, часть встроенных браузеров) — окно эффектов честно пишет причину, а не
  просто прячет кнопку. Проверка дешёвая: `isVideoEffectsSupported()`.
- **QR-код: сведения о формате рисуются в ДВУХ местах, и ветви там разные.** Биты
  0–5 идут ВНИЗ по столбцу (строки 0–5), биты 9–14 — ВЛЕВО по строке (столбцы
  5–0), у второй копии набор зеркальный (биты 0–7 — верхняя строка справа,
  8–14 — левый столбец снизу). Перепутанные ветви дают код, который «выглядит
  правильно» и не читается ни одним сканером: без сверки с независимым эталоном
  (python-qrcode) и настоящим сканером (zxing) такую ошибку не поймать.
- **QR-код в интерфейсе всегда тёмный на светлом** (`--ms-qr-*` одинаковы во всех
  темах): инвертированный код («негатив») сканеры читают через раз.
- **Виды активности собеседника живут в событии `typing` (поле `kind`).** Список
  видов есть и на сервере (`TYPING_KINDS`), и на клиенте
  (`utils/peerActivity.ts`); за согласованностью следит тест. Сервер незнакомый вид
  заменяет на `text`, поэтому новый вид, добавленный только на клиенте, просто не
  покажется — без ошибки в логе.
- **Функции, передаваемые опциями в composable'ы `Messenger.vue`, объявляйте
  `function`, а не `const`.** `Messenger.vue` — один огромный `<script setup>`:
  `useMediaRecording({ beginActivity })` стоит ВЫШЕ объявления, и `const` даёт
  «использование до объявления» (страница падает при загрузке).
- **Тест задачи воркера должен подменять `make_engine`/`make_session` из
  `tasks/base.py`, а не `db_helper`.** Воркер создаёт СВОЙ движок из настроек
  (`settings.db_url`), у фикстуры API подменена только зависимость запросов
  (`app.dependency_overrides`), поэтому такая задача в тесте уходит в БД из
  настроек. Локально это совпадает с тестовой БД случайно — `make test-backend`
  задаёт ещё и `DATABASE_URL`, — а в CI падает на пароле
  (`InvalidPasswordError`) и выглядит как поломка кода. Образец:
  `tests/test_gif_caption.py` (тест воркера) и `tests/test_message_reminders.py`.
  Проверка «как в CI»: `TEST_DATABASE_URL=… pytest`, но БЕЗ `DATABASE_URL`.
- **Бюджет веса бандла — шаг CI, и он падает от любого нового импорта.**
  `check-bundle-size.mjs` сравнивает gzip каждого чанка с
  `scripts/bundle-size-baseline.json` (допуск +3% и не больше 2 КБ): новый модуль
  в основном чанке сразу даёт превышение. Чтобы не растить главный чанк, тяжёлое
  выносим в ленивые чанки (`dynamic import`), например конвейер эффектов видео
  (`stores/call/videoPipeline.ts`) и мелкие настройки отдельным модулем
  (`utils/videoEffectSettings.ts`). Рост по делу — `--update-baseline`, и это
  стоит отметить в `docs/changelog.md`. С 20.09.2026 и сборка, и эта проверка
  входят в `make check-frontend` (до этого были только в CI).
- **Celery + RabbitMQ 4.x: воркер не должен просить global QoS.** Kombu читает
  версию брокера и для RabbitMQ >= 3.3 считает «семантику QoS несовпадающей» со
  спекой (`Transport.qos_semantics_matches_spec` → `False`), после чего Celery
  выставляет `basic_qos(..., a_global=True)`. В RabbitMQ 4.x это deprecated-фича,
  запрещённая по умолчанию: в логе брокера на каждом подключении воркера
  появляется `[error] Deprecated features: global_qos ... not permitted anymore`,
  и фича будет удалена «независимо от конфигурации». Поэтому в
  `core/celery_app.py` признак переопределён на `True` — просим per-consumer
  prefetch (как рекомендует RabbitMQ). Для нас это то же поведение: очередь одна,
  консьюмер один, prefetch = 4 × concurrency (80); страж —
  `tests/test_celery_broker_qos.py`. Второе предупреждение (во время старта),
  `management_metrics_collection`, — это сбор метрик плагином management: он
  РАЗРЕШЁН по умолчанию, и убрать строку можно только отключив сборщик метрик
  (`deprecated_features.permit.management_metrics_collection = false`) — тогда в
  management UI пропадут графики очередей, так что это предупреждение терпим.
- **Новая модалка обязана объявить себя слоем: `useMobileLayer`.** На телефоне
  «назад» закрывает верхний слой — но только те, о которых знает стек
  (`frontend/src/composables/useMobileOverlay.ts`). Правило: рядом с состоянием
  модалки одна строка `useMobileLayer(() => myDialogOpen.value, closeMyDialog)`
  (закрывающая функция — та же, что у крестика). Забытая модалка ломает именно
  то, чего ждёт человек: «назад» либо выходит из приложения прямо из-под
  открытой карточки, либо закрывает чат или раздел под ней. Отдельный случай —
  императивные окна (`Dialog.create` в `utils/appDialogs.ts`): у них нет флага
  состояния, поэтому они регистрируются вручную — `const release = pushMobileLayer(() => dialog.hide())`,
  а `release()` зовётся в `onDismiss`.
- **Число маркеров в истории = число нажатий «назад», которые ждёт экран.**
  Android-обёртка решает так: `if (webView.canGoBack()) webView.goBack(); else super.onBackPressed()`
  (`MainActivity.onBackPressed`). Значит «внутри приложения делать нечего» -
  это не «слоёв ноль», а «история кончилась». Отсюда правило: у КАЖДОГО уровня
  навигации (модалка, раздел внутри экрана, режим выделения) обязан быть свой
  шаг. Грабля 20.09.2026: у разделов настроек профиля своего шага не было —
  два действия («в раздел» + «закрыть настройки») тратили один маркер, и на
  телефоне второе нажатие уходило системе = выход из приложения из-под
  открытых настроек. Теперь раздел — слой: `useMobileLayer(isInSection, backToSections)`
  в `views/UserProfile.vue` (админский экран не входит: он отдельный вход).
- **Модалки — слои, а не перечисление по именам.** Раньше каждая модалка должна
  была попасть в `layers`/`overlayOpen` в `useChatNavigation`; забытая модалка
  не участвовала в решении, и шаг «назад» уходил тому, кто под ней. Теперь
  стек — единственный источник правды, а на каждый слой в истории браузера есть
  свой шаг: сколько модалок открыл — столько раз «назад» их и закроет.
- **Гашение маркеров — счётчиком, а не флагом** (`programmaticBacks` в
  `useChatNavigation`): когда разом снимаются два слоя (например, переключили
  чат — модалки закрылись сразу), уходит два `history.go(-1)`, и первый popstate
  не должен снимать защиту со второго. На случай «popstate не придёт» есть
  таймаут-страховка — иначе защита съела бы следующее настоящее «назад».
- **Список `layers` в стеке — `shallowRef`, а не `ref`.** Глубокий proxy
  подменяет объекты слоёв при чтении, а слои снимаются сравнением по ссылке
  (`layer !== mine`) — с `ref` снятие молча не работало (тест
  `mobileOverlay.spec.ts` это и поймал).
- **Проверять навигацию — только живыми нажатиями в браузере на 390px.**
  Стек слоёв и историю браузера видно только в работе: открой модалку/раздел и
  посчитай `history.length` и `history.state.position` до и после (у нас каждое
  открытие = +1 запись с `pismoNav: true`). Замер в jsdom этого не показывает,
  а «на глаз» расхождение в один шаг не читается.
