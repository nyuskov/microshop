# Мониторинг прода

Скрипт `scripts/monitoring/check_prod.sh` запускается **на локальной машине** по cron
каждые 15 минут и проверяет:

| Проверка | Что означает |
|---|---|
| `https://pismo.space/` → 200 | фронтенд отдаётся (nginx/SPA живы) |
| `/health` → 200 | процесс API жив |
| `/health/ready` → 200 | API видит **БД и RabbitMQ** (иначе 503) |
| `/api/v1/auth/channels/` → 200 | роутер `api_v1` собран и отвечает |
| контейнеры на сервере | все `Up`, ни одного `unhealthy` |
| свободное место на диске сервера | предупреждение при < 10% (порог `DISK_MIN_FREE_PERCENT`) |
| свежесть бэкапа в `~/Документы/pismo_backup/db` | предупреждение, если последний дамп старше 26 ч (значит, локальный cron бэкапа не работает) |

## Оповещения

Основной канал — **e-mail (SMTP)**: Telegram `api.telegram.org` недоступен ни с
прод-сервера, ни с локальной машины (блокировка в РФ-сетях, проверено), а SMS через
SMS Aero без договора с операторами отклоняются.

SMTP-настройки берутся автоматически: сначала из окружения, затем из локального
`.env`, затем из **продового** `.env` по ssh (поэтому достаточно настроить один раз —
см. `docs/email-smtp.md`). Если SMTP нигде не задан, скрипт пишет предупреждение в
лог и в вывод: «НЕТ КАНАЛА ОПОВЕЩЕНИЙ» — это значит, что о проблемах вы не узнаете.

SMS можно включить принудительно (`ALERT_SMS=1`, номер в `ALERT_PHONE`) — на случай,
когда SMTP недоступен, но помните про цену и требование договора.

Повторные оповещения об одной и той же проблеме приходят не чаще, чем раз в
`ALERT_MIN_INTERVAL` минут (по умолчанию 180), при восстановлении — отдельное письмо
«прод снова в норме».

## Установка

```bash
./scripts/monitoring/install_local_cron.sh              # каждые 15 минут
CRON_SCHEDULE='*/5 * * * *' ./scripts/monitoring/install_local_cron.sh

crontab -l | grep -v '# pismo-monitor' | crontab -       # удалить
```

## Проверка

```bash
./scripts/monitoring/check_prod.sh               # обычный прогон (оповестит при проблеме)
./scripts/monitoring/check_prod.sh --dry-run     # отчёт без отправки писем
./scripts/monitoring/check_prod.sh --test-alert  # отправить тестовое письмо
```

Лог: `~/Документы/pismo_backup/logs/monitor.log`, состояние дедупликации —
`logs/monitor.state`.

Проверено 10.09.2026: обычный прогон «всё в норме», недоступный сайт детектируется
(тест с `SITE_URL=http://127.0.0.1:9`), тестовое письмо доставлено на
`nyuskov@gmail.com`, письмо с прод-сервера через приложение (`core.mailer`) тоже
уходит — то есть цепочка «проблема → письмо» рабочая.

## Чего мониторинг не покрывает

- Он сам запускается локально: если выключен компьютер, проверок нет. Отчасти это
  компенсируется проверкой свежести бэкапа (его тоже делает локальный cron).
- Не проверяет бизнес-логику (что регистрация/вход реально работают) — это делает
  смоук-тест после деплоя в CI.
