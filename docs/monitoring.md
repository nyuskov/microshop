# Мониторинг прода

Скрипт `scripts/monitoring/check_prod.sh` запускается **на локальной машине** по cron
каждые 15 минут и проверяет:

| Проверка | Что означает |
|---|---|
| `https://pismo.space/` → 200 + `<!DOCTYPE html` | фронтенд отдаётся (nginx/SPA живы) |
| `/api/v1/health` → 200 + `"status"` | процесс API жив |
| `/api/v1/health/ready` → 200 + `"database":"ok"` | API видит **БД** (иначе 503) |
| `/api/v1/auth/channels/` → 200 | роутер `api_v1` собран и отвечает |
| `/api/v1/users/search/?query=…` → 401 | защищённый эндпоинт не отдаёт данные без токена |
| контейнеры на сервере | все `Up`, ни одного `unhealthy` |
| свободное место на диске сервера | предупреждение при < 10% (порог `DISK_MIN_FREE_PERCENT`) |
| свежесть бэкапа в `~/Документы/pismo_backup/db` | предупреждение, если последний дамп старше 26 ч (значит, локальный cron бэкапа не работает) |

> ВАЖНО про пути: наружу nginx проксирует только `/api/` и `/media/`, а любой
> другой путь (в том числе корневой `/health`) отдаёт SPA-фолбэк — код 200 и
> HTML. Поэтому проверять надо проксируемые пути **и содержимое ответа**: иначе
> падение API выглядит как «всё в норме». (Так и было: первый вариант скрипта
> считал `/health` здоровым, пока API не отвечал.)

## Отчёты о падении приложения (свой «Sentry», 05.10.2026)

Редкую ошибку интерфейса иначе не разобрать: браузер показывает человеку экран
«500» (`FatalErrorScreen`), а в логах сервера её нет — запроса к серверу не было.
Владелец жаловался на такую ошибку при выборе аудиофайла в PWA; в логах nginx и
слота web при этом ни одного 5xx.

Внешний трекер (Sentry и подобные) в проекте не подходит: это передача данных за
границу и лишний скрипт в CSP `script-src 'self'` (см. `docs/rkn-notification.md`,
там же причина, по которой метрики тоже свои). Поэтому отчёт идёт на свой эндпоинт.

Как это работает:

| Шаг | Что происходит |
|---|---|
| 1 | `FatalErrorScreen` показан → `reportFatalError` зовёт `sendClientError` (`frontend/src/services/clientErrorReport.ts`) |
| 2 | `POST /api/v1/system/client-error/` (без входа можно) шлёт текст, стек, путь страницы и сборку `__BUILD_INFO__` |
| 3 | Бэкенд пишет строку в лог (`Ошибка на клиенте …`) и увеличивает `pismo_client_errors_total` |
| 4 | Владельцу уходит письмо с текстом ошибки (воркер `tasks.notifications.send_email`, адрес `ALERT_EMAIL`), не чаще раза в 5 мин |
| 5 | Правило `PismoClientError` в `monitoring/prometheus/rules/pismo.yml` — страховка: сработает, даже если SMTP/Celery лежат |

Что видно на сервере:

```bash
docker compose -p microshop-test -f docker-compose.prod.yaml logs web-green --since 24h | grep 'Ошибка на клиенте'
T=$(grep '^METRICS_TOKEN=' .env | cut -d= -f2-); curl -s -H "X-Metrics-Token: $T" \
  https://pismo.space/api/v1/system/metrics/ | grep client_errors
```

Границы: логи живут в json-file (2×5 МБ на контейнер) — редкий отчёт там может
быть вытеснен; письмо и счётчик — нет. В отчёте НЕТ текстов сообщений, ключей
E2EE и query-строки (там бывают id чата и параметры звонка): только путь.
Отчёт ограничен лимитом (10 в минуту на клиента) и исключён из заглушки техработ.

## Оповещения

Основной канал — **e-mail (SMTP)**: Telegram `api.telegram.org` недоступен ни с
прод-сервера, ни с локальной машины (блокировка в РФ-сетях, проверено), а SMS через
SMS Aero без договора с операторами отклоняются.

SMTP-настройки берутся автоматически: сначала из окружения, затем из локального
`.env`, затем из **продового** `.env` по ssh (поэтому достаточно настроить один раз —
см. `docs/email-smtp.md`). Если SMTP нигде не задан, скрипт пишет предупреждение в
лог и в вывод: «НЕТ КАНАЛА ОПОВЕЩЕНИЙ» — это значит, что о проблемах вы не узнаете.

SMS можно включить принудительно (`ALERT_SMS=1`, номер в `ALERT_PHONE`) — на случай,
когда SMTP недоступен, но помните про цену и требование договора.

Оповещаем **только об ошибках**. Повторные оповещения об одной и той же проблеме
приходят не чаще, чем раз в `ALERT_MIN_INTERVAL` минут (по умолчанию 180).

Письмо «прод снова в норме» по умолчанию **не отправляется** (успешные прогоны не
шлют ничего). Включить его можно явно: `ALERT_ON_RECOVERY=1` — тогда письмо придёт
один раз на инцидент (после устранения проблемы), а не на каждый успешный прогон.

> Состояние дедупликации в `logs/monitor.state`: первая строка — «отпечаток»
> активной проблемы, `ok` (всё в норме) или `test`. Восстановление определяется
> только по переходу «отпечаток проблемы → `ok`»; после сброса на `ok` письма
> больше не отправляются, поэтому «снова в норме» не может сыпаться каждые 15 минут.

## Метрики для Prometheus (свои, без внешних сервисов)

Кроме почтовых проверок приложение умеет отдавать метрики текстом —
`GET /api/v1/system/metrics/` (формат exposition 0.0.4, см. `backend/core/metrics.py`).
Своё, а не Sentry/облако: метрики не покидают наш сервер (см.
`docs/rkn-notification.md` про передачу данных за границу).

| Что отдаём | Метрика |
| --- | --- |
| Запросы по маршруту, методу и классу кода | `pismo_http_requests_total` |
| Время ответа (гистограмма, корзины 5 мс … 10 с) | `pismo_http_request_seconds` |
| Люди на связи и открытые сокеты (события и звонки) | `pismo_ws_users`, `pismo_ws_sockets` |
| Соединения в пуле БД (занято/свободно) | `pismo_db_pool_connections` |
| Время с запуска процесса | `pismo_process_uptime_seconds` |

Что важно знать:

- **Ключ серии — шаблон маршрута** (`/api/v1/messages/{chat_id}/`), а не реальный
  путь, и число серий ограничено (`MAX_SERIES = 200`, лишнее сворачивается в
  `other`): иначе перебор путей сканером раздул бы память процесса.
- **Эндпоинт закрыт токеном**: задайте `METRICS_TOKEN` в `.env` — без него
  эндпоинта как будто нет (404), с чужим токеном — 401. Метрики не публичные:
  они рассказывают про нагрузку и внутреннее устройство сервиса.
- Метрики работают и во **время технических работ** (исключены из заглушки) —
  именно тогда по ним и видно, что происходит.
- Счётчики живут в памяти процесса, а слотов `web` два (blue/green): Prometheus
  увидит два набора (по `instance`), поэтому на графиках берите `rate()`, а не
  абсолютные значения — переключение слота обнуляет счётчик.

Проверка вручную:

```bash
curl -s -H "X-Metrics-Token: $METRICS_TOKEN" \
  https://pismo.space/api/v1/system/metrics/ | head -20
```

Сбор и графики уже стоят в прод-стеке (сервисы `prometheus` и `grafana` в
`docker-compose.prod.yaml`) — настраивать ничего не нужно, см. следующий раздел.

## Графики: Prometheus + Grafana в стеке прода

| Что | Где | Как открыть |
| --- | --- | --- |
| Grafana, дашборд «Pismo · обзор» | порт **3000**, только `127.0.0.1` сервера | `ssh -L 3000:127.0.0.1:3000 -i ~/.ssh/id_rsa1 user1@176.108.249.9` → http://localhost:3000 |
| Prometheus (цели, ad-hoc запросы) | порт **9090**, тоже только `127.0.0.1` | тот же туннель с `-L 9090:127.0.0.1:9090` |
| Alertmanager (активные алерты, «молчание») | порт **9093**, тоже только `127.0.0.1` | тот же туннель с `-L 9093:127.0.0.1:9093` |

- **Логин** в Grafana — `admin`, пароль лежит в прод `.env`
  (`grep '^GRAFANA_ADMIN_PASSWORD=' ~/microshop/.env`). Наружу порты не открыты
  намеренно: слушают только localhost, доступ — SSH-туннель с твоего компьютера.
- **Что собирается**: `monitoring/prometheus/prometheus.yml` — цель одна,
  `frontend:443` (nginx внутри сети). Поэтому переключение слота `web-blue` /
  `web-green` при деплое цель не меняет, и вечно «мёртвых» целей в выдаче нет.
- **Дашборд и источник данных** описаны в репозитории
  (`monitoring/grafana/provisioning/`, `monitoring/grafana/dashboards/pismo.json`) и
  подхватываются при старте: после пересоздания контейнера ничего не теряется.
  Панели: запросы в секунду по классам кода, доля 5xx, медиана и p95 времени ответа,
  топ маршрутов, сокеты и пул БД, «съеденное» время по маршрутам, доступность цели.
- **Правка дашборда**: удобнее в интерфейсе (сохраняется в том `grafana_data`); чтобы
  закрепить в репозитории — выгрузить JSON и заменить файл
  `monitoring/grafana/dashboards/pismo.json`.
- **Хранение метрик** — 30 дней (`--storage.tsdb.retention.time=30d`) в томе
  `prometheus_data`, лимиты как у остальных сервисов (256 МБ Prometheus, 384 МБ Grafana).
- Переменная `METRICS_TOKEN` передаётся и в контейнер Prometheus, а сам контейнер
  подставляет её в конфиг при старте: в `prometheus.yml` стоит плейсхолдер
  `__METRICS_TOKEN__`, `entrypoint` делает `sed` в копию конфига (`/tmp/prometheus.yml`)
  и запускает её. Так секрет не попадает в командную строку процесса (`ps`), а в
  экспозиции метрик остаётся только `Authorization`.
  ГРАБЛЯ: флага `--config.expand-env` у Prometheus НЕТ (он принадлежит
  Alertmanager) — с ним контейнер падает в цикле перезапусков с «unknown long flag».

Чего пока НЕТ (сознательно, первый шаг): глубины очереди Celery и задержки задач
(нужен доступ к management API RabbitMQ), счётчиков отправленных push (они живут в
процессе воркера, а метрики снимаются с `web`) и трейсинга.

## Алерты: Prometheus + Alertmanager

Раньше метрики только рисовались на графиках: заметить проблему можно было, лишь
зайдя в Grafana, а о падении узнавал локальный cron (`check_prod.sh`, раз в 15
минут). Теперь у метрик есть пороги и доставка — независимо от того, включён ли
компьютер с cron.

- **Правила**: `monitoring/prometheus/rules/pismo.yml`, подключены через
  `rule_files` в `prometheus.yml`. Пять правил: API не скрейпится (`PismoApiDown`),
  сам Prometheus молчит, доля 5xx > 5%, p95 времени ответа > 1 c, пул БД занят
  > 90%. Активные алерты видны в Prometheus на `/alerts`.
- **Доставка**: сервис `alertmanager` (порт 9093, только localhost) шлёт письмо
  по SMTP — теми же переменными, что `scripts/monitoring/check_prod.sh`
  (`SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_FROM`, адрес
  получателя `ALERT_EMAIL`, по умолчанию `nyuskov@gmail.com`). Письмо «алерт
  закрылся» тоже отправляется.
- **Секретов в конфиге нет**: `monitoring/alertmanager/alertmanager.yml` — шаблон
  с плейсхолдерами `__SMTP_*__`, их подставляет entrypoint контейнера (как
  `__METRICS_TOKEN__` у Prometheus). Пароль со спецсимволами (`&`, `|`, `\`)
  обрабатывается: значения экранируются перед `sed`.
- Если SMTP не задан, контейнер поднимается и работает, но письма не уходят —
  алерты остаются видны в интерфейсе Prometheus. Это тот же принцип, что у
  cron-скрипта: «НЕТ КАНАЛА ОПОВЕЩЕНИЙ» — повод настроить почту, а не паника.

Проверить конфиги перед правкой (обе команды безопасны, ничего не запускают):

```bash
docker run --rm -v "$PWD/monitoring/prometheus:/etc/prometheus:ro" \
  --entrypoint /bin/promtool prom/prometheus:v3.15.0 check config /etc/prometheus/prometheus.yml
docker run --rm -v "$PWD/monitoring/alertmanager:/cfg:ro" \
  --entrypoint /bin/amtool prom/alertmanager:v0.28.1 check-config /cfg/alertmanager.yml
```

**Как применить правку конфига** — важно: деплой из CI запускает только `db`,
`rabbitmq`, `coturn`, `certbot`, слоты `web` и `frontend` (см.
`scripts/ci/deploy_remote.sh`), сервисы мониторинга он не пересоздаёт. После
изменения `prometheus.yml`, правил или `alertmanager.yml` подними их на сервере
руками:

```bash
cd ~/microshop
docker compose -p microshop-test -f docker-compose.prod.yaml up -d --no-build prometheus alertmanager
```

Первого запуска Alertmanager тоже касается: сервис новый, поэтому на проде его
нужно создать этой командой один раз.

## Чего мониторинг не покрывает

- Он сам запускается локально: если выключен компьютер, проверок нет. Отчасти это
  компенсируется проверкой свежести бэкапа (его тоже делает локальный cron).
- Не проверяет бизнес-логику (что регистрация/вход реально работают) — это делает
  смоук-тест после деплоя в CI: `scripts/ci/smoke_prod.sh`, job `smoke`
  в `.github/workflows/ci.yml`.
- `/api/v1/health/ready` проверяет только БД. Брокер (RabbitMQ) виден косвенно:
  он участвует в `docker healthcheck` сервисов `rabbitmq`/`web` и в проверке
  «нет контейнеров в состоянии `unhealthy`».
