# Улучшения и безопасность (2026-09-07)

### Окружение и секреты
- Секреты вынесены из кода/композа в корневой **`.env`** (в `.gitignore`); образец — `.env.example`. `docker compose` требует `POSTGRES_PASSWORD` и `JWT_SECRET_KEY`, при отсутствии файла `.env` останавливается с понятной ошибкой.
- `backend/core/config.py`: `JWT_SECRET_KEY` читается из окружения; если не задан — в лог пишется предупреждение (используется только dev-запасной ключ).
- **Требует действий:** смените `JWT_SECRET_KEY`/пароль БД, если значения попадали в публичный git (ротация + пересоздание volume). Старый файл `.env.dev` удалён из индекса.

### Аутентификация (OTP)
- OTP-коды теперь хранятся в **БД** (`otp_codes`, хеш + счётчик попыток), а не в памяти — переживают рестарт и работают при нескольких воркерах.
- Защита от перебора: лимит неверных попыток (`AUTH_OTP_MAX_ATTEMPTS`, по умолч. 5), кулдаун повторной отправки (`AUTH_OTP_RESEND_COOLDOWN_SECONDS`, 30 с, HTTP 429 + `Retry-After`).
- Удалены отладочные эндпоинты `/auth/basic-auth*`.
- Доп. защита (2026-09-08): часовой лимит запросов кода на номер (`AUTH_OTP_REQUEST_PER_PHONE_PER_HOUR`, 10) и блокировка номера после перебора (`AUTH_OTP_VERIFY_LOCKOUT_SECONDS`, 120 с, HTTP 429).

### Загрузка файлов
- Вложения и аватары проверяются: расширение из белого списка + сигнатура (magic bytes) для изображений. HTML/SVG/JS/XML и неизвестные типы отклоняются (защита от stored-XSS через `/media/...`).
- Импорт GIF: запрещены HTTP-редиректы (защита от SSRF), проверяется host, порт/userinfo и что ответ действительно GIF.
- **Квота на медиа** (`core/media_quota.py`, `MEDIA_QUOTA_BYTES`, по умолчанию 500 МБ):
  ограничивает накопление файлов у одного пользователя — размер одного файла был
  ограничен и раньше (15 МБ), а суммарный объём нет. Считаются только файлы,
  загруженные самим пользователем: пересылка переиспользует тот же файл на диске
  (`file_url` копируется), поэтому второй раз в квоту он не попадает. Аватар (один
  файл до 8 МБ) в квоту не входит.
- Превышение → `413` с цифрами («Хранилище заполнено: занято 250.0 МБ из 500.0 МБ»),
  проверка идёт **до** записи файла на диск (и в воркере для GIF). Место
  освобождается сразу после удаления сообщения, потому что квота считается по БД;
  осиротевшие файлы убирает ночная задача `cleanup_orphan_media`.
- `GET /api/v1/users/me/storage/` → `{used_bytes, quota_bytes, files, percent}` —
  профиль показывает индикатор заполненности (и предупреждает заранее при ≥90%).
  Квота `0` выключает ограничение (аварийный режим).

### Присутствие и БД
- `last_seen` больше не обновляется в `get_current_user` (не было лишних commit на каждый read-only запрос); теперь присутствие обновляется в poll-эндпоинте `GET /chats/`.
- При удалении сообщения его файл удаляется с диска (best-effort).
- `GET /messages/{chat_id}/media/` — вложения чата для галереи «Медиа/Файлы»:
  `kind=image|video|audio|file` и `before_id` листают вложения без выгрузки
  истории (по умолчанию **60**). В зашифрованном чате возвращается пустой
  список: содержимое зашифровано ключом чата, галерея строится из расшифрованной
  ленты (сервер не может показать картинку и определить тип).
- `GET /messages/{chat_id}/` всегда отдаёт страницу: по умолчанию последние **100** (`DEFAULT_MESSAGE_PAGE_SIZE`); `?limit=`/`?before_id=` — пагинация «вверх». Добавлен индекс `(chat_id, timestamp)`.

- **Логирование**: SMS-заглушка пишет через `logging` вместо `print`.
- **Зависимости**: `python-jose` удалён; `PyJWT` добавлен явно (именно его использует `import jwt`). Обновился `poetry.lock` (убраны rsa/pyasn1/six).

### Итерация (2026-09-12): аватары-миниатюры, галерея медиа, скорость голосовых, бейдж

- **Аватары**: сервер рядом с оригиналом кладёт миниатюру 128px
  (`core/avatar_store.py`, Pillow) и отдаёт `avatar_thumb_url`; клиент перед
  загрузкой сжимает фото до 512px (`optimizeAvatarFile`); интерфейс берёт
  миниатюру (`avatarUrlOf`/`groupAvatarUrl`), оригинал — только для крупного
  показа (`avatarFullUrlOf`). На кружок в списке чатов уходит миниатюра
  вместо оригинала: на реальных аватарах прод-сервера 58–60 КБ → 2–5 КБ, на
  лабораторном снимке 3000×2000 — 1.2 МБ → 1–2 КБ (замеры — в
  `docs/feed-performance.md`). Для уже загруженных
  аватаров миниатюры досоздаёт `python -m scripts.make_avatar_thumbs --apply`.
- **Галерея медиа**: `GET /messages/{chat_id}/media/` отдаёт вложения всей истории
  чата (фильтр `kind=image|video|audio|file`, пагинация `before_id`), а не только
  загруженные ~100 сообщений; в «Информации о чате» появилась кнопка «Показать
  ещё», а картинка вне загруженной ленты подгружает свою страницу и открывается в
  лайтбоксе. В зашифрованном чате список пуст (галерея — из расшифрованной ленты).
- **Скорость голосовых и видеосообщений**: кнопка `1×/1.5×/2×`
  (`utils/playbackSpeed.ts`), выбор общий для всех сообщений.
- **Бейдж приложения**: число непрочитанных ставится на иконку установленного PWA
  (`utils/appBadge.ts`); при push в закрытое приложение service worker ставит
  «точку».
- **«Ответить» из уведомления**: кнопка в системном уведомлении открывает чат
  с уже сфокусированным полем ввода (печатать текст прямо в уведомлении веб-
  приложению нельзя — такого API нет, поэтому «быстрый ответ» это чат, готовый
  к вводу; `?reply=1`, `isReplyLaunch`).
- **Мелочи**: убраны мёртвый CSS `.gif-btn` (вес 800 в шрифте, которого нет) и
  неиспользуемые импорты; предзагрузка иконочных шрифтов в `index.html`; скрипты
  очистки медиа (`cleanup_orphan_media`, `tasks/media_tasks`) больше не считают
  «сиротами» миниатюры аватаров и аватары групп (раньше удалили бы их как
  неиспользуемые).

### Итерация (2026-09-12, вторая): ссылки-приглашения в группы и починка звонка из push

- **Ссылки-приглашения в группы**: создатель или админ делает ссылку в карточке
  группы (`/chats/{id}/invites/`), отправляет её другу; тот открывает
  `https://<домен>/j/<токен>`, видит карточку группы (название, аватар, число
  участников) и вступает. Ссылку можно ограничить по сроку (`expires_in_hours`) и
  числу входов (`max_uses`) и отозвать. Повторный вход тем же человеком ничего не
  ломает и лимит не тратит; создатель, вернувшийся по ссылке, снова получает роль
  создателя. В зашифрованную группу вход по ссылке закрыт: ключ группы выдаёт
  участник, а не сервер (409 с понятным текстом).
- **Звонок из push**: кнопка «Ответить» больше не выглядит как отказ.
  * неудачная попытка принять (`reason: failed`) и «занят» (`busy`) больше не
    записываются в историю как «отклонён» — это пропущенный звонок;
  * отказ по кнопке уведомления теперь попадает в историю (раньше проходил мимо
    неё: зовущий видел «отклонил», а записи о звонке не было);
  * на экране ожидания звонка (приложение открыто кнопкой «Ответить», offer ещё в
    пути) есть обе кнопки — «Ответить» и «Отклонить», а не одна красная;
  * действие из уведомления не теряется, если offer уже пришёл.
- **Мелочи**: если чат удалили или вас исключили из группы, а он был открыт,
  приложение убирает его из списка и возвращает к чатам (раньше фоновое обновление
  бесконечно писало «Не удалось обновить сообщения»); карточка приглашения грузится
  отдельным чанком, поэтому основной бандл остался в бюджете размера.

### Итерация (2026-09-15): файлы перетаскиванием в любое место окна и вставкой из буфера

- **Перетаскивание**: файл можно бросить в любое место окна — на ленту
  сообщений, список чатов, шапку. Слушатели живут на `window`
  (`composables/useFileDrop.ts`), подсказка одна на всё приложение
  (`components/messenger/FileDropOverlay.vue`): затемнение + карточка с пунктиром
  «Отпустите файл, чтобы отправить» и пометкой «Можно перетащить несколько файлов
  сразу». Без открытого чата подсказка меняется на «Откройте чат, чтобы отправить
  файл», и сам бросок показывает уведомление.
- **ПОЧЕМУ окно, а не зона у композера** (первый заход, до коммита, был именно
  таким): `dragover`/`drop` в браузере — это навигация, поэтому бросок мимо зоны
  **открывал файл вместо чата**, то есть терял приложение вместе с неотправленным
  сообщением. Гасить события надо на всём окне, а раз цель одна — и подсветка
  одна: два индикатора (у полосы ввода и оверлеем) спорили между собой, а
  оставшийся в композере обработчик продублировал бы отправку.
- **Несколько файлов за раз**: уходят по очереди, каждый — отдельным сообщением
  (альбомов в модели сообщений нет). Подпись из поля ввода достаётся первому —
  после него поле очищается, как при отправке одного файла. Один неудачный файл не
  отменяет остальные: композер показывает «Не удалось отправить N из M файлов»,
  одиночный — свою причину.
- Отправка идёт тем же путём, что и кнопка «Прикрепить», поэтому сжатие фото,
  квота и E2EE-конверт работают без отдельной ветки кода.
- **Вставка картинки из буфера**: Ctrl+V с картинкой в поле ввода отправляет её
  вложением; обычный текст по-прежнему вставляется как текст.
- Тесты: `useFileDrop.spec.ts` (9 — включая «гасит поведение браузера»),
  `fileDropOverlay.spec.ts` (4), `composerPaste.spec.ts` (3). Проверено в браузере
  (headless Chrome + CDP): бросок двух файлов над лентой отправил два сообщения,
  события погашены, обе подсказки на месте (тестовые сообщения удалены).
- Бюджет размера бандла обновлён (`frontend/scripts/bundle-size-baseline.json`):
  от HEAD основной чанк вырос на 934 Б gzip (весь новый код перетаскивания) плюс
  475 Б CSS, а сама база к тому же отставала от HEAD на 2,7 % — без обновления
  проверка падала бы.

### Итерация (2026-09-15): видеосообщение получило свою иконку — «кружок в квадрате»

- **Было**: и видеозвонок, и видеосообщение («кружок») рисовались одним глифом —

  без этого падала бы на «нет в Lucide».
- Сетка и штрих нового глифа как у Lucide (поле 24, фигура 18, штрих 2): рядом с
  соседними иконками он не выглядит ни жирнее, ни крупнее.
- Шрифт иконок не пересобирали: рисованный глиф в него не попадает, а пересборка
  тянет свежую версию Lucide — поехали бы глифы всех остальных иконок. В
  `icons.css` обновилась только шапка (там было старое имя скрипта сборки и не

- Глиф стоит в композере (переключатель режима записи), в заголовке

- Тесты: `icons.spec.ts` (разные глифы у `videocam` и `video_message` + форма
  глифа разбирается из маски), `media.spec.ts` (иконка видео ≠ иконка видеозвонка).

### Итерация (2026-09-15): кнопка записи в композере стала акцентной

- **Было**: кнопка записи (микрофон / кружок-видео) была серой, как служебные
  «прикрепить» и «эмодзи» рядом.

  в `appearance.css`) и он же красит иконку в `--ms-text`. У слоя специфичность

  через `:global(html .messenger-shell .mic-hold-btn:hover)` — тот же приём, что в
  `StoriesStrip.vue` для фокуса.
- Заодно порядок состояний: `.mic-hold-btn.holding` объявлен ПОСЛЕ `.mode-video`,
  поэтому во время записи кружка кнопка заливается акцентом (раньше в режиме видео
  оставалась бледная подложка, хотя запись уже шла).

### Итерация (2026-09-15): согласие при регистрации, админская «шестерёнка», приглашения из приложения

**Согласие с документами сервиса (регистрация).**
- Раньше под кнопкой была только строка «Продолжая, вы соглашаетесь…» — явного
  действия не требовалось. Теперь при регистрации нужна **галка**
  (`components/common/ConsentCheckbox.vue`): она обязательна на шаге подтверждения
  кода для НОВОГО номера (там сервер и создаёт аккаунт, `/auth/verify-otp/`) и на
  шаге создания пароля для нового номера, а также на регистрации по приглашению.
  При обычном входе и при «задать пароль» существующему аккаунту галки нет —

- `core/media_crypto.py`: формат `encf:v1:` — заголовок (magic 8 Б + размер

- Раздачу медиа забрали у `StaticFiles`: расшифровать файл умеет только код,

  `HEAD`, `ETag`/`304`, отдаёт ответ потоком. Типы html/svg/xml отдаются как
  `application/octet-stream`, имя из URL проверяется (`..`, абсолютный путь,

### Итерация (2026-09-17): связь — плашка сверху и догрузка данных

- Жалоба: «нет подключения к интернету» не пропадает, когда связь вернулась, и
  приложение не пытается повторить запросы. Причина: плашка жила только на

  уже после восстановления.

### Итерация (2026-09-17): realtime между процессами web (B6, этап 1)

- Повод: сокеты живут в памяти конкретного процесса `web`. Пока процесс один —
  незаметно, а при двух (деплой «синий/зелёный») звонки между людьми на разных

- Мост RabbitMQ теперь работает в обе стороны: любой процесс публикует событие в
  fanout-обмен, каждый процесс читает свою очередь и раздаёт событие своим

- Дубли исключены меткой процесса (`origin`): своё же событие из fanout
  отбрасывается — иначе звонок получил бы два `call-answer`. Повторная доставка
  (at-least-once) отсекается по `event_id`.
- Для сигналинга добавлено подтверждение доставки: отправитель просит `ack` и
  ждёт его (`wait_for_delivery`). Без этого нельзя понять, абонент офлайн или
  просто «в другом процессе», и вызов парковался бы зря. Теперь зовущий паркует
  вызов только когда сигнал не доставлен ни в один сокет.
- Единая точка отправки — `api_v1/events/service.dispatch_realtime` (локально +
  мост): через неё идут сообщения, прочтение, `chat.read-self`, presence,
  «печатает…», события каналов и историй. Канал публикации переиспользуется,
  публикация ограничена таймаутом (0,5 с) и предохранителем (5 с тишины после
  двойной неудачи) — недоступный брокер не задерживает HTTP-запросы и не заливает
  логи одинаковыми ошибками.
- Осознанно не сделано (этап 2): парковка офлайн-вызова, недоставленный сигналинг
  и состояние присутствия остаются в памяти процесса-отправителя. Поэтому
  перекрытие слотов остаётся коротким (~2 с, DNS nginx) — это описано в

- Тесты: `backend/tests/test_realtime_bridge.py` — 9 (origin и `event_id`,

### Итерация (2026-09-17): качество звонка на плохой сети (междугородние звонки)

- Замечание: «Москва — Россошь: плохо слышно, сигнал плохой». Причина не только в
  канале: до этого в сообщении `ice-candidate` не уходил кандидат (см. выше
  регрессию), и медиа поднималось только перезапуском ICE по сторожу — то есть
  разговор начинался «через релей и с потерями». Теперь связь устанавливается
  сразу, а качество подстраивается под сеть (`stores/call/quality.ts`).
- **Звук вперёд.** В описании (SDP) включаются помехоустойчивые параметры Opus:
  `useinbandfec=1` (потери до ~20 % восстанавливаются из избыточности, без
  переспроса и задержки), `usedtx=1` (в тишине пакеты не шлются — полоса
  освобождается для собеседника), `stereo=0` и `maxaveragebitrate=40000`
  (голос — моно), `minptime=10` (короче хвост задержки при дрожании). Настройки
  идут и в offer, и в answer — параметры пишутся в `fmtp`, другого API у Opus нет
  (`tuneOpusSdp`, `tunedDescription`).
- **Приоритет звука.** У микрофона `maxBitrate` 64 кбит/с (40 кбит/с голос плюс
  запас на FEC) и `priority: high`, у видео — `low`: при перегрузке канала
  браузер режет видео, а не разговор.
- **Адаптивный битрейт видео.** Раньше он был прибит к 300 кбит/с всегда. Теперь
  подбирается по статистике связи: 700 кбит/с на хорошей, 350 — при потерях от
  2 %, дрожании от 45 мс или задержке от 400 мс, 140 — при потерях от 8 % или
  дрожании от 90 мс. Ступень меняется только при изменении, а не на каждом
  опросе. При нехватке полосы качество падает по разрешению, а не по частоте
  кадров (`degradationPreference: maintain-framerate`) — картинка не «замирает».
- **Подсказки кодеку** (`contentHint`): микрофон — «речь», камера — «движение»,
  показ экрана — «текст» (для экрана ещё и `maintain-resolution`: мелкий текст
  должен остаться читаемым).
- Проверено живьём в настоящем Chrome (два аккаунта, фейковая камера): в
  согласованном описании — `maxaveragebitrate=40000;minptime=10;stereo=0;usedtx=1;useinbandfec=1`,

### Итерация (2026-09-17): чистый звук (как просили — «как в телеграм») и связи между участниками группы

Замечания: «качество звука с искажениями» и «не в групповом тоже». Причин
оказалось три, и все настоящие.

- **Искажения от DTX.** В прошлой итерации в Opus был включён `usedtx=1`
  (экономия тишины) и `minptime=10`. DTX на стыках фраз даёт щелчки и
  «бульканье» — это и слышно как искажения. Убрано: остаётся только
  `useinbandfec=1` (потери до ~20 % восстанавливаются избыточностью), моно
  (`stereo=0;sprop-stereo=0` идут парой), 48 кбит/с вместо 40 и штатные 20 мс
  пакетирования. Предел полосы микрофона — 72 кбит/с (48 голос + запас на FEC).
- **Речь звучала дважды.** В групповом звонке звук идёт через Web Audio, но
  элементы плиток не глушились (в одиночном звонке — глушились): одна и та же
  речь играла из элемента и из Web Audio с небольшой задержкой. Голос
  «расплывался» — тоже воспринимается как искажения. Теперь плитки глушатся
  ровно тогда, когда звук играет Web Audio (иначе — фолбэк, чтобы не было тишины).
- **Слышно было только одного собеседника.** Модуль вывода держал ОДИН источник:
  каждый новый поток заменял прежний. Теперь источники собираются в список —
  слышны все, а ушедший участник вынимается из микшера. Громкость меняется
  плавно (30 мс): мгновенная смена слышна как щелчок в динамике.
- **Главное: в группе из трёх «средние» участники не соединялись друг с другом.**
  Правило «младший по id инициирует» ломается о то, что первый offer уходит,
  пока человек ещё звонит: он отбрасывает его как «тот же звонок». Ветка
  присоединения к идущему разговору стояла ПОСЛЕ этой проверки и была
  недостижима, поэтому offer пропадал навсегда — слышал только зовущий.
  Исправлено: (1) сервер рассылает состав звонка после `call-answer`, (2) клиент
  повторяет неотвеченный offer (не чаще 4 с, до 6 раз) и добавляет дорожки только
  при первом заходе, (3) присоединение проверяется ДО «этот же звонок», (4) свой
  зависший offer не мешает принять чужой — связь начинается заново.
- Захват звука задан явно: эхоподавление, шумодав, автоматический уровень, моно.
- Проверено живьём (три аккаунта, настоящий Chrome): у каждого участника 2 связи
  и 2 источника звука, видно и слышно всех; в одиночном звонке звук идёт одним
  путём (элемент заглушён).
- Тесты: `callQuality.spec.ts` — 15, `groupCall.spec.ts` — 43. Всего: фронтенд
  1151, бэкенд 530.

### Итерация (2026-09-18): качество звука и видео — ступени вместо «одной полки»

Разбор предложений по качеству звонков и реализация всего, что не требует смены
архитектуры (SFU/нативный WebRTC — отдельный шаг, см. ниже).

- **Звук сужается на потерях.** Быт фиксированный потолок 72 кбит/с у
  передатчика, теперь ступени 48 / 32 / 24 кбит/с по статистике связи
  (`audioBitrateFor`): крупные пакеты теряются чаще мелких, поэтому на плохом
  канале разборчивее узкий поток. Меняется через `setParameters`, без
  пересогласования. В `fmtp` Opus добавлен явный `minptime=20` — чтобы
  собеседник со старым клиентом (`minptime=10`) не мельчил пакеты. `usedtx` так
  и не включаем: был откат из-за щелчков.
- **Захват звука:** 48 кГц (родная частота Opus — без ресемплинга), `latency:
  0.01` (задержка захвата складывается с задержкой буфера) и `voiceIsolation`
  (Chrome 116+: голос в шуме чище; незнакомые констрейнты браузеры игнорируют,
  поэтому Safari это не ломает).
- **Режим обработки микрофона** — «Чистый голос» (шумодав) / «Естественный»:
  на части телефонов шумодав делает голос «роботом», теперь это выбор человека
  в панели устройств. Смена режима — новый `getUserMedia` (констрейнты задаются
  только при захвате); старая дорожка гасится ТОЛЬКО после успешной замены, иначе
  неудачная смена оставляла звонок без звука вообще.
- **Видео уступает по трём осям, а не только битрейтом.** К ступеням битрейта
  (700/350/140 кбит/с) добавились разрешение (`scaleResolutionDownBy` 1/1,5/2 —
  640×480 → 480×360 → 320×240) и частота кадров (30/24/15): 140 кбит/с на полном
  кадре — это «мыло» и артефакты, на уменьшенном та же полоса даёт чистую картинку.
- **Показ экрана выведен из-под ступеней сети:** 1,2 Мбит/с, 15 к/с,
  `maintain-resolution`, разрешение не режется. Раньше `_adaptVideoBitrate` на
  показе экрана просто выходил, а битрейт брался из «камерной» ступени — если сеть
  перед этим уронила видео до 140 кбит/с, текст на экране становился нечитаемым.
- **Адаптация — по каждой связи.** В группе качество у собеседников разное,
  а `_adaptVideoBitrate` смотрел статистику только «основной» связи: одному шлём
  700 кбит/с, другому надо 140. Теперь `_tuneLinksByStats` снимает `getStats()`
  по каждой связи, кладёт её ступени в `runtime.linkQuality` и применяет к её
  передатчикам.
- **Авто-пауза видео при долгой плохой связи.** Потери 8 %+, дрожание 90 мс+ или
  RTT 600 мс+ три опроса подряд (≈15 с) — видео снимается у всех связей
  (`replaceTrack(null)`), собеседник видит аватар, звук остаётся. Возврат — после
  пяти хороших опросов (≈25 с) или сразу решением человека (пункт «Вернуть видео»
  в меню «Ещё», кнопка камеры). Передатчики запоминаются отдельно
  (`runtime.pausedVideoSenders`): после `replaceTrack(null)` найти их по дорожке
  нельзя, а связь, появившаяся во время паузы, приостанавливается сразу.
- **Буфер воспроизведения** (`jitterBufferTarget`, в старых браузерах
  `playoutDelayHint`): 50–140 мс для звука и 200–700 мс для видео — по дрожанию
  сети. Браузерный буфер по умолчанию берётся «с запасом», и разговор идёт с
  ощутимой задержкой (люди перебивают друг друга); маленький буфер без запаса
  рвёт звук, поэтому цель растёт вместе с дрожанием.
- **«План Б» по камере вместо отказа от звонка.** `acquireLocalMedia` пробует
  640×480@24 → 480×360@20 → 320×240@15 → и только потом звонок БЕЗ видео
  (`_applyAcquiredKind` переводит интерфейс в голосовой режим). Раньше
  `OverconstrainedError` на дешёвом Android заканчивался «не удалось получить
  доступ» и отказом, хотя разговаривать было можно. Запрет доступа и «камера
  занята» формат не перебирают: лишние диалоги без пользы. Устройство из настроек
  требуем только в первой попытке — выдернутую внешнюю камеру заменяем любой
  другой. В группе захват сразу меньше (480×360@20): поток уходит каждому.
- **Диагностика стала честнее:** читаем `remote-inbound-rtp` (потери НАШЕГО
  потока у собеседника — на мобильной сети страдает именно отправка),
  `qualityLimitationReason` («ограничивает: полоса/процессор»),
  `availableOutgoingBitrate`, `jitterBufferDelay`, `framesDropped`, `freezeCount`,
  `nackCount`. Индикатор «плохая связь» учитывает и аплинк. В панели — новые
  строки, в ступенях — опора на доступную полосу, а не только на потери.
- **ICE:** явные `bundlePolicy: 'max-bundle'`, `rtcpMuxPolicy: 'require'`,
  пул кандидатов 2 → 4. TURN по TLS/TCP уже включён на сервере (5349 открыт в
  облаке) — правок не потребовал.
- **Гистерезис ступеней.** Ухудшение применяется сразу (звук важнее красоты), а
  улучшение — только выждав 15 с (`QUALITY_STEP_COOLDOWN_MS`): пороги близки, и на
  границе ступень «дышала» бы каждый опрос — картинка то расширяется, то
  ужимается. Действующая ступень хранится по каждой связи (`runtime.linkSteps`),
  а таблицы «ступень → битрейт/разрешение/кадры» живут в одном месте
  (`senderTuningForStep`, `initialSenderTuning`).
- **Кто говорит.** Читаем `audioLevel` из `inbound-rtp` (по каждой связи),
  превращаем в флаг с двумя порогами (`speakingNow`: 0.01 на включение, 0.004 на
  выключение — иначе кольцо мигает на паузах между словами) и подсвечиваем
  плитку участника в сетке: `outline`, а не `border` — рамка двигала бы соседние
  плитки при каждом слове.
- **Групповая диагностика.** В группе качество снималось по каждой связи, но
  нигде не было видно: в панели диагностики теперь СТРОКА НА КАЖДОГО участника
  (`peerQualityLine`: задержка, потери приёма, потери НАШЕГО потока на его стороне,
  ступень) — панель отвечает на вопрос «кто именно меня не слышит», — и эти же
  строки попадают в копируемый отчёт для поддержки. Реактивная копия статистики
  живёт в `peerDiagnostics` (в `runtime` она неподконтрольна Vue) и чистится при
  выходе участника.
- **Бейдж «Плохая связь» в группе — по худшей связи** (`worstQuality`): показывать
  «всё хорошо», когда один собеседник нас не слышит, значит врать.
- **Пауза видео — по большинству связей** (`shouldPauseForQuality`): плохая связь
  с одним участником (он в метро, у него 2G) больше не гасит картинку
  остальным — каждому мы отправляем своим потоком, ступени у связей свои, и
  хорошие связи продолжают получать видео. Гасим, только когда плохо больше
  половины связей — это уже похоже на нашу собственную сеть. В 1:1 поведение
  прежнее.
- **Живая проверка в настоящем Chrome** (headless с фейковой камерой, модули
  `stores/call/*` выполнены в странице через Vite). Подтвердилось: констрейнты
  захвата принимаются (48 кГц, 1 канал, `latency 0.01`, эхоподавление и шумодав,
  `voiceIsolation` — как запрос: в `getSettings` он отдаётся `false`, если
  устройство его не умеет) ; политики ICE — `max-bundle/require/4`;
  согласование с мунжем Opus РАБОТАЕТ (в итоговом SDP обоих участников
  `minptime=20;useinbandfec=1;stereo=0;sprop-stereo=0;maxaveragebitrate=48000`,
  состояние `connected`); `setParameters` принимает и возвращает ступени
  (бедная: звук 24 кбит/с + `priority high`, видео 140 кбит/с + `scale 2` +
  15 к/с + `maintain-framerate`; хорошая: 48 кбит/с и 700 кбит/с + `scale 1` +
  30 к/с; экран: 1,2 Мбит/с + `scale 1` + `maintain-resolution`);
  `jitterBufferTarget`/`playoutDelayHint` поддерживаются (запросили 80/290 мс —
  измеренная задержка буфера ≈269 мс); `availableOutgoingBitrate` приходит
  (300…2500 кбит/с в loopback). Не удалось проверить живьём только порог
  «говорит»: у фейкового микрофона Chrome `audioLevel` = 0 (нужен реальный
  микрофон на телефоне).
- **Найдено живьём и исправлено: кодеки.** У `inbound-rtp`/`outbound-rtp` в
  текущем Chrome поля `mimeType` больше нет — есть `kind` и ссылка `codecId` на
  отдельную запись `codec`, поэтому в панели диагностики вместо кодеков стояло
  «—». Теперь имя берётся через `codecId` (с фолбэком на старое поле).
- **Звук и уровень речи идут только через привязанный элемент.** Живая проверка
  нашла два связанных дефекта. Chrome отдаёт поток в Web Audio (и считает
  `audioLevel`) ТОЛЬКО когда поток привязан к медиаэлементу: без элемента
  звук не доходит вовсе, а с заглушённым элементом Chrome `audioLevel` = 0
  (тон 0,5: элемент — 0,503, Web Audio — 0).
  - В сетке плитка с выключенной камерой (и любая плитка аудио-группы) элемента
    не имела: теперь `<video>` есть у каждой плитки всегда, а без картинки он
    просто невидим (`grid-video-hidden`) и аватар лёг поверх него.
  - В одиночном звонке было два элемента (`<video>` и `<audio>`) и `v-if` по
    состоянию камеры: остался ОДИН `<video>`, всегда в разметке
    (`remote-hidden` вместо удаления). Отдельного `<audio>` больше нет — это
    заодно исключает два пути вывода для одного потока.
- **Уровень речи измеряем сами** (`output.ts`: `AnalyserNode` перед громкостью,
  `remoteLevels()`, `rmsLevel`): Chrome `audioLevel` для нашей схемы вывода
  не работает, поэтому кольцо «говорит» считается по своему RMS, а статистика
  служит фолбэком, когда звук играет элемент. Живьём: тон 0,5 → наш уровень
  0,355 (RMS сходится), тишина 0,0003 → «не говорит», пороги 0,01/0,004 верны.
  Опрос — раз в 400 мс (`SPEAKING_POLL_INTERVAL_MS`), перерисовка только при
  смене признака.
- **Иконка `videocam_off`** (бейдж «Видео приостановлено») — прогнаны
  `scripts/build_icons.py` и `scripts/build-icons-font.py`; попутно

- **Побочно:** тест `callHistory.spec.ts` больше не «протухает» на следующий день

# Стикеры и эмодзи-паки: бэкенд (2026-09-18)

### Свои стикеры (библиотека, а не сообщение)

- Новые таблицы `sticker_packs` и `stickers` (миграция
  `2026_09_18_1200-c1d2e3f4a5b9`). Стикер — элемент библиотеки: человек собирает
  паки один раз, а отправляет картинку сколько угодно раз, и на диске файл при
  этом один. Поэтому отдельные таблицы, а не «вложение в сообщении».

  добирает ночная уборка сирот (`scripts/cleanup_orphan_media.py` теперь знает и
  про `stickers.file_url`).
- Приведение картинки к виду — `core/sticker_store.py`: PNG/WebP пересобираются
  в WebP (сначала lossless, если не влезает — lossy), сторона обрезается до
  512 px, лимит 512 КБ. **GIF отдаём как есть**: пересборка сломала бы анимацию,
  поэтому большой GIF честно отклоняется, а не «пережимается».
- Лимиты: 12 паков, 120 стикеров в паке, общий rate limit загрузок (тот же, что
  у вложений) и общая квота на медиа. **Грабли:** в квоте стикер считался как

- `POST /messages/attachment/` получил `sticker=true`: сообщение уходит с

- `POST /stickers/from-message/` копирует картинку из сообщения в пак (пак по
  умолчанию создаётся сам, чтобы жест работал до всякой настройки).
- Работает только там, где сервер может прочитать файл: в E2EE-чате вложение —
  шифротекст, поэтому оттуда стикер делает клиент (загружает уже расшифрованные
  байты обычной загрузкой), а сервер отвечает `400` с объяснением. Это честнее,
  чем «ничего не произошло».
- Постороннему чужое сообщение не отдаём (`404`) — иначе так можно было бы
  вытащить картинку из закрытого чата.

### Паки эмодзи и «Мои» — на аккаунт

- `GET/PUT /users/me/emoji/` (`emoji_pack_choices`, `emoji_favorites`): выбор

### Найденные и исправленные дефекты

- **`-> None` у 204-эндпоинта = 500 при старте.** FastAPI берёт аннотацию
  возврата как модель ответа, а `NoneType` — «не None», поэтому `DELETE` падал
  на `Status code 204 must not have a response body` прямо при импорте роутера.
  Теперь такие ручки возвращают `Response(status_code=204)`, как в
  `users/views.py`.
- **Ответ с паком падал на `MissingGreenlet`.** `StickerPackOut` содержит
  стикеры, а ленивая загрузка в async-сессии невозможна: `POST/PATCH

  `selectinload` (а ручки загрузки просят `with_stickers=false`, чтобы не тянуть
  список зря), и обновлённый пак освежается вместе с содержимым.
- **Дублирующийся id ревизии.** Миграция приехала с id, который уже был занят
  миграцией привязки Telegram: alembic падал с «Cycle is detected in revisions»
  и «Revision ... is present more than once» — то есть `alembic upgrade head` не
  работал вообще. Id заменён на свободный `c1d2e3f4a5b9` (проверено `grep`).

# Расписание celery beat: ненужную задачу убрали (2026-09-18)

### Что за задача и почему она мешала

- `tasks.telegram.telegram_poll_updates` — long polling обычного Telegram-бота:
  ловит `/start bind_<код>` и привязывает чат к аккаунту (резервный канал
  доставки OTP). Задачу ставил celery beat каждые 5 секунд
  (`TELEGRAM_POLL_INTERVAL_SECONDS`).
- **Пользы от неё не было:** до `api.telegram.org` с прод-сервера маршрута нет
  (сетевая блокировка), поэтому бот не получал ничего, задача мгновенно
  выходила — а в логе воркера появлялась строка
  `succeeded in 0.0001751s: None` каждые несколько секунд. В dev это то же самое:
  если бот-токен задан, а сети до Telegram нет, остаётся бэккофф и пустые тики.

### Что сделано

- Расписание beat теперь собирается функцией `build_beat_schedule(settings)`:
  статические задачи (уборка media, историй, сигналинга, журнала безопасности)
  объявлены в ней, а `telegram-poll-updates` попадает в расписание только если
  есть и токен бота, и разрешение на опрос. Так «выключено» означает, что задачи
  нет вовсе, а не что она мгновенно выходит.
- Новая настройка `TELEGRAM_POLL_ENABLED` (по умолчанию `true` — поведение для
  тех, у кого Telegram доступен). `false` убирает задачу из расписания.
  Токен бота стирать не нужно: он нужен доставке кода в уже привязанный чат.
- Переменная добавлена в `.env.example`, `docker-compose.yaml`,
  `docker-compose.dev.yaml` (beat) и `docker-compose.prod.yaml` (beat); в нашем
  `.env` выставлено `TELEGRAM_POLL_ENABLED=false`.
- `tests/test_celery_schedule.py` (5 тестов): задача есть при включённом опросе
  с токеном (и с нужным интервалом), и её нет при `false` или пустом токене;
  статические задачи на месте в любом случае.
- Документация: раздел «Периодические задачи (celery beat)» в `docs/backend.md`
  с таблицей расписания и инструкцией выключения.

Как применить: `docker compose up -d beat` (воркеру правки не нужны).

### Панель эмодзи и стикеров — как в Telegram

- Сверху **лента значков**: категории эмодзи (или паки стикеров), ниже —
  **содержимое столбиком** секциями («Недавние», наборы, категории). Тап по
  значку прокручивает к секции, прокрутка подсвечивает секцию, которая сейчас на
  экране. Первая попытка была только вкладками (одна категория на экран), вторая
  — только столбиком (без ориентира, где что лежит); правильная форма — обе
  части вместе, как в Telegram.
- Подсветка не мигает при переходе: плавная прокрутка «пролистывает» промежуточные
  категории, поэтому после тапа пересчёт по экрану на 600 мс выключается, а
  активный значок сразу ставится выбранным и держится на виду в ленте.
  Позицию считаем `scrollTo` от контейнера (а не `scrollIntoView`: тот дёргал
  заодно список чатов).
- Содержимое секции монтируется лениво (`PanelSection.vue` + `useVisibleOnce`):
  в каталоге эмодзи ~1900 символов, держать их все в разметке сразу — заметная
  работа на ровном месте. Раньше у панели был свой вертикальный скролл внутри
  сетки — теперь прокручивается один контейнер секций.

- В панели стикеров они идут **первым паки** — это наши картинки, они есть у всех

### Отказ от ссылок на паки (решение)

- Передача пака по ссылке (`/s/<токен>`, `share_token`, копии паков) была

  стикеры», а целый набор сразу виден в панели, если он стандартный. Ссылка

  покрывают эти два. Вместе с ней ушли поле «Добавить по ссылке», кнопка

  (её стало негде вставлять).
- Из серверного отката: удалена миграция `a1b2c3d4e5f7` (она ещё не была в
  продакшене), поля модели, три ручки API и три теста; квота снова считает все

### Лента значков: не была привязана к механизму прокрутки

- Симптом: лента категорий и паков не листалась мышью в вебе (и непонятно было,
  что она вообще прокручивается).
- Причина: обработчики колеса/перетаскивания в разметке стояли, но сам элемент в
  `useHScroll` не передавался — composable работал «вслепую»: перетаскивание
  мышью и затухания краёв молча ничего не делали, а признака, что справа есть
  ещё значки, не появлялось. Колесо при этом прокручивало ленту на считаные
  пиксели (переполнение было маленьким), поэтому выглядело как «не работает».
- Исправление: элемент отдаём напрямую (`:ref="panelStrip.el"`), подключили
  `reveal` для подкрутки активного значка.
- Страж в `hScrollLanes.spec.ts`: для каждой ленты проверяем, что элемент
  действительно попадает в composable (`el: <имя>` + `ref="<имя>"` либо
  `:ref="<объект>.el"`), и что имя привязки совпадает с деструктурированным.

# Задача уборки сигналинга звонков: модуль не попал в воркер (2026-09-18)

### Симптом

- В логе воркера раз в 5 минут: `Received unregistered task of type
  'tasks.call_tasks.prune_call_signals'` + «The message has been ignored and
  discarded».

### Причина

- Задача есть в расписании beat (`prune-call-signals` в `build_beat_schedule`) и
  есть в коде (`tasks/call_tasks.py`), но модуль `tasks.call_tasks` не был
  добавлен в список `include` приложения Celery (`core/celery_app.py`). Воркер
  при старте импортирует только перечисленные модули, поэтому задачу не знает и
  молча выбрасывает сообщение из очереди.
- Миграции тут ни при чём: ошибка возникает на этапе **регистрации** задачи, до
  любого обращения к БД. Таблицы `pending_call_offers`/`queued_call_signals`
  создаёт миграция `f9a0b1c2d3e4`; если бы она была не накатана, в логе было бы
  другое — `ProgrammingError: relation ... does not exist` уже внутри задачи.

### Исправление

- `core/celery_app.py`: в `include` добавлен `tasks.call_tasks`.
- Страж
  `tests/test_celery_schedule.py::test_beat_tasks_are_registered_in_worker`:
  для каждой задачи из `build_beat_schedule` проверяет, что её модуль есть в
  `celery_app.conf.include`. Раньше расхождение «расписание есть, модуль не
  импортируется» ловилось только логом воркера на проде.
- После выката перезапустить `worker` и `beat` (образ собирается из кода
  бэкенда): `docker compose -f docker-compose.prod.yaml up -d --build worker
  beat`.

# Панель эмодзи/стикеров: переход по значку вставал не на заголовок (2026-09-18)

### Симптом

- Тап по значку в ленте категорий вёл не к заголовку группы: панель уезжала ниже
  (или не доезжала), и короткая группа — «Реакции», «Недавние» — иногда вообще не
  попадала на экран.

### Причины

- Позиция считалась через `offsetTop`, а он отмеряется от ближайшего

  вкладки, полоса «Добавить/Паки» и лента значков, поэтому цель уезжала вниз
  ровно на их высоту.
- Секции монтируются лениво (`useVisibleOnce`), и у неотрисованной секции высота
  ещё не та: позиция, посчитанная в момент тапа, окажется неверной, как только
  секции по пути дорисуются.

### Исправление

- `MessageComposer.vue`: позиция считается по прямоугольникам относительно самого
  контейнера прокрутки (`sectionOffsetTop`), а не через `offsetTop`.
- Перед переходом лента просит показать всё до цели: у `PanelSection` появился
  проп `force`, в композере — `forcedSectionsUpTo`. Секции ниже цели остаются
  ленивыми, так что выигрыш от ленивой отрисовки сохраняется (в каталоге эмодзи
  ~1900 символов).
- Конец перехода определяется по тишине в событиях прокрутки (`JUMP_QUIET_MS`), а
  не по фиксированной паузе: плавная прокрутка длинной панели идёт больше
  секунды, и прежняя пауза 600 мс успевала вернуть подсветку во время движения —
  активный значок мигал по промежуточным категориям.
- Страж в `frontend/src/__tests__/hScrollLanes.spec.ts`: переход считает позицию
  внутри контейнера, а секции до цели форсируются.

### Проверено

- В браузере (dev, обе панели): тап по каждому значку ставит заголовок секции
  ровно в верх панели («Реакции», «Смайлы», «Природа», «Предметы», «Флаги»),

# Мультиустройство: телефон и компьютер читают одну переписку (A5, 2026-09-18)

### Что было

- У аккаунта уже было несколько ключей E2EE (по устройству), но ключ ЛИЧНОГО чата
  выводился из общего секрета двух «текущих» устройств: второе устройство новые
  сообщения прочитать не могло — самая частая жалоба на такие схемы.

### Клиент

- `frontend/src/services/e2ee.ts`: у личного чата теперь симметричный ключ чата
  (как у группы) и обёртки на КАЖДОЕ устройство обоих участников
  (`distributeChatKey` → `PUT /keys/chat/{chat_id}/`, `chatRawKey` → чтение своей
  обёртки). Обёртка шифруется общим секретом конкретной пары устройств
  (`pairwiseAesKeyWithDevice`), поэтому открыть её может только получатель.
- `chatAesKeyFor` предпочитает симметричный ключ, а прежний ключ из общего секрета
  остаётся фолбэком: им читается переписка, зашифрованная до этой правки
  (перевыпуск ключа задним числом сделал бы её нечитаемой).
- Расшифровка перебирает оба ключа (`chatDecryptKeysFor` + `decryptTextWithKeys`),
  а при полной неудаче один раз перечитывает обёртки (`clearChatKeyCache`): ключ
  могли перераспределить с другого устройства (например, выключили и включили
  шифрование заново).
- Новое устройство участника получает ключ от того, у кого он уже есть:
  `refreshChatKeyWrappers` при открытии чата (раз в сессию) добавляет обёртки для
  появившихся устройств. Само новое устройство раздать не может — у него ключа
  ещё нет.
- Обёртки пишутся ПОВЕРХ (`replace: false`): чужие строки не удаляются, иначе
  выпущенная кем-то копия ключа разломала бы чтение второй стороне.
- `Messenger.vue`: включение E2EE в личном чате раздаёт ключ (`applyChatE2ee`),
  открытие чата обновляет обёртки (`prepareChatE2ee`).

### Проверки

- `frontend/src/__tests__/e2eeMultiDevice.spec.ts` (6, с настоящим WebCrypto):
  устройство собеседника открывает обёртку и получает тот же ключ; второе
  устройство своего аккаунта и новый телефон собеседника читают чат; чужому
  устройству обёртка не подходит; для расшифровки отдаются оба ключа; страж
  проводки в `Messenger.vue`.
- Фронтенд: 1146 тестов, `vue-tsc`, `eslint`, `prettier`, стилевые проверки и
  бюджет бандла (+2435 Б к `index.js`, в допуске 3%) — чисто.
- Живой E2E на двух устройствах не гонялся: нужны два клиента с ключами и
  зашифрованный чат между ними (проверены криптография и проводка).

# Резервная копия ключа шифрования (F2, 2026-09-18)

### Зачем

- Приватный ключ живёт только в `localStorage` этого браузера: переустановка
  приложения, очистка данных или потеря телефона делали переписку зашифрованных
  чатов нечитаемой — сервер расшифровать её не может (в этом и смысл сквозного
  шифрования). Мультиустройство (A5) спасает второе АКТИВНОЕ устройство, но не
  пропажу телефона.

### Что сделано

- `frontend/src/services/e2eeBackup.ts`: файл-копия — JSON с ключом устройства
  (`priv` + `pub` + метка устройства) под AES-GCM, ключ шифрования из парольной
  фразы через PBKDF2-SHA256 (210 000 итераций, соль и IV случайны на каждую
  копию). Проверяются формат, версия, аккаунт (`user_id`), ограничены итерации
  при чтении (10 000…2 000 000).
- `services/e2ee.ts`: `myKeyMaterial` / `installKeyMaterial` — ключ отдаётся
  наружу только в зашифрованном виде, при установке сверяется, что публичная
  часть соответствует приватной (иначе шифрование ломалось бы молча). Метка
  устройства восстанавливается вместе с ключом: обёртки чатов сделаны на пару
  «устройство + ключ».
- Интерфейс: профиль → «Безопасность» → «Ключ шифрования» →
  `E2eeBackupDialog.vue` (ленивый чанк, иначе чанк профиля выходит за бюджет):
  сохранить копию (фраза дважды) и восстановить (файл + фраза). Явное
  предупреждение, что файл + фраза = доступ к переписке; ничего автоматического.

### Побочно найденный и исправленный баг (метка устройства)

- `bootstrapE2ee` фиксировал метку устройства ПОСЛЕ генерации ключа, поэтому
  свежая установка считалась «прежним клиентом» и получала `device_id = legacy`.
  Два устройства (телефон и компьютер) с одной меткой писали ключ в одну строку
  и затирали друг друга — то есть ровно та проблема, ради которой делалось A5
  (и владельцу приходило письмо «ключ заменён»).
- Теперь метка фиксируется до генерации ключа, а уже сохранённая `legacy`
  переводится на свой идентификатор (`utils/deviceId.ts`). У по-настоящему
  старого ключа появится лишняя строка с ТЕМ ЖЕ публичным ключом — безобидно, в
  отличие от столкновения устройств.
- Проверено вживую: в браузере было `pismo_device_id=legacy` и строка `legacy` на
  сервере; после правки у устройства свой UUID, старые чаты читаются.

### Проверки

- `frontend/src/__tests__/e2eeBackup.spec.ts` (8, настоящий WebCrypto): тот же

### Зачем

- Отправленная картинка живёт в переписке вечно: «удалить у всех» — действие
  задним числом. Для чувствительных фото нужен привычный сценарий «сгорело после
  просмотра».

### Что сделано

**Бэкенд**
- Миграция `b6c7d8e9f0a1`: `messages.view_once` (вложение одноразовое) и
  `messages.view_once_opened_at` (когда открыли — по нему в ленте видно
  «Просмотрено», а раздача отличает «сгорело» от «ещё не открывали»).
- `api_v1/media/views.py`: первый GET такого файла помечает вложение
  просмотренным и удаляет блоб ФОНОВОЙ задачей — поток читает файл лениво, и
  удаление раньше оборвало бы уже начатый ответ; дальше — 410 «уже просмотрено».
  `HEAD` просмотр НЕ расходует: браузеры щупают файл перед загрузкой, и «сгорание»

  запрос в БД. Иначе на каждую картинку чата приходился бы запрос к базе —
  раздача медиа обязана оставаться без БД (горячий путь).
- Пересылка одноразового запрещена (`forward_message` → 400): иначе копия уехала
  бы в другой чат и осталась там навсегда. Стикер одноразовым быть не может
  (стикер живёт в панели). Галерея «Медиа» такие вложения не показывает: сетка
  превью выпила бы их разом.

  после открытия»), после просмотра — «Просмотрено» (и по локальной отметке,
  и по `view_once_opened` с сервера).
- Отдельное окно просмотра `ViewOnceViewer.vue` (ленивый чанк): без листания по
  ленте и без кнопки «Скачать». Содержимое скачивается в память вкладки (blob) и
  освобождается при закрытии; для E2EE — обычный путь расшифровки.
- В панели действий и в листе «⋯» у одноразового нет «Переслать», «Сохранить в
  Сохранённые» и «В стикеры».
- В самом окне честно написано, что скриншот или запись экрана запретить нельзя.

### Проверки

# Напоминания о сообщении: «напомнить мне» (F6, 2026-09-19)

Остаток F6 к отложенным сообщениям: «верни меня к этой строке». Отличие по
смыслу — там пишется новое сообщение, здесь человек просит вернуть СЕБЯ к уже
отправленному (бытовой сценарий: «посмотрю вечером», «спрошу завтра»).

### Что сделано

- Таблица `message_reminders` (миграция `a2b3c4d5e6f7`): `user_id`, `chat_id`,
  `message_id` (FK с `ON DELETE CASCADE`), `remind_at` (naive UTC), `created_at`.
  **Текста в записи нет** — он берётся из сообщения в момент срабатывания: его
  могли отредактировать, а напоминание всё равно должно быть узнаваемым.
- Одно напоминание на сообщение у человека (`UNIQUE(user_id, message_id)`):
  повторный выбор времени переносит срок, а не копит «будильники» на одну строку.
- API `api_v1/messages`: `POST /messages/{message_id}/reminder/`
  (`MessageReminderCreate`), `GET /messages/reminders/?chat_id=`,
  `DELETE /messages/reminders/{id}/`. Чат берётся из самого сообщения — напомнить
  о строке из чужого чата нельзя (403), несуществующее сообщение — 404, чужое
  напоминание при удалении — тоже 404 (по ответу нельзя перебирать чужие id).
  Границы времени: 10 секунд … год (`MIN_REMIND_AHEAD`/`MAX_REMIND_AHEAD`).
- Разбор очереди: `tasks/scheduled_tasks.send_due_message_reminders` (beat, раз в
  минуту, `_drain_reminders`) забирает наступившие записи и ставит push
  `tasks.notifications.send_reminder_push`. Запись удаляется при разборе: если
  push уйдёт в никуда (нет подписки/сети), напоминание пропадёт, а не будет
  повторяться каждую минуту вечно.
- Push: уведомление `type: 'reminder'` с названием чата и текстом сообщения;
  в E2EE-чате — только «🔒 защищено сквозным шифрованием», настройка «скрывать
  текст в уведомлениях» тоже соблюдается (остаётся название чата). Тихие часы
  напоминание НЕ отменяют: это просьба самого человека, а не уведомление
  собеседника (как у push о безопасности). Тег уведомления — по id напоминания,
  поэтому два напоминания об одном чате не затирают друг друга.
- Service worker: напоминание считается «чатным» push'ем наравне с сообщением
  (тап открывает приложение в этом чате), но без кнопок «Ответить»/«Отметить
  прочитанным» и без пометки бейджа — новых сообщений оно не приносит.
  `CACHE_VERSION` 28 → 29.
- Клиент: пункт «Напомнить» в меню сообщения (`MessageActionsBar`) и в листе
  действий (`MessageActionSheet`); у сообщения с напоминанием подпись меняется на
  «Изменить напоминание», а у времени появляется колокольчик с подсказкой
  «Напоминание через 1 ч» (`reminderAt` проходит через `MessageThread` функцией,
  как `quoteOf`). Диалог `ReminderDialog.vue` (ленивый чанк) — пресеты «Через
  20 минут», «Через час», «Сегодня в 20:00», «Завтра в 9:00», «Через неделю»,
  текущий срок и кнопка «Убрать напоминание». Полей даты/времени нет осознанно:
  родные контролы браузера в WebView «уезжают» (см. `SelectField`).
- Локального списка (`pismo_reminders`) не делаем: без сервера напоминание не
  сработало бы с закрытым приложением, а две копии очереди — это два источника
  правды (то же решение, что у отложенных).

# Правый клик по сообщению больше не открывает лист действий (2026-09-19)

Просьба владельца: «по правой кнопке в вебе открывается окно с реакциями и др. —
надо отрубить, в мобилке оно тоже мешает».

### Что было

`MessageRow` открывал лист действий (`MessageActionSheet.vue`, то же меню, что на
телефоне) по событию `contextmenu` — а его присылают ТРИ разных источника: правый
клик мышью, СИСТЕМНОЕ меню долгого нажатия (Android) и клавиатура (`Shift+F10`).
Из-за этого на телефоне одно долгое нажатие и выделяло сообщение (наш таймер
удержания), и открывало лист поверх него — то самое «иногда мешает». На компьютере
лист был вообще дублированием: те же действия есть в панели «⋯» при наведении.

### Что стало

- `openContextFromEvent` открывает лист ТОЛЬКО с клавиатуры (у такого события нет
  координат, `clientX/clientY === 0`) — это доступность, а не дублирование. Если у
  события есть координаты (мышь или сенсор), обработчик выходит.
- Событие по-прежнему гасится (`@contextmenu.prevent`): своё меню браузера здесь не
  нужно, действие «Копировать» есть в интерфейсе.
- Пути к действиям на телефоне остались прежними и единственными: первое удержание
  выделяет, повторное удержание уже выделенного сообщения открывает лист (реакции,
  «Ответить», «Перезаслать», «Закрепить», «Пожаловаться» — из панели выделения их
  взять негде, поэтому лист не удалён).

# Каналы: поиск в общем поле, посты как содержимое канала, комментарии экраном (2026-09-19)

Владелец: «как-то криво всё в каналах» и «может не отдельно каталог, а в поиске

# Расшифровка голосовых в текст (F4, 2026-09-19)

Голосовое нельзя прочитать на совещании или в шумном месте, а для слабослышащих
это ещё и доступность — теперь у голосового есть кнопка «В текст».

### Как сделано

- `frontend/src/utils/voiceRecognition.ts`: `SpeechRecognition` по умолчанию
  слушает МИКРОФОН, поэтому для файла используется расширение Chrome —
  `start(MediaStreamTrack)`: звук загружается, декодируется (`AudioContext` →
  `decodeAudioData`) и уходит треком из `MediaStreamDestination` прямо в
  распознаватель. Звук не выводится в колонки: расшифровка идёт молча.
- Кнопка «В текст» в `AudioMessage.vue` (id сообщения приходит из
  `MessageAttachment`) есть ТОЛЬКО там, где браузер умеет распознавать записи
  (`speechRecognitionSupported()`: есть API и `createMediaStreamDestination`).
  В Safari/Firefox кнопки нет — обещать недоступное нельзя.
- Результат живёт в памяти вкладки (карта по id сообщения): на сервер текст не
  уходит и не сохраняется. Фрагменты речи (`continuous` + `interimResults`)
  собираются в один текст, конец записи закрывает распознавание; уход из чата
  зовёт `stopAllRecognitions()` (и `blob:`-ссылка вот-вот освободится),
  «Скрыть» убирает текст, «Скопировать» кладёт в буфер.
- Поведение кнопки зависит от состояния (`transcriptActionFor`): нет расшифровки —
  «В текст», идёт — «Распознаём…» (нажатие отменяет), готово — «Скрыть текст»,
  ошибка — «Ещё раз» (повтор, а не пустое скрытие: иначе кнопка выглядела бы
  сломанной «со второго раза работает»). Ошибки объясняются словами
  (`network`/`no-speech`/запрет).
- Под расшифровкой — честная подпись: распознаёт браузер устройства, и он может
  обращаться к своему сервису; наш сервер аудио не получает. Это проверено
  живьём: в среде без доступа к сервису распознавания приходит `error: network`,
  и человек видит «Браузер не смог обратиться к своему сервису распознавания».

### Проверки

- `frontend/src/__tests__/voiceTranscript.spec.ts` (12): сборка фрагментов речи,
  понятные ошибки (network/тишина), остановка при уходе из чата, «Скрыть»,
  повтор после ошибки и отсутствие кнопки без поддержки API. Полный прогон:
  фронтенд 1335 тестов, vue-tsc/eslint/стилевые проверки и бюджет бандла чисто.
- Живьём (dev, чат 40): голосовой файл виден как «0:00 / 0:03», кнопка «В текст»
  → «Распознаём…» → понятная ошибка про недоступный сервис (сеть среды), затем
  «Ещё раз». Тестовое сообщение удалено.

# Расшифровка голосовых: точность и язык (F4, 19.09.2026, позже в тот же день)

Уточнение к разделу выше: там описана первая версия, здесь — что изменилось после
того, как владелец проверил её на своих голосовых.

### Язык распознавания — главная причина «распознаёт не то»

- **«Привет» превращался в «private»**: язык брался из `navigator.language`, то
  есть у русского человека с английским браузером русская речь разбиралась
  английской моделью — и текст выходил ЧУЖИМИ словами. Теперь по умолчанию
  `ru-RU` (интерфейс приложения русский), а рядом с кнопкой есть выбор языка
  (`SPEECH_LANGUAGES`: русский, English, українська, қазақша, türkçe; «Авто» =
  русский). Выбор помнится на устройстве (`localStorage.pismo_stt_lang`), а не в
  аккаунте: язык голоса — свойство устройства.
- **Язык видно во время распознавания** (`speechLanguageInUse`): если текст вышел
  не тот, причина видна сразу, а не угадывается.
- **Грабля проверки**: правки в `voiceRecognition.ts` не доехали до уже открытой
  вкладки (HMR), и она продолжала крутить модуль, который брал язык из браузера, —
  отсюда «опять private». Живой модуль надо проверять в самой вкладке
  (`await import('/src/utils/voiceRecognition.ts')`), а после правок utils —
  перезагружать страницу. В dev виноват именно HMR: service worker кэширует только
  `/assets/*` и навигацию, `/src/*` он не трогает.

### Точность

- **Запись идёт кусками по 15 с** (`continuous = false`): у Chrome длительный
  continuous-режим разбирает слова хуже и теряет хвост. Кусок кончился — просим
  `stop()` и ждём финальный фрагмент до 1.5 с; `abort()` на нормальном конце не
  зовём вовсе (он выбрасывал незавершённый фрагмент — терялись последние слова).
- **Склейка фрагментов с пробелом** (`appendPart`): Chrome не обязан ставить
  пробел в конце фрагмента, без этого получалось «приветмир».
- **Тихая запись усиливается по пику** (`decodeAudio`, до 0.5 от шкалы, не больше
  ×8): «записал тихо» — частая причина пропущенных слов, а вместе с речью шум не
  поднимаем.
- **`maxAlternatives` убран**: Chrome его фактически не поддерживает, а лишний
  параметр мог увести распознавание на другую ветку (и тогда язык перестаёт
  учитываться). Выбор самой уверенной альтернативы в коде остался — он безвреден
  и сработает там, где уверенность приходит.

### Кнопки: скрытие в одном месте, повтор в блоке

- Владелец: «в копировать/скрыть дублирование, а ещё скрыть текст» → в шапке
  голосового **одна** кнопка-переключатель: «В текст» → «Распознаём…» →
  «Скрыть текст» (одинаково во всех состояниях). В блоке расшифровки — только

  («кнопка ещё раз есть, а скрыть нету»), а готовый текст нельзя было переиграть —
  только скрыть.

# Расшифровка голосовых: нативное распознавание в Android (F4, 19.09.2026)

В WebView API распознавания речи нет вовсе (Web Speech — возможность браузера
Chrome, а не движка WebView), поэтому в приложении кнопки «В текст» не было
вообще. Теперь запись распознаёт САМО устройство.

### Как сделано

- `android/app/src/main/java/space/pismo/app/SpeechFileRecognizer.java`: звук
  пишется во временный файл и уходит системному распознавателю как источник
  (`RecognizerIntent.EXTRA_AUDIO_SOURCE`, нужен Android 13+ — проверили по
  `api-versions.xml` из android-35). Сначала берём распознаватель «на устройстве»
  (`createOnDeviceSpeechRecognizer`, работает без сети), иначе — обычный системный.
- Мост: `PismoNative.speechSupported/speechBegin/speechChunk/speechCancel`, события
  `pismo:speech` (`partial` — текст по мере чтения, `ready`/`failed` — итог).
  Вызовы идут из JS-потока, а распознаватель обязан жить в главном, поэтому
  обращения к нему идут через `Handler(mainLooper)`, а буфер звука защищён
  `synchronized`.
- `frontend/src/utils/audioPcm.ts`: декодирование записи, усиление тихой (±×8),
  моно 16 кГц и PCM 16 бит — системный распознаватель НЕ понимает контейнеры
  (wav/ogg), ему нужен «сырой» поток. Пересчёт частоты делает `OfflineAudioContext`
  (у него есть фильтры), с запасной линейной интерполяцией там, где офлайн-рендера
  нет (тесты).
- `frontend/src/services/nativeSpeech.ts`: звук уходит кусками по 192 КБ (одним
  вызовом большой файл не пролезет) и base64 (строку принимает мост). Подписка на
  событие идёт ДО отправки звука — короткое голосовое иначе отвечало бы в пустоту.
- Выбор пути в `utils/voiceRecognition.ts`: нативный, если он есть, иначе Web
  Speech (куски по 15 с). Кнопка отмены у обоих путей одна, поэтому уход из чата
  останавливает и нативное распознавание.

### Проверки

- `frontend/src/__tests__/nativeSpeech.spec.ts` (12): мост подменяется, поэтому
  проверяются формат звука (2 с при 48 кГц → 32000 отсчётов 16 кГц), нарезка на
  куски и их сборка обратно в байты, одно-вызовный `last`, показ промежуточного
  текста, отсев чужих расшифровок, отмена. Вместе с `voiceTranscript.spec.ts` — 39.
- `./gradlew compileDebugJavaWithJavac` в образе `pismo-android-build` проходит.
- **Не проверено живьём:** распознавание на устройстве (в среде разработки
  распознавателя нет), поэтому в первую очередь надо проверить на телефоне
  Android 13+ и, если система попросит, скачать языковой пакет «на устройстве».

### Что показала живая проверка в среде разработки (19.09.2026)

В песочнице у Chrome НЕТ аудиокодеков: не декодируется даже свой сгенерированный
WAV (`decodeAudioData` → `EncodingError: Unable to decode audio data`), и потому
`<audio>` у всех голосовых даёт `MEDIA_ERR_SRC_NOT_SUPPORTED` (код 4) — в интерфейсе
это «Не удалось воспроизвести аудио», и кнопки расшифровки нет вовсе (она живёт в
нерабочей ветке разметки). Прогнать распознавание живьём тут нельзя, но проверка
поймала настоящий огрех: при нечитаемой записи человек видел ровно код браузера —
английское `EncodingError: Unable to decode audio data`. Теперь сказано по-русски:
«Запись не удалось прочитать — возможно, файл повреждён» (`describeAudioError` в
`utils/audioPcm.ts`, закреплено тестом).

Тестовое сообщение (226) удалено, файл сгенерированного WAV удалён.

# Перевод сообщений (F5, 19.09.2026)

Пункт «Перевести» в меню сообщения: перевод делает ВСТРОЕННЫЙ переводчик браузера
(`Translator`, Chrome 138+) — текст никуда не уходит, что для E2EE-чата
обязательно (сервер открытого текста не знает и знать не должен).

### Что сделано

- `frontend/src/utils/translation.ts`: определение направления по алфавиту (модель
  определителя языка — это ВТОРАЯ загрузка на один перевод, поэтому её не
  используем), выбор языка перевода с запоминанием на устройстве, кэш переводчика
  по паре языков, отмена, состояния `running/ready/failed/download`.
- `frontend/src/components/messenger/MessageTranslation.vue`: блок под сообщением с
  подписью направления («EN → RU»), чипами языка, текстом, процентами скачивания и
  полоской; клик мимо и Escape закрывают блок.
- Пункты меню по наведению и в листе действий, подпись по состоянию
  (`translationActionFor`): «Перевести» → «Перевод…» → «Скрыть перевод».
- Иконка `translate` (Lucide `languages`) добавлена в `utils/icons.ts`, шрифт
  пересобран (`scripts/build_icons.py`).

### Грабли (все выловлены живьём)

- **Модель весит десятки мегабайт и качается один раз.** Молча ждать нельзя:
  `availability()` спрашивается с ограничением 4 с, и, если модель не готова,
  показывается надпись и кнопка «Скачать и перевести» — человек видит, на что
  соглашается.
- **Скачивание требует жеста.** Если перед `create()` сначала ждать
  `availability()`, действие человека уже потрачено и загрузка не начинается
  («почему-то не скачивается»). Поэтому в режиме кнопки `create()` зовётся сразу.
- **Крестик отменяет только скачивание** и стоит в конце полоски прогресса
  («а то непонятно для чего он»), появляется вместе с полоской и блок не убирает —
  после отмены снова видно предложение скачать.
- **Отмена отпускает пару языков** (`releasePair`): иначе повтор подхватывал бы ту
  же прерванную загрузку и снова висел.
- **Любое ожидание ограничено**: браузерный API может не ответить вовсе.
- **Ответ `unavailable` бывает устаревшим** («Для этой пары языков перевода нет» у
  владельца): не отказываем, а даём нажать и попробовать `create()`; если и он
  откажет — пишем, что нужен Chrome 138+.
- **Причина называется прямо**: в браузере внутри VS Code (Electron) сервиса
  моделей Chrome нет, `availability()` там молчит — текст так и говорит («откройте
  приложение в обычном Chrome»), вместо бесконечного «Скачиваем модель…».

### Проверки

- `frontend/src/__tests__/messageTranslation.spec.ts` (28): направление по
  алфавиту, выбор и запоминание языка, кэш пары, проценты и полоска, старт
  скачивания по нажатию, отмена скачивания без потери блока, отказ пары,
  закрытие по клику мимо, и что запросов к нашему API у перевода нет.
- Живьём (dev): блок появляется по пункту меню, показывает предложение скачать
  модель, кнопка стартует попытку (появляются проценты и полоска), крестик её
  останавливает и возвращает предложение.
- **Не проверено живьём:** сам перевод с моделью — в этой среде её скачать неоткуда.

### Что решено не делать

- Внешний сервис перевода (Google/Яндекс) и серверный перевод: текст уходил бы
  третьей стороне или на наш сервер, то есть ломало бы обещание E2EE и §6 политики
  конфиденциальности. Решение владельца: только устройство-перевод.

### Догонка по переводe (19.09.2026)

- **«После перевода на немецкий другие языки дают ошибку»**: отмена освобождала
  пару языков вместе с УЖЕ ГОТОВЫМ переводчиком, а следующий запуск брал из кэша
  уничтоженный объект — браузер отказывался с ним работать, и человек видел «Не
  удалось перевести сообщение». Теперь `releasePair` отпускает только
  НЕзавершённую загрузку, а `AbortError` объясняется словами («Перевод отменён»).
- **Ответ `unavailable` больше не блокирует**: браузер так отвечает и когда модель
  ещё не скачалась (владелец видел «Для этой пары языков перевода нет» на en→ru).
  Теперь показывается предложение и попытка делается по нажатию; если и `create()`
  откажет — пишем, что нужен Chrome 138+.
- **Крестик** стоит в конце полоски прогресса, появляется вместе с ней и
  останавливает только скачивание: блок остаётся, предложение скачать снова видно.

**«Добавить весь набор» — как «ДОБАВИТЬ СТИКЕРЫ» в Телеграме.** Встроенный набор
лежит статикой в приложении (`public/stickers/…`), у сервера его нет, поэтому
добавление — это скачать картинки и загрузить их своим паком: дальше это обычные
свои стикеры (переименовать, переставить, удалить — можно). Кнопка в двух местах:
блок «Наборы приложения» в окне «Мои стикеры» и кнопка в заголовке секции набора в
панели стикеров (у `PanelSection` появился слот `action`). Логика одна на оба места
(`composables/useStandardSetImport.ts`), сам импорт — в сторе
(`importStandardSet`). Отметка «добавлен» — в `pismo_sticker_imports` (ключ набора →
id пака, а не по названию: пак можно переименовать); удалили пак — набор можно
добавить заново. В «Недавние» импорт не пишет.

- ГРАБЛЯ, найденная сразу: `message_upload_limit_per_minute` = 10 загрузок в минуту,
  и на 11-м файле набора приходит 429. Замер на живом сервере: из 16 стикеров прошли
  10 и дальше `429 {"detail":"Слишком много загрузок…"}`. Лечение —
  `uploadStickerPacing`: ждём `Retry-After` и продолжаем (до 8 окон), а в подписи
  кнопки видно «Ждём лимит загрузок (60 с)». Иначе человек получал бы половину
  набора, а набор помечался бы добавленным.
- Тесты: `__tests__/standardSetImport.spec.ts` (5) — набор становится паком, «Недавние»
  не забиваются, частичный сбой НЕ ставит отметку, 429 переживается (fake timers).

**Ключ собеседника больше не спрашивает по кругу.** `public_key` на сервере — это
ключ САМОГО СВЕЖЕГО устройства (`order_by(updated_at desc)`), поэтому у человека с
телефоном и компьютером он законно перескакивает. Клиент помнил ровно один
«виденный» и один «подтверждённый» ключ, поэтому предупреждение возвращалось при
каждом входе, сколько бы раз ни нажимать «Понятно» (жалоба владельца). Теперь
хранится НАБОР ключей (`peer_v2_`/`peer_ok_v2_`, до 8, старый формат читается как
«уже видели»): предупреждаем только про незнакомый ключ, а подтверждение помнит все
подтверждённые. Тесты `__tests__/e2eePeerKey.spec.ts` (8, +3 новых).

**Комментарии канала: аватар вырастал до 512 px.** В диалоге комментариев
`<img class="avatar-img">` не имел правил ни в компоненте, ни глобально (`rows.css`
задаёт аватар только внутри `.ms-rows`) — картинка рисовалась в натуральную
величину и сжимала текст комментария в столбик по одной букве. Замер: аватар
512×518 px, колонка текста 350 px → после правки 34×34 и 828 px. База аватара
(40 px, круг, `object-fit: cover`) теперь в `appearance.css`, компонент со своим
размером её перекрывает; страж — `__tests__/avatarStyles.spec.ts`.

Проверки: 1414 тестов (135 файлов), vue-tsc/eslint/стилевые стражи и бюджет
бандла чисто.

### Публичные (предустановленные) наборы на сервере (19.09.2026)

Вопрос владельца: «у своих стикеров есть пак, а у меня как нет набора?» — по
сообщению пак не определить: отправленный стикер уходит обычным вложением (то есть
новой картинкой на сервере, а не строкой из пака). Поэтому «добавить весь набор»
работало только для встроенных наборов (они помечены меткой в имени файла) либо
требовало бы повторной загрузки каждой картинки.

- `sticker_packs.is_preset` (миграция `b3c4d5e6f7a8`) — «публичный» набор. Ставит
  СУПЕРАДМИН: в окне «Мои стикеры» у пака появился значок-рупор (`authStore.isOwner`).
- `GET /stickers/presets/` — публичные наборы, доступны всем;
  `POST /stickers/presets/{id}/copy/` — «добавить весь набор»: сервер копирует
  ССЫЛКИ на файлы, поэтому это ОДИН запрос — ни лимит частоты загрузок (10 файлов
  в минуту), ни двойное место в квоте не мешают. Повторное добавление → 409
  «Такой набор уже добавлен».
- Панель стикеров показывает публичные наборы секциями и даёт добавить их
  широкой кнопкой под набором; свой же публичный набор не дублируется
  (фильтр по названию).
- Заодно исправлено: широкая кнопка стояла между `v-if` и `v-else-if` и рвала
  цепочку условий сетки — перенесена под сетку.
- Тесты: `backend/tests/test_stickers_api.py` (+2: публикация и копирование с
  переиспользованием файлов, права), всего бэкенд 590.

### Окно набора по тапу на стикер (19.09.2026)

Запрос: «в Телеграме по клику на стикер открывался пак стикеров». Так и сделано:
тап по стикеру в ленте открывает ОКНО НАБОРА — сетку всего набора, отправку
стикера прямо оттуда и кнопку «Добавить весь набор» (у своего набора — «Это ваш
набор», у уже добавленного — «Добавлен»).

- Набор узнаётся по метке в имени файла (`utils/presetStickers.ts`):
  `st-<ключ>` — встроенный (как было), НОВОЕ `sp-<id пака>` — серверный: свой или
  публичный. Метку пишет та же отправка, что и раньше, — при отправке из панели
  теперь помечается и стикер из своего/публичного пака.
- Разбор метки и сборка окна — `utils/stickerSet.ts` (`resolveStickerSet`,
  `stickerSendRef`), без Pinia: его же зовут тесты. Тап по обычной картинке и по
  стикеру без метки работает как раньше (лайтбокс), пункт меню «Добавить набор»
  для встроенных остался.
- Окно — `StickerSetDialog.vue` (ленивый чанк, 1.5 КБ gzip) на общем языке окон
  (`.ms-overlay`): на телефоне листом снизу, на компьютере карточкой по центру.
- Чужой ЛИЧНЫЙ набор опознать нечем (в сообщении только картинка) — как и в
  Телеграме, набор надо опубликовать: тогда он виден всем и добавляется одним
  запросом.
- Тесты: `__tests__/stickerSet.spec.ts` (+9: разбор метки, свой/публичный набор,
  окно и его подвал), `presetStickers.spec.ts` (+3 на метку `sp-`). Вживую через
  CDP: тап по стикеру из встроенного набора — «Реакции, 16 шт., Добавить весь
  набор», тап по стикеру из своего пака — «Это ваш набор»; ошибок в консоли нет.
