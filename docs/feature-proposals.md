# Предложения по развитию Pismo

Составлено 10.09.2026 по итогам разбора кода и прода. Ниже — что можно сделать
дальше, с оценкой сложности и рисков. Порядок внутри разделов = мой приоритет.
Оценки трудозатрат — в «вечерах» разработки (1 вечер ≈ 2–3 часа).

Легенда сложности: 🟢 низкая (вечер-два), 🟡 средняя (2–4 вечера), 🔴 высокая
(недели, отдельный проект).

---

## A. Сквозное шифрование

Сейчас E2EE — «этап 1»: ECDH P-256 + HKDF + AES-GCM для **текста** в **личных**
чатах (`frontend/src/services/e2ee.ts`), публичный ключ на сервере
(`device_keys`), группы и «Сохранённые» зашифровать нельзя (сервер отдаёт 400 —
`backend/api_v1/chats/crud.py:47-51`). Звонки 1-на-1 защищены транспортом
WebRTC (DTLS-SRTP), но сервер управляет сигналингом.

### A1. E2EE для групп («sender keys») ✅ сделано 11.09.2026

**Что:** групповые чаты шифруются симметричным ключом группы. Создатель (или
админ) включает шифрование — ключ раздаётся участникам «обёртками», где каждая
обёртка зашифрована парным ECDH-ключом с получателем (`chat_group_keys`, API
`GET/PUT /keys/group/{chat_id}/`). Когда состав меняется, ключ пересобирается;
после исключения участника выпускается НОВЫЙ ключ, поэтому исключённый не читает
дальнейшую переписку. Заодно шифруются вложения (см. A3).

**Важно:** обёртку может выдать любой участник (например, если создатель не в
сети) — сервер проверяет только членство. Мультидевайс остаётся ограничением
(см. A5), forward secrecy — задача A4.

### A1-исходное-описание (архив) 🔴

**Что:** шифровать групповые чаты. Создатель генерирует симметричный ключ группы,
раздаёт его каждому участнику через уже существующий попарный ECDH-канал; при
изменении состава ключ ротируется, новый участник историю не читает.

**Зачем:** это то, чего нет даже у Telegram (там E2EE только в личных чатах) —
сильный аргумент в описании продукта и в RuStore.

**Как:** `frontend/src/services/e2ee.ts` — добавить уровень «ключ группы» поверх
текущего; `backend/api_v1/chats/crud.py:47-51` — снять запрет; новая таблица
`chat_group_keys` (зашифрованный per-user блоб ключа) + миграция; UI-замок в
`ChatHeader.vue` уже есть.

**Риски:** серверный поиск по такой группе перестаёт работать; мультидевайс
ломается (один ключ на пользователя — см. A5); нужен аккуратный протокол ротации,
иначе исключённый участник продолжит читать.

**Компромисс:** разрешить E2EE-группы до 20 участников и явно предупредить в UI о
потере поиска и истории.

### A2. Проверка ключей собеседника (safety number) ✅ сделано 17.09.2026

**Что:** экран «Проверить шифрование» в карточке зашифрованного чата с кодом из
12 групп по 5 цифр; одинаковый у обоих участников код сверяют вслух или глазами.

**Зачем:** без этого сервер теоретически может подменить публичный ключ и читать
переписку (MITM), то есть обещание «сервер не может прочитать» оставалось без
проверки.

**Как сделано:** код = SHA-512 от публичных ключей ОБОИХ участников в
отсортированном порядке (`utils/safetyNumber.ts` + `safetyNumberWithPeer` в
`services/e2ee.ts`), серверу знать о нём не нужно — считается на устройстве.
Показывается в `SafetyNumberDialog.vue`, вход — кнопка в разделе сквозного
шифрования `ChatInfo.vue`. Короткая версия — первые 30 цифр.

**Осталось (не делали):** QR-код (нужна библиотека кодирования, зависимость ради
одного экрана не оправдана) и отметка «проверено»: ключ привязан к устройству, а
сам факт сверки нигде не хранится — после смены устройства сверять надо заново.

### A3. Шифрование медиа и голосовых ✅ сделано 11.09.2026

**Что:** вложения шифруются на клиенте отдельным случайным ключом (AES-GCM), а
сам ключ вместе с настоящим именем/типом/размером/подписью складывается в
«конверт», который шифруется ключом чата и уходит в текст сообщения. Сервер
хранит только шифротекст и нейтральное имя `enc_<hex>.bin`; в списке чатов и
пуш-уведомлениях такие вложения показаны как «🔒 Вложение». Работает и в личных
зашифрованных чатах, и в группах (`frontend/src/services/e2eeFiles.ts`,
`composables/useDecryptedMedia.ts`).

**Осталось:** серверная генерация превью (если появится) и шифрование аватарок
групп — сейчас аватары групп не шифруются.

### A3-исходное-описание (архив) 🔴

**Что:** сейчас `messages.encrypted` относится только к тексту — картинки,
видео, голосовые и файлы лежат на сервере в открытом виде, хотя в политике
говорится про E2EE для отдельных чатов. Шифровать блоб случайным ключом, ключ
класть в текст сообщения (зашифрованный E2EE), сервер хранит только блоб.

**Зачем:** закрывает расхождение «политика обещает больше, чем код делает» —
это ещё и юридический риск, а не только продуктовая дыра.

**Как:** `frontend/src/services/storage.ts` (шифрование до загрузки),
`backend/api_v1/messages/crud.py` (не отдавать превью/имя файла для зашифрованных),
превью в списке чатов — «🔒 Вложение».

**Риски:** ломается серверная генерация превью (если есть), растёт нагрузка на
клиент, придётся решать, что делать с медиа в уже существующих чатах.

### A4. Мониторинг «этап 3»: forward secrecy 🔴

**Что:** полноценный Double Ratchet (Signal) — ключ на каждое сообщение, старые
ключи уничтожаются.

**Зачем:** компрометация одного ключа сейчас раскрывает всю историю чата.

**Честно:** это отдельный проект на недели, требует prekeys, хранения сессий,
решения конфликтов мультидевайса. **Не советую брать до A1/A2.** Дешёвый
промежуточный вариант — цепочечный ключ: каждые N сообщений (например 100) ключ
ратируется, старые недоступны.

### A5. Несколько устройств вместо одного ключа ✅ сделано 18.09.2026

**Что:** разрешить один аккаунт на нескольких устройствах: ключи на пару
(user, device), а не один на пользователя (`backend/core/models/device_key.py`).

**Зачем:** новый вход больше не делает прежнюю переписку нечитаемой — это самая
частая жалоба на такие схемы.

**Сделано (сервер):**

- `device_keys` идентифицируется парой `(user_id, device_id)` (миграция
  `c4d5e6f7a8b9`): вход с телефона добавляет строку, а не заменяет ключ
  компьютера. `device_id` генерирует клиент и хранит у себя; строка `legacy` —
  старый клиент, который его не присылает (совместимость сохранена).
- `PUT /keys/me/` принимает `device_id`, `GET /keys/{user_id}/` отдаёт список всех
  устройств (`devices`) и прежнее поле `public_key` (ключ самого свежего
  устройства) — старый клиент продолжает работать.
- Обёртки ключа чата на устройства: таблица `chat_device_keys` и эндпоинты
  `GET/PUT /keys/chat/{chat_id}/` (миграция `f1a2b3c4d5e6`). Раздать может любой
  участник чата, обёртка для незарегистрированного устройства не сохраняется.
- Клиент уже присылает свой `device_id` (`utils/deviceId.ts`): впервые —
  случайный, а на устройстве со старым ключом остаётся `legacy`, чтобы тот же
  ключ не записался второй строкой.
- Тесты: `tests/test_device_keys_multi.py` (5), `tests/test_chat_device_keys.py`
  (8).

**Сделано (клиент, 18.09.2026):** у ЛИЧНОГО чата теперь тоже симметричный ключ
(как у группы), а не ключ из общего секрета двух «текущих» устройств.

- `services/e2ee.ts`: `distributeChatKey` выпускает ключ и раскладывает обёртки на
  ВСЕ устройства обоих участников (`userDevices` → `pairwiseAesKeyWithDevice`:
  общий секрет конкретной пары устройств); `chatRawKey` открывает свою обёртку
  (`GET /keys/chat/{chat_id}/`); `chatAesKeyFor` предпочитает симметричный ключ,
  а прежний ключ из общего секрета остаётся фолбэком — им читается переписка,
  зашифрованная до этой правки.
- Расшифровка перебирает ОБА ключа (`chatDecryptKeysFor` + `decryptTextWithKeys`),
  а если не подошёл ни один — обёртки перечитываются один раз
  (`clearChatKeyCache`): ключ могли перераспределить с другого устройства.
- Новое устройство участника получает ключ от того, у кого он уже есть:
  `refreshChatKeyWrappers` при открытии чата один раз за сессию добавляет обёртки
  для появившихся устройств (само новое устройство раздать не может — у него
  ключа ещё нет).
- Обёртки ПИШУТСЯ ПОВЕРХ (`replace: false`): чужие строки не удаляются, иначе
  сторона, выпустившая свою копию ключа, разломала бы чтение собеседнику.
- Включение E2EE в личном чате раздаёт ключ сразу (`applyChatE2ee`), открытие —
  обновляет обёртки (`prepareChatE2ee`).
- Тесты: `frontend/src/__tests__/e2eeMultiDevice.spec.ts` (6) — с настоящим
  WebCrypto: обёртка открывается устройством собеседника, второе устройство
  своего аккаунта и новый телефон читают чат, чужому устройству обёртка не
  подходит; плюс страж проводки в `Messenger.vue`.

**Ограничение (осознанно):** пока обёртки для устройства нет, чат шифруется
прежним ключом — сообщение прочитают только «текущие» устройства. Так же
работает история, зашифрованная до этой правки: перевыпуск ключа задним числом
сделал бы её нечитаемой.

**Побочно найден и исправлен баг:** метка устройства определялась ПОСЛЕ генерации
ключа, поэтому свежая установка тоже считалась «прежним клиентом» и получала
`device_id = legacy` — телефон и компьютер снова писали ключ в одну строку.
Теперь метка фиксируется до генерации (`bootstrapE2ee`), а уже сохранённая
`legacy` переводится на свой идентификатор (`utils/deviceId.ts`): у старого ключа
появляется лишняя строка с тем же публичным ключом — безобидно, в отличие от
столкновения устройств.

### A6. Честность бейджа в звонках + код сверки ✅ сделано 17.09.2026

**Что:** в звонке 1-на-1 медиа действительно идёт между участниками
(DTLS-SRTP, TURN только релеит и расшифровать не может), но сигналинг ведёт наш
сервер — теоретически он мог бы вклинить третьего участника. Теперь это можно
проверить, а бейдж говорит правду.

**Как сделано:**

- код сверки — 6 цифр из отпечатков сертификатов DTLS (`a=fingerprint:sha-256`)
  ОБЕИХ сторон, взятых в отсортированном порядке (`utils/callVerification.ts`):
  каждая сторона берёт свой локальный и чужой удалённый отпечаток, поэтому код
  совпадает, а подмена сертификата даёт другой код. Показывается в звонке (меню
  «Код сверки») с пояснением, что сверять надо вслух и при каждом звонке;
- бейдж вместо общего «Сквозное шифрование» показывает маршрут: «Напрямую (P2P)»
  или «Через релей» (по `candidateType` из `getStats`), а в подсказке написано,
  что при релее шифрование сохраняется и релей видит только шифротекст.

**Осталось (осознанно не делали):** показ отпечатка целиком и QR — цифр хватает,
а для QR нужна библиотека кодирования.

## B. Звонки

### B1. Демонстрация экрана ✅ сделано 10.09.2026

Кнопка «Показать экран» в звонке (`getDisplayMedia` + `replaceTrack`). Если звонок
был голосовым — добавляется видео-линия и делается пересогласование SDP
(`call-renegotiate`/`call-renegotiate-answer` в сигналинге), интерфейс переходит в
видео-режим. Камера на время показа гасится, при остановке включается заново
(если не удалось — звонок продолжается без видео). Остановка через кнопку в нашем
интерфейсе или плашку браузера. Собеседник видит плашку «Собеседник показывает
экран».

### B2. Групповые звонки до 4 человек «mesh» ✅ сделано 17.09.2026

**Что:** вместо тяжёлого SFU — полносвязная P2P-схема на 3–4 участника (каждый
держит отдельный `RTCPeerConnection` с каждым). Сервер только раздаёт SDP/ICE по
участникам.

**Зачем:** групповой звонок есть в списке «сознательно отложено» именно из-за
SFU. Но до 4 человек SFU не нужен — а это уже покрывает почти все бытовые
сценарии (семья, пара друзей, маленькая команда).

**Бонус:** только при mesh-схеме сохраняется сквозное шифрование (медиа идёт
напрямую), с SFU оно ломается — то есть mesh даёт нам «групповые звонки со
сквозным шифрованием», чего нет у большинства.

**Как сделано:** комнаты на сервере не понадобились — ретранслятор уже
адресный (`to_user_id`), а состав звонка ведёт небольшой реестр
(`_group_calls` в `api_v1/calls/views.py`). Клиент перешёл с одного
`peerConnection` на карту связей (`runtime.links`): SDP/ICE раскладываются по
связи отправителя, а медиа-операции (показ экрана, смена камеры/микрофона,
битрейт, состояние медиа) применяются ко всем связям сразу. Кто с кем
соединяется — решает правило «младший по id инициирует»: иначе обе стороны
начали бы offer одновременно (glare). Сервер рассылает состав звонка
(`call-peers`), проверяет, что чат групповой и оба участника в нём, и держит
лимит в четыре человека («full» пятому). Интерфейс — сетка плиток
(`components/calls/CallGrid.vue`), у каждого участника своя плитка и свой поток.
Кнопка звонка появилась в групповых чатах (в каналах — нет).

**Риски:** растёт трафик и CPU на слабых телефонах — поэтому лимит 4 и явное
сообщение, когда мест нет. Проверено в браузере: вызов из группы доходит до
сервера и паркуется у офлайн-участника; полноценная проверка на 3–4 устройствах
— на реальных телефонах (в dev столько аккаунтов нет).

**Побочная находка (исправлено):** поиск личного чата между людьми не проверял
тип чата, поэтому «написать лично» мог открыть ГРУППУ на двоих, а запись о
звонке попадала в группу вместо личного диалога (`get_private_chat_id_between`).

### B3. Выбор устройств и запоминание настроек ✅ сделано 10.09.2026

Панель «Устройства звонка» (кнопка `tune`) со списками камер/микрофонов/динамиков
на основе `enumerateDevices`; выбор сохраняется в localStorage
(`pismo_call_devices`) и применяется на следующем звонке. Смена камеры/микрофона

### B4. TURN: TLS и временные креды 🟡

Сейчас в coturn статический логин/пароль, без TLS (`docker-compose.prod.yaml:240`,
`docs/turn.md` сам помечает это как обязательное для прода). Правильно: TLS на
5349 + креды, вычисляемые сервером по HMAC на короткое время (TURN REST API).
Это чистая безопасность: статический пароль в бандле могут увести и гонять
чужой трафик через наш релей.

### B6. Сигналинг звонков и presence — в мост RabbitMQ ✅ сделано 17.09.2026

**Что:** раньше `call_manager` и presence/«печатает» жили только в памяти
процесса (`backend/api_v1/calls/manager.py`, `api_v1/events/manager.py`), а через
мост ходили лишь события от воркера. Теперь события мессенджера и сигналинг
звонков идут через обмен моста: каждый процесс получает их из fanout и раздаёт
своим сокетам.

**Сделано (этап 1):**

- `core/amqp.py`: в теле события есть метка процесса (`origin`) и номер
  (`event_id`). Своё же событие процесс отбрасывает (иначе звонок получал бы два
  `call-answer`), повторная доставка отсекается по `event_id`. Канал публикации
  переиспользуется, есть таймауты и предохранитель (5 с тишины после двойной
  неудачи), чтобы недоступный брокер не задерживал HTTP-запросы.
- Подтверждение доставки (`ack`): отправитель сигнала просит ack и ждёт его
  (`wait_for_delivery`). Без этого нельзя решить главный вопрос — абонент офлайн
  или просто «в другом процессе»; теперь паркуем вызов только в первом случае.
- `api_v1/events/service.dispatch_realtime` — единая точка отправки: локальная
  раздача плюс мост. Через неё идут все события (сообщения, прочтение,
  presence, «печатает…», каналы, истории), а сигналинг звонков — через
  `_deliver_signal` в `api_v1/calls/views.py`.
- Что это даёт: при двух слотах `web` (деплой, масштабирование) звонок
  соединяется, а сообщения и presence доходят до человека на другом процессе.

**Сделано (этап 2, 17.09.2026):**

- парковка офлайн-вызова и недоставленный сигналинг переехали в БД
  (`pending_call_offers`, `queued_call_signals`, миграция `f9a0b1c2d3e4`,
  `api_v1/calls/store.py`): абонент, открывший приложение на другом слоте, вызов
  получает, а зовущий — придержанный ответ. Строки живут минуты и удаляются при
  чтении; страховочная задача `tasks.call_tasks.prune_call_signals` раз в 5 минут.
- присутствие собирается из своих сокетов и пульса других процессов
  (`presence-heartbeat` раз в 15 с, TTL 45 с): человек «в сети», даже если смотрит
  в приложение на другом слоте, а умерший процесс перестаёт пульсировать и его
  пользователи гаснут сами.

**Итог:** перекрытие слотов `web` больше не ломает ни звонки, ни статусы — второй
слот можно держать живым дольше (см. `docs/production.md`). Перед изменением
`DRAIN_SECONDS` стоит один раз проверить вызов и статус между слотами вживую.

**Сложность:** средняя — интерфейс публикации уже есть
(`core/amqp.py::publish_realtime_event`), нужно провести через него звонки и
добавить идемпотентность (событие может прийти дважды).

### F1. Одноразовые медиа («посмотреть один раз») ✅ сделано 18.09.2026

**Что:** у вложения флаг «сгорает после просмотра»: сервер отдаёт файл один раз
и удаляет, в ленте остаётся «Просмотрено».

**Зачем:** отправленная картинка живёт в переписке вечно, а «удалить у всех» —
действие отправителя задним числом. Одноразовые медиа — привычный сценарий для
чувствительных фото.

**Как сделано:**
- Миграция `b6c7d8e9f0a1`: `messages.view_once` и `messages.view_once_opened_at`
  (второе — чтобы отличать «сгорело» от «ещё не открывали»).
- Файл одноразового вложения кладётся с префиксом имени `vo_`
  (`core/media_store.VIEW_ONCE_PREFIX`). По нему раздача медиа понимает, что
  нужно сходить в БД, — обычные картинки по-прежнему отдаются без единого
  запроса к базе (это горячий путь).
- `api_v1/media/views.py`: первый GET помечает вложение просмотренным и удаляет
  блоб ФОНОВОЙ задачей (поток читает файл лениво — удаление раньше оборвало бы
  ответ), дальше — 410 «уже просмотрено». `HEAD` просмотр не расходует: браузеры
  щупают файл перед загрузкой.
- Пересылка одноразового запрещена (`forward_message` → 400): иначе копия уехала
  бы в другой чат и осталась там навсегда. Галерея «Медиа» такие вложения не
  показывает — сетка превью сожгла бы их разом.
- Интерфейс: в меню вложения («Прикрепить») появился пункт «Посмотреть один раз»
  (только фото/видео); в ленте вместо превью — плашка «Одноразовое фото · сгорит
  после открытия», после просмотра — «Просмотрено». Открывает отдельное окно
  (`ViewOnceViewer.vue`, ленивый чанк): без листания по ленте и без «Скачать»,
  содержимое скачивается в память вкладки (blob) и освобождается при закрытии.
- В панели действий и в листе «⋯» у одноразового нет «Переслать»,
  «Сохранить в Сохранённые» и «В стикеры» — обещать недоступное нельзя.

**Риски (написано в самом окне просмотра):** скриншот или запись экрана запретить
нельзя — поэтому текст честно предупреждает об этом, а не делает вид, что медиа
не сохранить.

### F2. Резервная копия ключа: переписка переживает новое устройство ✅ сделано 18.09.2026

**Что:** явный экспорт ключа шифрования (файл или слова) и восстановление на
новом устройстве.

**Зачем:** ключ устройства лежит в `localStorage` (`pismo_e2ee_v1_<uid>`);
переустановка приложения = история нечитаема. A5 закрывает случай «телефон и
ноутбук одновременно», но не потерю телефона.

**Как:** `crypto.subtle.wrapKey` ключом из пароля → файл, восстановление обратным
порядком; ключи чатов затем перевыпускаются обёртками на восстановленный ключ.

**Риски:** самая чувствительная точка — копия ключа равна доступу к переписке.
Только по явному действию, с предупреждением, никогда автоматически.

**Как сделано (18.09.2026):**

- `frontend/src/services/e2eeBackup.ts`: файл-копия — JSON с ключом устройства
  (`priv` + `pub` + метка устройства), зашифрованным AES-GCM, а ключ шифрования
  выводится из парольной фразы через PBKDF2-SHA256 (210 000 итераций, соль и IV
  случайны на каждую копию). Без фразы файл бесполезен, без файла фраза не нужна.
- Метка устройства восстанавливается ВМЕСТЕ с ключом: обёртки ключей чатов
  сделаны на пару «устройство + ключ», без метки восстановленный ключ историю не
  откроет. Нового устройства на сервере при этом не появляется — строка та же.
  Пара проверяется на согласованность (`pub` сверяется с `priv`), иначе
  шифрование ломалось бы молча.
- Копию нельзя восстановить в другой аккаунт (в файле `user_id`), файл
  проверяется на формат и версию, число итераций при чтении ограничено
  (10 000…2 000 000 — защита от «файла на миллиард»).
- Интерфейс: профиль → «Безопасность» → «Ключ шифрования» →
  `E2eeBackupDialog.vue` (ленивый чанк). Явное предупреждение, что файл + фраза =
  доступ к переписке; ничего автоматического.
- Тесты: `frontend/src/__tests__/e2eeBackup.spec.ts` (8, настоящий WebCrypto) —
  тот же ключ и метка на новом устройстве, переписка читается после
  восстановления, чужая фраза/подменённый файл/чужой аккаунт/короткая фраза
  отклоняются, две копии отличаются, несовпадающие части не устанавливаются.

**Осталось осознанно:** мнемоника вместо фразы (BIP39) и автоподсказка «сделайте
копию» — сейчас о копии напоминает только раздел «Безопасность».

### F3. Список поставивших реакцию ✅ сделано 18.09.2026

**Что:** тап по реакции — имена тех, кто её поставил (сейчас только счётчик).

**Зачем:** в группах счётчик читается как «кто-то», а имена — та самая обратная
связь, за которой реакции и ставят.

**Как сделано:**
- Бэкенд: в агрегат реакции (`ReactionSummary`) добавлено поле `user_ids` —
  только id авторов, без имён: имена уже есть в участниках чата, дублировать их
  в каждом сообщении незачем (и это лишний вес ответа в группе на сотни
  сообщений). Порядок — как реакции пришли из БД. Поле есть только у полного
  сообщения (`message_to_dict`); в превью списка чатов реакций нет вообще.
- Клиент: тап по чипу по-прежнему ставит/снимает СВОЮ реакцию, а **удержание
  (450 мс) или правый клик** открывает список «Кто поставил»
  (`ReactionUsersDialog.vue`). Имена берутся из участников чата по id, аватар —
  миниатюра (`avatar_thumb_url`), неизвестный id показывается как «Участник»,
  «Вы» всегда первым и с пометкой.
- Вид — как в Telegram: чипы реакций живут ВНУТРИ пузыря (в нижнем ряду рядом со
  временем, фон пузыря служит подложкой), рамок у чипа нет — выделение тоном
  (`--ms-accent-soft` у своей реакции). Пока отметивших не больше трёх, в чипе
  видны их мини-аватарки, дальше — счётчик. Эмодзи в сообщении прежнего размера
  (`--ms-fs-md`), а в окне «кто поставил» — крупнее (`--ms-fs-lg` на вкладках и
  24 px в шапке): там он содержание, а не метка.
- Окно списка — всплывающее (`q-menu`), привязано к чипу (`anchor="bottom
  middle"`, `self="top middle"`): открывается СНИЗУ от реакции, при нехватке
  места Quasar сам разворачивает вверх. `no-parent-event` — чтобы клики по чипу
  не мигали окном (открываем только удержанием/правым кликом).
- Новая реакция проигрывает анимацию: эмодзи «выстреливает» (scale + поворот)
  и вокруг расходится ореол тоном. Класс `fresh` ставится по РОСТУ счётчика
  (`watch` на `message.reactions`) и снимается таймером — снятие реакции и
  первая отрисовка ленты не анимируются, иначе мигала бы вся история.
- Удержание отменяется сдвигом указателя больше 12 px (жест прокрутки), а не
  выходом за чип: при наведении появляется панель действий, строка едет, и
  `pointerleave` гасил удержание при неподвижном пальце.
- Окно подключено лениво (`defineAsyncComponent`), `QMenu` зарегистрирован в
  `src/quasar.ts` и добавлен в подмножество стилей Quasar
  (`quasar-subset.sass`), иначе меню отрисовалось бы без стилей.

**Цена:** главный чанк `index.js` вырос на ~4.2 КБ gzip (новые чипы, лица,
анимация и полосы подсветки), бюджет обновлён осознанно
(`scripts/bundle-size-baseline.json`, 18.09.2026).

**Риски (осознанно отложено):** в очень больших группах список может быть
длинным — показываем всех, «и ещё N» добавим, если попросят; список обрезан
визуально скроллом карточки.

### F4. Расшифровка голосовых в текст 🟡

**Что:** кнопка «В текст» у голосового сообщения.

**Зачем:** голосовое нельзя прочитать на совещании или в шумном месте; для
слабослышащих это ещё и доступность.

**Как:** `SpeechRecognition` (Web Speech API) — бесплатно и на устройстве; в
E2EE-чате это единственный возможный путь.

**Риски:** поддержка браузерами разная, в Android-обёртке (WebView) может
отсутствовать — кнопку показывать по наличию API.

### F5. Перевод сообщений 🟡

**Что:** «Перевести» в меню сообщения.

**Зачем:** переписка на другом языке — частый случай, особенно в каналах.

**Как:** вызов внешнего API с клиента (текст и так на устройстве), результат —
строкой под исходным. В E2EE-чате только на клиенте: открытый текст на сервер не
уходит.

**Риски:** внешний сервис видит текст (в незашифрованных чатах он и так на
сервере); нужен лимит и кэш по сообщению.

### F6. «Отправить позже» и напоминание о сообщении ✅ сделано 18–19.09.2026

**Что:** отложенная отправка (время) и «напомнить мне» о конкретном сообщении.

**Зачем:** «не пиши ночью, отправь в 9:00» и «вернуться к этому вопросу» —
бытовые сценарии, которых сейчас нет вовсе.

**Как:** отложенные — маленькая таблица + задача Celery (иначе не сработает с
закрытым приложением); напоминания проще локально (`pismo_reminders`, как пины и
архив), но тогда нужен push-дубль на случай закрытого приложения.

**Риски:** серверная очередь требует чистки и лимита; локальная молчит в фоне.

**Как сделано (отложенные, 2026-09-18):**
- Таблица `scheduled_messages` (текст + `send_at`), миграция `c8d9e0f1a2b4`.
  Хранится **только текст**: вложение пришлось бы держать на диске до срока, а
  при отмене файл остался бы сиротой.
- Разбор очереди — `tasks/scheduled_tasks.py` (beat, раз в минуту), поэтому
  сообщение уходит и с закрытым приложением. Права (мут, бан, выход из чата)
  проверяются в **момент отправки**: к тому времени они могли измениться, а
  безнадёжную запись удаляем с записью в лог — иначе она повторялась бы вечно.
- API: `POST/GET/DELETE /messages/scheduled/` — лимиты по времени (не раньше
  10 с и не позже 30 дней), чужую отмену отдаём как 404, чтобы по ответу нельзя
  было перебирать чужие id.
- Клиент: удержание или правая кнопка на кнопке отправки открывают время
  («Через час» / «Сегодня в 9:00» / «Завтра в 9:00»); шторка над полем ввода
  показывает очередь этого чата и умеет отменить. В E2EE-чате текст шифруется
  до отправки на сервер, а список показывает расшифрованное превью.
- **Осталось:** «напомнить мне» о конкретном сообщении (локальные напоминания
  `pismo_reminders` + push-дубль для закрытого приложения).

**Как сделано (напоминания, 2026-09-19):**
- Таблица `message_reminders` (миграция `a2b3c4d5e6f7`): человек, чат, сообщение и
  время. **Текста в записи нет** — он берётся из самого сообщения в момент
  срабатывания (сообщение могли отредактировать или удалить, а напоминание всё
  равно должно привести в чат); удалили сообщение — напоминание уходит вместе с
  ним (`ON DELETE CASCADE`).
- На одно сообщение у человека одно напоминание (`UNIQUE(user_id, message_id)`):
  повторный выбор времени переносит срок, а не копит «будильники» на одну строку.
- API: `POST /messages/{message_id}/reminder/` (чат берётся из сообщения —
  напомнить о строке из чужого чата нельзя), `GET /messages/reminders/?chat_id=`,
  `DELETE /messages/reminders/{id}/` (чужое — 404, чтобы по ответу нельзя было
  перебирать чужие id). Границы времени — 10 с … год.
- Доставка: та же beat-задача разбора очереди, что у отложенных
  (`tasks.scheduled_tasks.send_due_message_reminders`, раз в минуту) ставит push
  `tasks.notifications.send_reminder_push` (Web Push + RuStore). Запись удаляется
  при разборе: пропущенный push не должен повторяться каждую минуту вечно.
- **Тихие часы напоминание не отменяют**: это не уведомление собеседника, а
  просьба самого человека вернуться к сообщению — он сам выбрал время (то же
  правило, что у push о безопасности). Настройка «скрывать текст в уведомлениях»
  соблюдается: остаётся только название чата.
- В уведомлении — название чата и текст сообщения (в E2EE-чате только пометка
  «🔒 защищено сквозным шифрованием»: на сервере шифротекст). Тап открывает
  приложение в этом чате (service worker считает напоминание «чатным» push'ем,
  как сообщение, но без кнопок «Ответить»/«Отметить прочитанным»).
- Интерфейс: пункт «Напомнить» в меню сообщения и в листе действий (у сообщения с
  напоминанием — «Изменить напоминание»), диалог `ReminderDialog.vue` с
  пресетами («Через 20 минут», «Через час», «Сегодня в 20:00», «Завтра в 9:00»,
  «Через неделю») и кнопкой «Убрать напоминание», значок-колокольчик у времени
  сообщения с подсказкой «Напоминание через 1 ч». Свои поля даты/времени не
  используем: родные контролы браузера в WebView «уезжают» (см. `SelectField`).
- Локального списка (`pismo_reminders`) в итоге НЕ делаем: без сервера
  напоминание не сработало бы с закрытым приложением, а держать две копии
  очереди — это два источника правды (то же решение, что у отложенных).

### F7. Экспорт переписки 🟡

**Что:** «Выгрузить чат» — файл с историей (текст, автор, время, ссылки на медиа).

**Зачем:** данные человека должны быть выносимы — и для своего архива, и как
аргумент доверия.

**Как:** на клиенте: собрать историю страницами, расшифровать E2EE на месте,
отдать забранным HTML/JSON. Серверу открытый текст не нужен.

**Риски:** тяжело на длинных чатах — постранично, с предупреждением о размере.

### F8. Мультиаккаунт 🟡

**Что:** несколько аккаунтов на устройстве (личный и рабочий) с переключением.

**Зачем:** вход закрытый (по приглашению), один телефон на две роли — сейчас это
второй браузер или повторный вход с кодом.

**Как:** второй набор токенов + переключатель в профиле. Данные уже разделены по
id пользователя (ключи `pismo_*`), мешает единичность `authState`.

**Риски:** уведомления и бейдж должны знать активный аккаунт; фоновые запросы
второго аккаунта не должны «оживлять» присутствие.

### F9. Экран поиска каналов (каталог) ✅ сделано 19.09.2026

**Что:** поиск публичных каналов по названию и адресу и подписка из него.

**Зачем:** сейчас подписаться можно только по прямой ссылке `/c/<адрес>`. Сервер
уже умеет `GET /channels/search/`, в клиенте есть `searchChannels` — но экрана
нет, функция не вызывается нигде.

**Как:** строка поиска в разделе «Каналы» + список карточек, переиспользовать
`ChannelCard` и `ChannelJoinDialog`.

**Риски:** с появлением поиска нужна модерация каталога (спам-каналы): показывать
каналы с активными владельцами и закрывать по жалобам.

**Как сделано (19.09.2026):** отдельного экрана НЕТ — это третья вкладка общего
поиска («Люди / Сообщения / Каналы») в панели поиска: серверный поиск каналов уже
был, а второе место для того же запроса только путало бы. Выбор канала открывает
знакомую карточку подписки (тот же экран, что по ссылке `/c/<адрес>`), а пустой
раздел «Каналы» просто подсказывает искать поиском. По ходу починено в самом
поиске: экранирование символов `LIKE` (запрос «%» показывал ВСЕ публичные каналы),
точное совпадение адреса поднято первым и добавлен лимит на поиск каналов.

### F10. Анти-флуд в группах: мут, бан-лист, медленный режим ✅ сделано 18.09.2026

**Что:** остаток раздела C. Роли сделаны 17.09, но флуд остановить нечем:
`kick_group_member` есть, а исключённый входит по той же ссылке, и никто не
мешает писать по 50 сообщений в минуту.

**Как сделано:**
- `chat_user_association.muted_until` — мут живёт в самом членстве: он неразрывно
  связан с участием (исключили — мут не нужен), а срок снимается сам по времени,
  отдельного действия «снять мут» в БД не требуется.
- `chat_bans` (новая таблица, уникальная пара «чат + человек») — исключение эту
  задачу не решало: исключённый возвращался по ссылке. Забаненный не входит ни по
  ссылке-приглашению, ни добавлением админом (в канале — так же), снимает бан
  только админ/создатель.
- `chats.slow_mode_seconds` — пауза между сообщениями участника (0 — выключено),
  пресеты в интерфейсе: 10 с, 30 с, 1 мин, 5 мин, 15 мин, 1 час.
- Проверка одна на все пути отправки — `chats/crud.py::ensure_can_write`: текст,
  вложение, пересылка. Иначе мут обходится «отправить картинкой». У загрузки она
  стоит ДО чтения тела: молчащему незачем гнать мегабайты, чтобы получить отказ.
- Админов и создателя не ограничивает ничего (они и ставят правила), себя
  ограничить нельзя, админ не ограничивает админа — те же правила, что у
  исключения.
- API: `POST/DELETE …/members/{id}/mute/`, `POST …/members/{id}/ban/`,
  `DELETE …/bans/{id}/`, `GET …/bans/`, `PATCH …/slow-mode/`. Мут и бан отвечают
  карточкой группы: список участников на экране обновляется без второго запроса.
- Интерфейс: в карточке группы у участника появились «Замутить» (пресеты
  длительности) и «Забанить», у замученного — метка «в муте», ниже — блок
  «Анти-флуд» с выбором медленного режима и бан-листом с кнопкой «Разбанить».

**Риски (осознанно):** лимит бьёт и по легитимным всплескам — поэтому админы
исключены из режима; мут навсегда не делаем (для этого есть бан), максимум неделя.

### F11. Наблюдаемость: Sentry и метрики 🟡

**Что:** ошибки фронта и бэка — в Sentry, метрики (запросы, лаг Celery, очередь) —
в Prometheus.

**Зачем:** сейчас наблюдаемость — почтовый мониторинг раз в 15 минут и
`X-Request-ID` со логом медленных запросов: инцидент виден по факту «сайт не
открывается», а деградация — только строкой в логе.

**Как:** `sentry-sdk` в FastAPI + `@sentry/vue`, `/metrics` из
`prometheus-fastapi-instrumentator`, экспортёр RabbitMQ.

**Риски:** внешний сервис — это трансграничная передача ПДн (см.
`docs/rkn-notification.md`): из событий исключить тела сообщений и номера.

### F12. Общий стор для лимитов и «замков» (Redis) 🟡

**Что:** вынести in-memory состояние в Redis: окна rate-limit и «замки» перебора
OTP.

**Зачем:** в `core/rate_limit.py` прямо написано, что для горизонтального
масштабирования нужен общий стор. События, звонки и присутствие мост RabbitMQ уже
развёл, а лимиты остаются у каждого процесса свои — при двух `web` лимит на
пользователя фактически удваивается.

**Как:** интерфейс узкий (`enforce_limit`, `SlidingWindowLimiter`): заменить
хранилище на `INCR`+`EXPIRE`, in-memory оставить фолбэком для dev.

**Риски:** новый сервис и новая точка отказа; нужен только со второго процесса.

## Чего не советую делать сейчас

- **Полный Signal-протокол (A4)** — недели работы, ломает мультидевайс; сначала
  A5.
- **SFU для групповых звонков** — инфраструктура на отдельный сервер, ломает E2EE
  звонков; mesh до 4 человек закрывает 90% сценариев.
- **Треды** — меняют всю модель ленты; при текущем числе пользователей отдачи не
  дадут.
