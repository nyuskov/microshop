# Ротация ключа шифрования «в покое» (AT_REST_KEY)

Зачем: этим ключом зашифрованы тексты в БД (`core/at_rest.py`) и все файлы media
(`core/media_crypto.py`). Если ключ утёк (попал в переписку, в чужой ноутбук, в
лог, в копию `.env`), надо просто сменить его. Без поддержки ротации смена ключа
означала бы «вся история нечитаема» — поэтому её и откладывают, а это худший
вариант: скомпрометированный ключ остаётся в работе.

Устроено так же, как ротация JWT-секрета (`docs/jwt-rotation.md`):

- пишем **только текущим** ключом (`AT_REST_KEY`);
- читаем текущим и прошлыми (`AT_REST_KEY_PREVIOUS`, можно несколько через
  запятую — если ротаций было несколько);
- в шифротексте есть **номер ключа** (первые 8 hex-символов SHA-256 ключа):
  формат значения `enc:v2:<номер>:<base64>`, формат файла — заголовок
  `encf:v2:<номер>:…`. По номеру сразу видно, что ещё не перешифровано, и не
  нужно перебирать ключи на каждом чтении;
- старые данные (формат `enc:v1:` / `encf:v1:`, без номера) читаются перебором
  известных ключей — совместимость сохраняется.

## Процедура

```bash
# 1) Сгенерировать новый ключ
openssl rand -hex 32
```

2. В продовом `~/microshop/.env` (старый ключ — из менеджера паролей, не
   копированием из дампа):

```dotenv
AT_REST_KEY=<НОВЫЙ ключ>
AT_REST_KEY_PREVIOUS=<СТАРЫЙ ключ>
```

3. Применить (нужен деплой или перезапуск web/worker — переменные передаются в
   оба сервиса; `.env` сам в контейнер не попадает, строки в compose уже есть):

```bash
ssh user@prod.example.com "cd ~/microshop && docker compose -p microshop-test \
  -f docker-compose.prod.yaml up -d --no-deps $(sh scripts/lib/web_slot.sh) worker"
```

4. Проверить, что история читается: открыть приложение (старые чаты, картинки),
   `./scripts/ci/smoke_prod.sh`. Если файл или сообщение показываются — значит
   прошлый ключ подхватился.

5. Перешифровать историю новым ключом (сначала посмотреть объём — команды
   идемпотентны и не мешают работе приложения):

```bash
docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web \
  poetry run python -m scripts.encrypt_texts --rotate --dry-run
docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web \
  poetry run python -m scripts.encrypt_texts --rotate
docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web \
  poetry run python -m scripts.encrypt_media --rotate --dry-run
docker compose -p microshop-test -f docker-compose.prod.yaml exec -T web \
  poetry run python -m scripts.encrypt_media --rotate
```

Повторный `--dry-run --rotate` должен показать `0`. Строки и файлы, которые не
читаются ни одним известным ключом, скрипты **не трогают** и пишут о них
предупреждение: перезапись без расшифровки зашифровала бы шифротекст повторно и
потеряла данные.

6. Убрать `AT_REST_KEY_PREVIOUS` из `.env` и перезапустить web/worker. После
   этого старый ключ больше нигде не нужен.

7. Удалить старый ключ из менеджера паролей (или пометить «скомпрометирован,
   выведен из эксплуатации»).

## Что важно помнить

- **Бэкапы.** Дампы и архивы media, снятые до ротации, зашифрованы старым ключом.
  Восстановление из такого бэкапа возможно, только пока старый ключ есть в
  менеджере паролей: перед удалением убедитесь, что свежий бэкап снят и проверен
  (`scripts/backup/verify_prod_backup.sh`).
- **Порядок «сначала прочитать, потом писать».** Если поменять `AT_REST_KEY`, не
  указав `AT_REST_KEY_PREVIOUS`, приложение начнёт писать новым ключом, а читать
  старую историю не сможет: текст и файлы будут отдаваться как шифротекст (`503`
  для медиа). Ключ при этом не потерян — достаточно вернуть старый в
  `AT_REST_KEY_PREVIOUS` и перезапустить сервисы.
- **Ключ не должен попадать в дампы.** Он живёт в `.env` и в менеджере паролей;
  если он оказался в бэкапе БД/медиа рядом с шифротекстом, смысл шифрования
  теряется — это и есть повод для ротации.
- **Смена ключа не трогает E2EE.** В личных чатах текст и часть вложений
  зашифрованы ещё и на клиенте — серверный ключ к ним отношения не имеет.

## Проверки

Тесты: `backend/tests/test_at_rest.py` (номер ключа в значении, чтение прошлым
ключом, несколько прошлых ключей, старый формат `v1`, мусор в списке ключей),
`backend/tests/test_at_rest_texts.py` (ротация истории в БД: пока прошлый ключ
на месте — читается, после `--rotate` читается только новым, чужие значения не
перезаписываются), `backend/tests/test_media_at_rest.py` (заголовок с номером
ключа, старый формат файла, `--rotate` файлов, файл с чужим ключом не портится).
